# EmberPad

The iPad app shows itself to users as **Ember Slate** (home-screen name and in-app text); the library header shows the Ember star mark alone; the project, targets, bundle IDs and paths keep the EmberPad name.

Base code for a personal offline iPad teaching app. The Ember House colour tokens, reusable type styles, original app and Companion artwork, and branded launch background, the phase-1 library screen, the initial worksheet chrome and the toolbar strip are in place; the teacher's on-device decisions are still pending. This is a development scaffold, not yet a classroom-ready release.

## Layout

| `Apps/Companion` | macOS menu-bar window (the sync server's status line, a warning row only while something needs the teacher, Present on Mac and Lesson recording, then **Settings…** and Quit) and its Settings window (Drive EMBER source folder, document counts per subject with a not-read list, iPad pairing code, the ink backup folder, an Open at login switch, a renewal placeholder), the Present on Mac presentation window with its optional projector backdrop and the lesson recorder, plus the Debug-only peer-to-peer hello listener |
| `Apps/EmberPadTests` | iOS unit tests of app-layer logic, hosted by the EmberPad app |
| `Apps/EmberPadCompanionTests` | macOS unit tests of the Companion, hosted by the Companion app, which then starts none of its models and runs headless (EP136): no Dock icon, never the active app, and the windows tests bring up are transparent, let clicks through and never take the keyboard (`CompanionWindowFocus`) |
| `EmberSyncKit` | Swift package target: validated manifests, streaming SHA-256, update planning, disk storage, expiry parser, the macOS Drive EMBER library reader, the transport-agnostic sync wire protocol, the Debug-only peer-to-peer hello framing and transport, pairing credentials with their Keychain store and TLS-PSK connection parameters, the macOS sync server and ink backup folder, the iPad's Bonjour connector, sync download and ink backup, the Present on Mac messages and link, the lesson recording's record, picture rule, audio health and video writer, and tests |

| `resign` | Uninstalled renewal script with its optional Outbox delivery, format helpers, disabled example config and LaunchAgent template |

No third-party app dependencies, extensions, entitlement files or capability-backed services. iPad deployment floor is 17.5, macOS floor is 14.0. The local build is Xcode 26.6 (17F113), iOS/macOS SDK 26.5. CI selects Xcode 26.6 on `macos-26`.

## Build and test without signing

```sh
swift test --package-path EmberSyncKit
xcodebuild -project EmberPad.xcodeproj -scheme EmberPad \
  -configuration Debug -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/emberpad-ios CODE_SIGNING_ALLOWED=NO build
UDID=$(xcrun simctl list devices available --json | python3 -c 'import json,sys; d=json.load(sys.stdin)["devices"]; c=[x for v in d.values() for x in v]; print(next((x for x in c if x["name"].startswith("iPad")), c[0])["udid"])')
xcodebuild -project EmberPad.xcodeproj -scheme EmberPad \
  -configuration Debug -destination "id=$UDID" \
  -derivedDataPath /tmp/emberpad-test CODE_SIGNING_ALLOWED=NO ONLY_ACTIVE_ARCH=YES test
xcodebuild -project EmberPad.xcodeproj -scheme 'EmberPad Companion' \
  -configuration Debug -destination 'generic/platform=macOS' \
  -derivedDataPath /tmp/emberpad-mac CODE_SIGNING_ALLOWED=NO build
xcodebuild -project EmberPad.xcodeproj -scheme 'EmberPad Companion' \
  -configuration Debug -destination 'platform=macOS' \
  -derivedDataPath /tmp/emberpad-mac CODE_SIGNING_ALLOWED=NO test
zsh -n resign/renew.zsh
plutil -lint resign/dev.emberpad.renew.plist
```

These commands do not install on a device, provision an App ID or need an Apple account. The bundle IDs are final: changing the iPad ID later means deleting the app and its ink. The checked-in `EmberPad.xcodeproj` and shared schemes are the source of truth. `Apps/EmberPad`, `Apps/Companion`, `Apps/EmberPadTests`, `Apps/EmberPadCompanionTests` and `Apps/EmberPadUITests` are file-system synchronized folders, so adding or removing a `.swift` file there needs no `project.pbxproj` edit (`Info.plist` files stay referenced by path and are excluded from membership). Commit test changes with source changes.

The GitHub workflow runs package tests, both unsigned builds, the EmberPadCompanionTests macOS suite, the EmberPadTests simulator suite, the EmberPadUITests real-touch suite, and syntax/plist checks. The simulator and real-touch suites are split over four parallel `ipad-tests` shards: shards 1, 2 and 4 name their test classes and shard 3 runs every class the others do not name, so a new test class needs no workflow change. `python3 -I scripts/check_test_shards.py` checks that every test class runs in exactly one shard. The shards run on an iPad Pro 11-inch (M5) Simulator on the newest iOS runtime the runner has, found or created by `scripts/pick_ci_simulator.py`; the job fails, naming what is installed, when there is none, and never takes another size, because how much of a page fits on the screen is part of what some UI tests check (on a 13-inch iPad in portrait the Teacher copy panel opens naming page 2). Each test in a shard may run for 5 minutes, twice the longest any has taken in CI; one that hangs then fails by name and the rest still run, where before it ran until the job's 30 minutes were up. On a Simulator xcodebuild cannot say where a hung test was stuck, so `scripts/report_hung_test.py` watches the log and prints into it where every thread of the app is when a test has logged nothing for 150 seconds, each stack once with how many threads are stuck there. In the unit-test process PDFKit's automatic page analysis (Vision text and form recognition on every PDF page a PDF view shows) is switched off by its own undocumented settings, registered by the test bundle's principal class (`Apps/EmberPadTests/PDFPageAnalysisOff.swift`) before the first test: over hundreds of tests that analysis took every background thread the process may have, and `StudentBackdropTests` then hung showing a window (EP146). The app, and the app the UI tests launch, still analyse pages; `PDFPageAnalysisOffTests` fails if the settings stop working. Run only the UI tests locally with `-only-testing:EmberPadUITests` on the test command above. Ink feel, touch routing, Pencil double-tap, rendering at 1x/2x, capture traits, external-display behavior and signing cannot be established by those checks.

## Drawing stress test on an iPad

`scripts/device-stress-test.sh <device-udid> <output-dir>` writes on a simulator or a connected iPad as fast as a student does, with every tool: fast fountain-pen brackets, long writing, strokes started while the last one is still landing, every pen colour and width, hold-to-line, hold-to-shape, shapes, the highlighter, both erasers at every size, erasing and then writing straight on (scrolling away and back, and changing page, in between; what was erased must never show again, EP113), lasso and circle-to-lasso moves (and a lasso drag and resize on a page full of ink, where the dragged ink must keep up with the finger, and big lassos closed round much of that page, which must select without freezing it), scribble-to-erase, the laser, undo and redo bursts, rapid tool switches, a toolbar drag, and writing straight after a zoom, a scroll or a page change. While it draws it watches every frame and checks that no stroke is lost or doubled, landed ink never leaves the screen even for one frame, each undo takes one stroke and redo brings it back, erasers remove exactly what they should, and latency and frame stalls stay within the bounds in `StressBounds`. It writes `summary.json` and `summary.md` (with the measured numbers and evidence pictures) to the output directory and into the result bundle. The tests run in a separate app, Ember Stress (`io.github.ka1oww.emberpad.stresstest`), installed beside Ember Slate and never over it (the script removes only an earlier copy of Ember Stress, so PencilKit's record of past drawings never carries over), in temporary libraries, with synthesized Pencil input and no Mac pairing; Ember Slate and its notebooks are never touched. On a physical iPad set `DEVELOPMENT_TEAM` first; the script passes `-allowProvisioningUpdates`. `DeviceDrawingStressTests` skip themselves unless the script runs them, and CI leaves them out.

## Pen-to-projector latency of Present on Mac

Present on Mac's latency is measured from a Pencil sample reaching the iPad's student view to the Mac finishing the frame that first shows it, and split into parts: the wait for the iPad's present loop, encoding, the send queue, the link, and on the Mac the receive, the decode, the wait for its frame, the render and the present. The total is given with and without the first of those. The iPad stamps each update on its way out; a Mac that is asked reports when each one arrived and when its frame was shown; the two clocks are lined up from those same messages, with an error of at most half their round trip, which the report states. In normal use no update asks for times and the Mac reports none: the measurement is on only in the tests below.

`PresentLatencyTests` in the Companion's tests runs it headless over the real link on loopback (TLS-PSK, the real sync server, the real presentation window) with a scripted stroke, prints each part's p50, p95 and max in milliseconds, and fails when the Mac's frame or the whole path is slower than `PresentLatencyBounds`. Set `TEST_RUNNER_EMBERPAD_LATENCY_OUTPUT=<folder>` to keep the numbers as files.

`scripts/device-present-latency.sh <device-udid> <output-dir>` measures the same between a connected iPad (or a simulator) and this Mac over their real link. It starts a debug Ember Companion as a latency host (`-EmberPresentLatencyHost`, compiled out of Release builds) with a pairing made for the run, and runs `DevicePresentLatencyTests` on the iPad in Ember Stress, once without a lesson recording and once while the Mac records. It writes `present-latency.md`, `present-latency.json` and `present-latency-samples.json` to the output directory. It never touches Ember Slate, the teacher's Companion, its pairing, the library or the lessons folder; the first run asks for Local Network access on the iPad. On a physical iPad set `DEVELOPMENT_TEAM` first. `DevicePresentLatencyTests` skip themselves unless the script runs them, and CI leaves them out.

## Offline library

Import PDFs with **Import from Files**, choosing an existing or new class name. Files open through security-scoped coordinated reads and are copied into the app. Encrypted/locked or unreadable PDFs are rejected. A Finder/Files delivery can also place PDFs at `Documents/Inbox/<Class>/<file>.pdf`; a loose Inbox PDF goes to `Unfiled`. The reserved `Documents/Inbox/EmberLibrary` folder is the Mac's library delivery, described below, and is never read as loose PDFs. Nested paths within a class are preserved as source identity. Inbox is checked on foreground and by **File Inbox**. `Documents/Inbox` is reserved by iOS, which creates it itself and refuses to let the app create it, so a missing Inbox counts as empty and is never created. Retained Inbox files are idempotent receipts, and are never deleted while a sender could be writing them. Symlink deliveries are skipped. No absent-file deletion is inferred from an incremental Inbox.

If separate import locations would otherwise share a class/path, EmberPad gives the later assignment an available visible filename suffix, preserving any existing suffixes. It remembers each source's assignment, so re-imports keep their identity across picker batch order, Inbox/Files arrival order and app/store reopen. A changed file at that same source path follows the version rules below.

The library sidebar groups non-archived Student worksheets by subject and shows their counts; **Archived** shows archived Student worksheets. Each subject is a folder browser that mirrors the Drive EMBER folder (EP69): its top level shows the subject's Drive folders (NOTES & TUTORIALS, Answering Technique, Organic Memory Sheets, TYS PAPERS, PRACTICAL and the rest) and any PDF filed loose in the subject folder. Tap a folder to open it; opening a topic such as Alkanes shows its notes beside its nested Tutorial folder, exactly as in Drive. A breadcrumb above the title and a back chevron lead to any folder above. Opening a folder slides it in like GoodNotes' folders (EP81), which use the standard iPadOS navigation push: the folder's page comes in from the right edge of the library column over the page you were in, which moves about a third of the way left underneath and dims slightly. Back and the breadcrumb play the exact reverse, and the parent comes back with the folder you left in view. The curve is a critically damped spring of about 0.3 seconds, with no bounce. Sidebar changes switch instantly. With Reduce Motion on, the pages cross-fade in 0.2 seconds instead of sliding. See the EP81 frame strips from a Simulator recording (synthetic library): [open a folder](docs/screenshots/ep81/push.png) and [Back](docs/screenshots/ep81/pop.png). Folder cards show the folder's item count (subfolders plus worksheets directly inside). Folders come first, then worksheets, both in Drive's name order (case-insensitive, "Paper 2" before "Paper 10"); the sort menu also offers Newest first and Oldest first for the worksheets. Inside a folder a card shows only the file's own title, without the folder context. **All subjects** shows each subject as a folder. The tree is worked out from each copy's source path every time, so no document folder or stored format changes; a worksheet imported from Files sits at its class folder's top level. There is no class filter. Drive folders that only hold build copies of PDFs filed elsewhere are hidden: a folder whose name contains `Source (LaTeX)`, ends with `Word Source`, or is `Source` (case-insensitive; `Text Sources` stays). Copies delivered from them before EP69 are hidden from the subject folders; an inked one stays reachable under **Archived**, where it has no Unarchive action. Cards use the Student copy's first page as a thumbnail and can show Updated, Older version, Teacher-paired and Ink badges. Card titles stay level whether or not a card has a badge. Opening a worksheet hides the sidebar so the worksheet fills the screen, in portrait and landscape; Back restores the sidebar as it was. A worksheet opens and closes like a GoodNotes document (EP87): GoodNotes neither slides the document in nor flies the tapped thumbnail into the page; it zooms about the centre of the screen. Tapping a card fades the library off the worksheet's bars, which stand where they sit (most of the library is gone in 0.1 seconds), and the page grows from about half size to full as it fades in, decelerating, in about 0.2 seconds. The zoom starts once the page has loaded and always ends when it would have, so a page that loads late zooms over what is left of it and one that loads too late simply appears when it is ready, as GoodNotes' does; the page is never in place later than it was with the old slide. The first worksheet opened after launch usually just appears. Back fades the bars quickly while the page shrinks a little toward the centre and fades over the library, which is already back underneath on the same folder and scroll position, in about a quarter of a second. Reopening the worksheet left open at launch does not animate. With Reduce Motion on, both directions are a 0.2 second cross-fade with no scaling. The system sidebar toggle is the only one, and **Import from Files** appears once, in the library toolbar. The toolbar search covers the open folder and every folder below it (in **All subjects**, the whole library; in **Archived**, the archived worksheets): every word typed must appear in the worksheet's own title or the names of its folders below the open one, in any order, ignoring case and accents. Results are listed as worksheets only, each with a folder line showing where it sits, and the subline reads "N of M worksheets" while a search is active. Archived cards show the same folder line. **Export flattened PDF** (worksheet More menu and a card's long-press menu) renders every page of a Student copy with its committed ink into a new PDF and opens the system share sheet. Both exports ask first, in a submenu (EP159): **With Ink** is the flattened export described here, and **Without Ink** shares the worksheet's original pages with no ink read or drawn, in the same order and sizes and with the pages added in Ember Slate, named `<title> (no ink).pdf` (or `<title> p<N> (no ink).pdf` for Export This Page). Ink for an open worksheet is taken from memory, so strokes still waiting for the one-second save are included. The export reads the stored PDF and drawings but never writes to them; it is built in a temporary folder that is removed when the share sheet closes. Teacher copies cannot be exported. Pages keep their original size; ink is rasterised at 3x over the vector page, so text stays sharp. Rotated pages (90 or 270 degrees) are exported at their displayed size, so ink lines up with what you saw on screen. **Export This Page** (worksheet More menu, beside Export flattened PDF) does the same for only the page in view: a one-page PDF named `<title> p<N> (annotated).pdf`, with the same renderer, ink flattening, read-only guarantees and Student-copy-only rule. Ink saved on other pages is not read. See the Simulator captures of the [More menu](docs/screenshots/export-this-page-menu.png) and the [share sheet](docs/screenshots/export-this-page-share-sheet.png), and the [exported page](docs/screenshots/export-this-page-output.png), all from a synthetic worksheet.

Each document version has its own `Application Support/Library/<UUID>/` folder:

```text
original.pdf            # untouched PDF bytes for this version
doc.json                # format 2: source class/path/hash and publication record, dates, status, ink pages, paired copy
pages.json              # every page in order: the PDF's own pages (ids pdf-0, pdf-1, ...) and pages added in Ember Slate,
                        # with each page's rotation and bookmark when set (EP62)
ink/pdf-0.drawing       # one page's ink by page id, native PKDrawing.dataRepresentation()
ink/<uuid>.drawing      # ink on an added page
```

Ink is stored by page id, so adding or deleting a page never moves another page's ink (EP61). A folder written before pages could be added has `page-<n>.drawing` files and no `pages.json`; the first time anything reads it, the store moves each `page-<n>.drawing` to `ink/pdf-<n>.drawing` and then writes `pages.json`. The moves are listed first in a `.pages-migration.json` journal, each is a rename within the folder, and `pages.json` is written last, so a crash at any point finishes the same moves on the next launch without losing or misplacing ink. `original.pdf` is never touched. A page added to a worksheet also counts as the teacher's work, like ink: a changed delivery adds an **Updated** copy beside it rather than replacing it.

EP62 adds two optional fields to a page in `pages.json`: `rotation` (90, 180 or 270, quarter turns clockwise on top of the PDF page's own rotation) and `bookmarked` (true). Each is written only when set, so a worksheet nobody turned or bookmarked keeps the exact `pages.json` it had, and a file written before EP62 reads as unturned and unbookmarked; the format stays `emberpad.pages/1`. Pages may also appear in any order, as long as each of the PDF's own pages appears exactly once. A turned page's ink is stored as if the page were not turned, so it always fits the page as `original.pdf` draws it; it is turned with the page on screen, in the student view and in exports, and turned back when it is saved. Turning a page therefore never rewrites its ink file. A moved or turned page counts as the teacher's work, like an added page; a bookmark alone does not, since it only helps find a page.

The app's `DocumentSession` owns every page drawing and updates from `canvasViewDrawingDidChange`, independently of overlays. It saves about one second after changes and flushes on editor exit and backgrounding. Save errors stay visible; corrupt saved ink never silently becomes an empty drawing. Once a closed worksheet's ink is saved, its session leaves memory with its editor (EP160), and opening it again reads both back. A memory warning drops the page thumbnails and Present's paper for all but the pages just shown, all of which can be made again. `MemoryStaysBoundedTests` runs a long presented, recorded lesson across two worksheets and checks that it adds no more than a budget to memory and stops growing. Storage uses Documents/Application Support, with no reliance on Caches. Deleting the app still deletes this data; the ink backup below keeps a copy of every inked Student worksheet on the paired Mac.

Same path and checksum is a replay. New bytes without ink replace the current copy while retaining the prior folder in hidden `.Previous` for 30 days. New bytes with ink create an **Updated** copy and mark the annotated one **Older version**; ink never moves to new bytes. An open, uninked worksheet is pinned: changed deliveries wait until the editor closes so an old canvas cannot write onto a replacement PDF. Recheck Inbox after closing it. Previous-version pruning is an explicit store operation; the base keeps versions conservatively until that maintenance path is wired.

The complete-manifest planner also returns archive and no-download relink actions for Mac deletion/rename. Ambiguous identical hashes are imported and archived conservatively rather than assigning somebody else's ink. Full manifests arrive by the Inbox copy or by sync, described below; the iPad has no cloud folder access (Debug builds also carry the synthetic peer-to-peer hello below).

### Library model v2

A version-2 manifest gives every entry a publication record: subject, optional class tag, a stable paper key, role (`student` or `teacher`), display title and an optional `archived` mark (written only when true). Each paper key has at most one copy per role. An archived copy is listed only under **Archived** on the iPad, beside copies archived because they left the Mac library, and it still pairs with its counterpart. Version-1 manifests and Inbox deliveries still load as Student copies whose subject is the class folder; the iPad never infers a Teacher role from a file or folder name. Format-1 `doc.json` files still load as Student copies and are upgraded to format 2 when next written. Format 2 keeps the publication record in `source` and stores `pairedDocumentID`: the single current copy of the opposite role with the same paper key, recomputed after document imports, replacements, relinks and archives.

A document's identity is its path plus role, and its role never changes, so one path may hold a Student and a Teacher copy and a role change files a new copy beside the archived old one. Student copies keep the rules above. Teacher copies cannot be inked in this version: the store refuses Teacher ink, a changed Teacher copy replaces in place, and a Teacher copy at a new path follows its paper key to its existing document. No rule replaces an inked document, moves ink onto other bytes or relinks across roles.

### Library source: Drive EMBER folder (macOS)

`EmberLibrarySource` builds a version-2 manifest from the Google Drive EMBER folder. `EmberLibrarySource.discoverDriveRoot()` finds it at `~/Library/CloudStorage/GoogleDrive-*/My Drive/EMBER`, taking the first Drive account folder by name that has one; a root passed in explicitly is used as given, and tests use synthetic trees. It only reads, and it never follows symlinks.

- **What is included:** eligible regular `*.pdf` files below the root, case-insensitively, including single-copy notes, commonly asked question booklets, answering techniques and TYS papers. Discovery is based on files; sign-off and publication records are not consulted. Hidden entries (names starting with `.`) and symlinks are skipped. Non-PDF files are skipped and counted. Build output is skipped and counted, never read: PDFs below folders named `redraws`, `crops`, `_build`, `artifacts`, `_assets`, `_qa` or starting with `_redraws`, PDFs below source folders (a name containing `Source (LaTeX)`, ending with `Word Source`, or equal to `Source`; `Text Sources` is kept), all case-insensitive, and the shared logo `ember-star.pdf`. A previous copy from a source folder is not carried forward.
- **Subject:** the top-level folder: `EMBER CHEMISTRY` is Chemistry, `EMBER MATH` is Math, `EMBER PHYSICS` is Physics and `EMBER BOOKLETS (MI + JC)` is Booklets. Any other top-level folder is a subject under its own name, except that leading underscores are removed from an underscore folder's subject name; a PDF directly in the root is General. The path below the subject folder is the manifest path and the title context: `NOTES & TUTORIALS/Topic/Notes.pdf` shows as **NOTES & TUTORIALS / Topic / Notes**.
- **Teacher pairing by name, in one directory:** a name ending in a Teacher marker pairs with the same-directory PDF whose name is identical once its marker is removed (case and repeated spaces ignored). Markers include `Teacher`, `Teacher Copy`, `Teacher Version`, `Solutions`, `Answers`, `Answer Key` and `Mark Scheme`, either in brackets (`(Teacher)`), after a hyphen, dash, underscore or em dash, as a trailing word, or as the whole name (`teacher.pdf`). A bracketed group at the end that contains the word Teacher also counts. A Student marker (`Student`, `Student Copy`, and corresponding version forms) is removed the same way. Both copies share the paper key `<subject>/<folders>/<name without marker>`. A PDF with no partner is a single-copy Student document, and an unpartnered Teacher-marked PDF is still delivered with role `teacher`, so it never becomes a Student copy. When a directory has exactly a Student-marked PDF and an unmarked PDF of the same name (and no Teacher-marked one), the unmarked PDF is the Teacher copy and the two pair, since Drive files the blank copy as `(Student)` beside the full-answers copy. Any other mix under one key, such as an unmarked, a Student-marked and a Teacher-marked PDF, or two Student-marked PDFs, is still held back as `duplicate-paper-key`.
- **Archive folders:** a delivered document below a non-build-output folder whose name starts with `_` (such as `_legacy-archive`) is delivered with the `archived` mark. A nested underscore folder stays in its source path but not its title; for a top-level underscore folder, leading underscores are removed from the subject name. Build-output folders remain excluded even when their names start with `_`.
- **Identity and misses:** content identity is the SHA-256 of the bytes. A file or folder that cannot be read (Drive offline, not downloaded yet, or metadata unavailable) is a miss with reason `unreadable`, never a deletion. Other miss reasons: `duplicate-paper-key` (two copies of one role under one key, or one path; all are held back rather than guessed between), `privacy-withheld`, `identical-copies` and `student-matches-a-teacher-copy` (a Student copy whose bytes equal any Teacher copy is held back, and the Teacher copy is still delivered), and `invalid-name`.
- **Carry-forward:** pass the previously delivered manifest as `previous`. Each previous copy (paper key and role) that is not delivered this run is carried forward unchanged, as `source-vanished`, `source-unreadable` or `held-back`, so a vanished source means "no update" and the planner never archives it. A carried copy still passes the privacy and cross-role checks.

Class is the folder- or file-name prefix (`MI PU1-3`, `YIJC JC1-2`, `NYJC-EJC JC1-2`, `SEC 1-4`), the first folder below the subject that has one winning over the file name. A prefix can also come from the alias table loaded from `~/Library/Application Support/EmberPad/class-aliases.json` and passed to `EmberLibrarySource` (synthetic example: `EmberSyncKit/Examples/class-aliases.example.json`). With no prefix, the copy belongs to **All classes**. Alias values must be known class codes or short uppercase tags matching `^[A-Z0-9][A-Z0-9-]{0,11}( [A-Z0-9][A-Z0-9-]{0,11}){0,2}$`; other values are skipped and counted. In every folder and file name, each `Sec 1-4` or `S1-4` token is checked against the complete word segment before it (after the preceding section token, if any): it must be empty, a class code or an alias key. Otherwise that segment's words are withheld and removed, and no class comes from it. Non-class name words in alias keys and configured `withhold` terms are also withheld. The real table is personal data and never goes in the repository. A final check rejects any copy whose emitted class tag is invalid, or whose source path, title, subject or paper key still contains a personal-name shape or withheld term. The local path of each copy and the miss list stay on the Mac and never go in the manifest.

The Companion's menu-bar window keeps only what is used in class (EP139): the sync server's status line, a warning row that appears only while something needs the teacher (the lesson is not saving sound or failed, the EMBER folder is not found, the last automatic Prepare failed, PDFs were not read, or no iPad is paired), the Present on Mac and Lesson recording sections, and **Settings…** (Command-comma) beside **Quit Ember Companion**. **Settings…** opens one Settings window, never at launch, with everything set up once: the EMBER folder and **Prepare iPad library**, the subjects and the not-read list, the iPad pairing, the ink backup folder, Open at login and renewal. The macOS Companion defaults to the discovered Drive EMBER folder and remembers a folder chosen with **Choose EMBER folder…**. The Companion prepares the iPad library by itself: once at launch, after **Choose EMBER folder…**, and whenever anything below the EMBER folder changes (a PDF or folder added, changed, renamed, moved or deleted, at any depth). `LibraryAutoPrepare` watches the folder with FSEvents, so there is no polling, and runs the same Prepare as the button (`LibraryOutbox.prepare(from:aliases:)`) once the folder has been quiet for 30 s after the last change. It waits longer while a changed PDF's modification date is less than 30 s old, which means it is still being written, but no more than 10 minutes in all. It never runs two Prepares at once: a change during one schedules exactly one more after it. Events that cannot change the library are ignored: hidden and non-PDF files (which only lengthen a wait already running), extended attributes, and the clone flag that each Prepare's own APFS copy into the Outbox reports on its source. A pending Prepare whose only changes are such clones of files whose size and date still match what the last Prepare read is dropped. On a Google Drive CloudStorage folder, files that Drive for desktop syncs in arrive as created events, and an online-only placeholder that is downloaded or made online-only again arrives as a modified event. Reading a placeholder downloads it, so the first Prepare after that is followed by one more. **Prepare iPad library** still prepares now and replaces any pending automatic Prepare. Below the buttons the Settings window shows whether it is watching, a change waiting to settle, when the library was last prepared automatically, and why the last automatic Prepare failed, with no popups. A Prepare reads and hashes every PDF each time: for the 386 documents in the real EMBER folder (212 MB) that took about 1 s with the files cached and 6 to 7 s cold. The window shows document counts per subject, the pair, single-copy and archived totals, and the PDFs or folders not read this time with their reasons. Preparation never writes inside the EMBER folder; it writes the iPad Outbox described below. The [light](docs/screenshots/companion-light.png) and [dark](docs/screenshots/companion-dark.png) screenshots show these sections as they were in the menu-bar window before EP139 moved them into Settings.

### Library delivery: Outbox to Inbox

**Prepare iPad library** writes the Outbox at `~/Library/Application Support/EmberPad/Outbox`: `EmberLibrary/manifest.json` (the version-2 manifest) and `EmberLibrary/files/<sha256>.pdf`, one PDF per content hash, so no local file name leaves the Mac. The Outbox's own manifest is the `previous` manifest for the next read, so a copy missing from Drive is carried forward with its bytes from the old Outbox. Every PDF read this run is copied in and checked against its manifest hash; if one changed meanwhile, the write fails and the old Outbox stays. A new Outbox is built in a hidden staging folder beside it and swapped in with one atomic rename (`RENAME_SWAP`), so a reader sees either the whole old Outbox or the whole new one.

The optional delivery in `resign/renew.zsh` copies the Outbox into the iPad's `Documents/Inbox` (see [resign/README.md](resign/README.md)). On foreground and **File Inbox**, the iPad reads `Inbox/EmberLibrary/manifest.json`; a manifest that is cut short or not version 2 changes nothing. It plans the whole manifest through `DiffPlanner`, then runs each action that needs bytes only when that PDF is present with the manifest's size and SHA-256 and opens as a PDF. Archive actions run only when every such action succeeded, so a half-delivered or interrupted copy files what arrived and archives nothing; the next check finishes it. Ink rules are the store's usual ones: an inked copy gets an **Updated** version beside it, and an open worksheet waits. Only documents that came from a library delivery are ever archived; worksheets imported from Files or loose Inbox PDFs are not. A completely applied delivery is recorded by its manifest hash and not applied again, and only then are Inbox copies the manifest no longer lists removed. Loose Inbox scanning skips the reserved `EmberLibrary` folder.

### Sync wire protocol

`Wire*.swift` in EmberSyncKit is the private protocol a later transport carries between the Mac (server) and the iPad (client). It opens no connection itself: `WireClientSession` and `WireServerSession` are pure state machines that take received bytes and the current time and return frames to send and events, so a driver moves bytes and calls `tick` on a timer. The server emits at most one frame per `receive` call; send that frame, then call `receive(Data(), now:)` while `hasPendingInput` is true before reading more transport bytes. This bounds response generation for coalesced requests while preserving the transport's backpressure. `InMemoryWireTransport` is an in-process pair with bounded buffers for tests; it opens no socket.

A frame is a 1-byte type, a 4-byte big-endian payload length and the payload. The client sends HELLO (magic `EMBR`, version range, role, largest chunk and manifest it accepts) and the server answers HELLO with the highest common version. The client then sends GET-MANIFEST (answered by MANIFEST, the `ManifestCodec` JSON) and GET by SHA-256 with initial credit (answered by DATA chunks at explicit offsets and a final END with the total length). Each request has a strictly increasing client-chosen id and gets exactly one terminal frame: MANIFEST, END, PUT_DONE, DIGEST or a request ERROR (not found, cancelled, stalled, busy, manifest too large, unavailable, rejected, storage failed, integrity failed).

Version 2 adds one upload, PUT, used only by the ink backup and only from the iPad to the Mac. PUT announces a size, a SHA-256 and up to 4 KiB of JSON metadata; the Mac answers PUT_DONE "already held", or grants PUT_WINDOW credit, and the iPad sends PUT_DATA at explicit offsets within that credit and then PUT_END. The Mac hashes as bytes arrive and answers PUT_DONE only once the size and SHA-256 match and the copy is stored. A PUT is at most 256 MiB. Both peers still offer version 1: a version-1 peer never receives a PUT frame, because the iPad sends PUT only when version 2 was negotiated, and a session at version 1 treats one as a protocol violation. PUT never travels Mac to iPad, and PUT_WINDOW and PUT_DONE never travel iPad to Mac.

Version 3 adds one small question, GET_DIGEST (EP91). The iPad sends a request id (a 9-byte frame) and the Mac answers DIGEST with the SHA-256 of the manifest's `ManifestCodec` JSON, exactly the bytes a MANIFEST would carry (a 41-byte frame), or a request ERROR `unavailable` before **Prepare** has run. The Mac reads the manifest afresh for each GET_DIGEST, as for GET_MANIFEST. A sync writes those same bytes as its downloaded manifest, so the digest equals the library's applied-delivery receipt once that manifest is filed. Every peer still offers versions 1 and 2: the iPad sends GET_DIGEST only when version 3 was negotiated, and a session at version 1 or 2 treats one as a protocol violation.

Version 4 adds Present on Mac (EP93): PRESENT (type 17, iPad to Mac, up to 16 MiB) carries one encoded `PresentUpdate`, and PRESENT_REPLY (type 18, Mac to iPad, up to 64 KiB) carries one `PresentReply`. They are opaque to the wire session; `PresentMessages.swift` defines their contents (below). Every peer still offers versions 1 to 3. The iPad sends PRESENT only when version 4 was negotiated, a session at version 1 to 3 treats one as a protocol violation, and a Companion from before EP93 never receives one: the iPad's HELLO tells it the Mac is older and it says so. Sync, GET_DIGEST and the ink backup are unchanged.

Version 5 adds lesson recording (EP129) and no frame type: on a version-5 link a `PresentUpdate` may also carry the open document's name and role (`d`) and the teacher's Start or End lesson (`c`), and a `PresentReply` may be the Mac's lesson status. Unknown keys are ignored by a version-4 decoder, but the iPad still sends them only on a version-5 link, and the Mac sends a lesson status only to a version-5 iPad, so an older peer on either side presents exactly as before. Every peer still offers versions 1 to 4.

Flow control is per transfer credit: the server sends only bytes the client has granted, chunked to the smaller of both peers' limits and round-robin across transfers. The client grants WINDOW increments only as the app reports bytes written, so a slow writer holds at most one window. The client checks every chunk's offset and credit, hashes the bytes as they arrive and reports a completed file only when the size and SHA-256 both match. CANCEL fails a request at once and discards its late bytes until the server acknowledges. A transfer with credit outstanding and no progress stalls on the client; one the client leaves without credit is dropped by the server. Unknown, out-of-direction and oversized frames are rejected from their headers before their payloads are buffered; malformed payloads are rejected when decoded. These violations close the session with a protocol-violation ERROR. Every length is bounded: chunks to 1 MiB, manifests to 32 MiB and credit to 16 MiB per transfer; concurrent requests are limited by `WireLimits`.

### Pairing

`PairingCredential`, `PairingKeychain` and `PairingTLS` in EmberSyncKit pair one Mac with one iPad. In the iPad section of the Companion's Settings window, **Pair iPad…** creates a pairing if there is none: a 256-bit secret and a 128-bit service id from `SecRandomCopyBytes`. The Mac saves it in its Keychain and shows it as a QR code (`EMBERPAD-PAIR:1:<service id>:<base64url secret>`, not a URL). The code opens in its own window with `sharingType = .none`, which keeps it out of screenshots and screen sharing where macOS honours that setting. The window closes after five minutes or on **Done**. On the iPad, tap **Pair with Mac…** in the library sidebar footer (or, when already paired, touch and hold **File Inbox** and choose **Pair with a different Mac…**), then scan the code with the camera. That needs only `NSCameraUsageDescription`, no entitlement. The camera preview is replaced while the screen is captured or a student display is connected. The scanner refuses any code not in the exact current format, and a refused code changes nothing.

Each side keeps the pairing only as one generic-password Keychain item (this-device-only on iPad, never synchronised). It is never stored in UserDefaults or files. Descriptions and reflection print `<redacted>` in place of the secret, and the app UI shows only the service id's first six characters and the date. **Forget iPad** on the Mac and **Forget Mac…** on the iPad each delete their own item. Once the Mac forgets, the old secret is useless: any new pairing has a fresh secret and service id. Pairing again overwrites the item, and **Pair iPad…** on the Mac treats an unreadable (corrupt) item as absent and replaces it with a fresh pairing.

`PairingTLS.parameters(for:)` is the only source of connection parameters for sync, and the Mac listener and iPad client use the same parameters. They set up TCP inside TLS 1.2 with a single PSK cipher suite (`TLS_PSK_WITH_AES_128_GCM_SHA256`) and peer-to-peer Wi-Fi on. The key is HKDF-SHA256 of the secret, bound to the service id; the PSK identity names the pairing, never the secret. The Bonjour type is `_embersync._tcp` and the instance name is the service id. Loopback tests over real sockets show the paired peer connects and negotiates that suite. A wrong key, a peer from another pairing, plain TCP, certificate TLS and a server with the wrong key all fail the handshake, and nothing they send reaches the server's reader. The Keychain store is tested against the real macOS Keychain under throwaway service names. The iPad app tests use an in-memory store, because the unsigned Simulator host has no Keychain entitlement. The Companion now listens (the sync server below); the iPad client (below) connects to it, so the Mac cannot tell whether the code was scanned until that iPad first syncs.

### Sync server

`SyncServer` in EmberSyncKit (macOS only) is the Companion's side of sync. While a pairing exists the Companion runs one: an `NWListener` on `PairingTLS.parameters(for:)`, so every connection uses the pairing's TLS pre-shared key and peer-to-peer Wi-Fi is on. That lets the iPad reach the Mac at home and at a venue with no shared Wi-Fi. It advertises the pairing's service id as `_embersync._tcp` over Bonjour, which needs the Companion's `NSLocalNetworkUsageDescription` and `NSBonjourServices` keys. A peer without this pairing's key fails the TLS handshake and never reaches the sync protocol. A connection that does not finish the handshake within 10 seconds is dropped, and at most four connections are open at once. **Forget iPad** stops the server at once; pairing again starts it with the new key. A failed listener retries by itself after five seconds.

Each connection runs one `WireServerSession` over `OutboxContentProvider`, which serves the Outbox's `manifest.json` and `files/<sha256>.pdf` by content hash. The manifest is read afresh for every request, so a new **Prepare iPad library** is served without a restart. Before **Prepare** has run, a manifest request gets `unavailable`. A file is opened with `O_NOFOLLOW` and must be a plain file, and it is read through that one descriptor for the whole transfer. The driver stops reading from the peer while 512 KiB of replies are still queued, and pulls file data only below that mark, so a slow iPad cannot make the Mac buffer the library.

While a transfer is in progress the server holds an IOKit `PreventUserIdleSystemSleep` assertion named "Ember Companion is sending the library to the iPad". It lets go two seconds after the last transfer ends, and on stop. The display may still sleep. The Companion header shows the server's status line: for example "Serving 16 documents · iPad synced 07:58", "Sending 2 files to the iPad", or "Sync unavailable · retrying". The iPad row adds the last sync time.

**Open at login** in the Companion's Settings window uses `SMAppService.mainApp`. It is off until you turn it on, and the Companion never registers itself. If macOS cannot find this copy of the app the switch is disabled, and if registering fails (for example in an unsigned build run from a build folder) the reason shows under it.

`SyncServerTests` run the real server on loopback with a real TLS-PSK `NWConnection`. The Outbox comes from the real Prepare path over a synthetic Drive EMBER tree, and the client is a small one built on EP-21's `WireClientSession`. The tests cover:

- the paired client fetches the manifest and every file, byte for byte, on window grants;
- the iPad's real `LibrarySyncDownloader` syncs the Outbox over the TLS-PSK connection and files it into a real library;
- a new Prepare is served without a restart, and an unknown hash is not found;
- wrong keys, another pairing, plain TCP and certificate TLS get no sync frame;
- a silent peer, connections over the limit and stop are all handled;
- the power guard is held only while sending, and the real assertion shows in `IOPMCopyAssertionsByProcess`.

`InkBackupTests` also run EP-24's real `LibrarySyncDownloader` end to end against this server (see Ink backup to the Mac below).

### Sync client (iPad)

Once paired, EmberPad syncs on launch, on every return to the foreground and on **Sync now** (in the library sidebar footer, which also shows the sync status, last synced time and plain error copy, and in the **File Inbox** menu). `LibrarySyncConnector` browses Bonjour for `_embersync._tcp` with peer-to-peer Wi-Fi on, takes only the instance named by the pairing's service id, and connects with `PairingTLS.parameters(for:)`, so a Mac without the pairing's key never gets a byte. The app declares `NSLocalNetworkUsageDescription` and `NSBonjourServices`; no entitlement is needed. A Mac not seen within 8 seconds is reported as not found, with nothing changed. Networking is foreground-only: leaving the app cancels the sync, and nothing runs while the iPad is not paired.

While EmberPad stays the active app, it also checks quietly about once a minute whether the Mac's library changed (EP91), so a worksheet the Companion prepares while the app is open appears without **Sync now**. `LibraryChangeMonitor` starts when the app becomes active (its first check is a minute after the foreground sync) and stops when it resigns active. Each check is one TLS-PSK connection found by the same Bonjour browse, carrying only HELLO and GET_DIGEST (`LibraryChangeProbe`): no manifest and no PDF. Measured against the real `SyncServer` over TLS-PSK on loopback, one unchanged check put 653 bytes of TCP payload on the wire (351 up, 302 down: the TLS handshake and four frames) and took about 6 ms, Bonjour aside; the real library's manifest, which a sync fetches, is roughly 150 to 200 KB. Only when the digest differs from the manifest the library last filed does the check run the usual sync, which downloads only the changed PDFs and backs up ink as every sync does. The check shares the sync's one slot, so a check and a sync never overlap; **Sync now** during a check cancels the check and syncs straight after it, and a check never runs while a sync does. It shows nothing itself: no status line, no error. A sync it starts shows its progress in the sidebar footer like any sync, and the library updates as it does today.

A check is skipped while Low Power Mode is on and while a worksheet is open, and runs as soon as the last open worksheet closes, so an open worksheet is never interrupted or reloaded. If a sync could not file a changed worksheet because it was open (the existing open-worksheet rule: it waits), the check after it closes syncs again and files it; it does not sync again for the same Mac library while the worksheet stays open. When the Mac cannot be reached (Companion closed, Mac asleep or out of range), or a sync the check started did not finish, the next check waits twice as long, up to five minutes, and returns to a minute after the next answer. A Companion from before EP91 only speaks versions 1 and 2: the iPad asks it nothing and stops checking until the next return to the foreground, and launch, foreground and **Sync now** still sync. A Mac with no library prepared counts as unchanged. Nothing about pairing, the TLS-PSK channel or the Companion's Prepare changes; the Companion serves GET_DIGEST from the same Outbox manifest, and a check is not counted as a sync in its header or held awake for.

Battery: an unchanged check wakes the Wi-Fi radio for well under a second to browse Bonjour (usually answered from the mDNS cache), make one TLS-PSK handshake and exchange those few hundred bytes, about 60 small radio bursts an hour while the app is open. Each burst costs a few tenths of a joule at most, so an hour of checks is of the order of 10 to 30 J: about 0.01 to 0.03% of an iPad battery of roughly 30 Wh (about 110 kJ), while the screen alone uses several thousand joules in that hour. This is an estimate from typical Wi-Fi power figures, not an on-device measurement. An unreachable Mac costs more per check (the Bonjour browse waits up to 8 seconds), which is why those checks back off to every five minutes.

`LibrarySyncDownloader` sends HELLO, asks for the manifest, plans it against the library with `DiffPlanner` and requests by SHA-256 only the PDFs an import, replace or new-version action needs. Each PDF is written to a hidden partial file and gets its `<sha256>.pdf` name only after the session has matched its size and SHA-256; bytes that do not match are dropped. The sidebar footer shows progress by bytes and files. The manifest is written last, atomically, in the same `EmberLibrary/manifest.json` and `files/` layout as the Inbox delivery, in `Application Support/Sync` (outside the Files-visible Documents folder). PDFs already verified stay for the next sync, which fetches only the rest.

The download is then filed by `LibraryDeliveryApplier.applyNewest`, the one manifest path for both routes: of the Inbox copy and the sync download it applies the one with the newer `generatedAt` (sync on a tie) and never the older one in the same check. The applied-delivery receipt now records the manifest's `generatedAt`, so an older manifest arriving later by either route is skipped as superseded instead of archiving papers the newer one added. All the Inbox rules above hold: ink is saved first, an inked copy gets an **Updated** version beside it, an open worksheet waits, and a cut-short sync files what arrived and archives nothing. After a complete apply the downloaded PDFs are removed, since the library holds them. **Last synced** is recorded only when the whole download arrived and the library holds a manifest at least that new.

The EmberSyncKit tests run EP-16's ink-safety tests over both routes, and run the client against a minimal in-test server built on `WireServerSession`, in memory and over real TLS-PSK loopback sockets. Bonjour browsing against an advertised in-test server runs only with `EMBERPAD_BONJOUR_TESTS=1`, because it uses the local network. The iPad tests drive `SyncClient` through `LibraryController` with synthetic PDFs.

### Ink backup to the Mac

On each sync, once the library download is filed and **Last synced** recorded, the iPad backs up its ink to the paired Mac over the same TLS-PSK connection (EP-33). It sends every Student worksheet whose ink changed since the Mac last confirmed a copy, as two files: an `.emberink` package (every inked page's PencilKit drawing, restorable as editable ink) and a flattened PDF (the same rendering as **Export flattened PDF**). Open worksheets are saved first; the backup only ever reads the library. The iPad remembers what the Mac confirmed in `Application Support/Backup/ledger.json`, per pairing, so pairing a new Mac sends everything again, and anything that did not reach the Mac is sent on the next sync. The sidebar's Mac sync line shows "Backing up ink to your Mac…" while it runs, then when the ink was last backed up and, on its own line, why a backup did not finish. A backup failure never fails, slows or undoes the library sync: a refused or failed copy, a dropped connection or leaving the app stops only the backup. A Companion from before EP-33 still syncs the library; the iPad asks for it to be updated. Nothing is ever sent back: the Mac never sends a backup to the iPad or changes its ink. Restoring inside the app is not part of this package.

On the Mac, the Companion's Settings window shows the **Ink backup** folder, when the last backup arrived, **Choose backup folder…** and **Show in Finder**. The folder defaults to `~/Library/Application Support/EmberPad/Ink Backup`. A folder inside Google Drive or any `~/Library/CloudStorage` folder, inside `~/Documents/Ember Projects` or inside the Outbox is refused (symlinks are resolved first), and a saved folder that later fails that check falls back to the default with a note. Changing the folder keeps earlier copies where they are. Copies are kept by subject and paper:

```text
Ink Backup/<Subject>/<Paper>/2026-11-06 19.42.10 ink 1A2B3C4D.emberink
Ink Backup/<Subject>/<Paper>/2026-11-06 19.42.10 annotated 1A2B3C4D.pdf
Ink Backup/<Subject>/<Paper>/.backup-index.json
```

`<Paper>` is the paper key without its subject (`Unit 1 - Paper 2`), or the title for a loose import; the time is when the copy arrived; the last part is the start of the iPad document id. Every copy is kept: nothing is overwritten or deleted, and a copy identical to the newest one of the same document and kind is answered "already held" instead of being kept twice. Each copy is written to a private file under `.incoming`, checked against its announced size and SHA-256, flushed to disk and only then linked into place under a name that cannot replace an existing file, so the folder never shows a partial copy. `.backup-index.json` lists every copy with its document id, title, SHA-256, size and arrival time. Names from the iPad are cleaned into single folder names and can never point outside the folder.

`InkBackupTests` cover the frames and version gating, PUT sessions (credit, already held, a hash mismatch, a storage failure, cancel and a stall), the folder (versions kept, nothing overwritten, cleaned names, no partial copy, refused locations), the ink package and the ledger, and loopback syncs: in memory, and over the real `SyncServer` with TLS-PSK sockets, with the real `LibrarySyncDownloader`. They show the upload, a new version on each ink change, a connection lost partway through a copy leaving the library sync whole and the rest sent next time, a copy the Mac fails or refuses, an older Mac, and an older iPad. The iPad tests drive `SyncClient` with real PencilKit drawings.

#### Restore drill

Run this drill once on a spare synthetic worksheet before relying on the backup, and again after any EmberPad update.

1. **Read the ink at once.** On the Mac, open the newest `annotated` PDF for the worksheet in Preview (Companion › **Settings…** › **Show in Finder**, then the subject and paper folder). It needs nothing from EmberPad. To have it on the iPad as a read-only page, AirDrop it and **Import from Files**; its ink is part of the page and cannot be edited.
2. **Get the worksheet back.** Reinstall EmberPad, pair again and sync, so the library downloads the PDF again. It gets a new document id.
3. **Unpack the editable ink.** In the same folder, decode the newest `.emberink` file into page drawings:

   ```sh
   python3 - "<the .emberink file>" "$HOME/Desktop/restored-ink" <<'PY'
   import base64, json, pathlib, sys
   package = json.loads(pathlib.Path(sys.argv[1]).read_text())
   assert package["format"] == "emberpad.ink/1"
   out = pathlib.Path(sys.argv[2]); (out / "ink").mkdir(parents=True, exist_ok=True)
   layout = package.get("layout")  # present only when pages were added, moved or turned in Ember Slate
   ids = [p["id"] for p in layout] if layout else [f"pdf-{i}" for i in range(package["pageCount"])]
   for page in package["pages"]:
       (out / "ink" / f"{ids[page['page']]}.drawing").write_bytes(base64.b64decode(page["drawing"]))
   if layout:
       (out / "pages.json").write_text(json.dumps({"format": "emberpad.pages/1", "pages": layout}, indent=2))
   print(package["title"], "- drawn on the PDF with SHA-256", package["pdfSHA256"])
   PY
   ```

4. **Check it is the same PDF.** The printed SHA-256 must equal `shasum -a 256` of the worksheet's PDF in the Outbox (`~/Library/Application Support/EmberPad/Outbox/files/<sha256>.pdf`). If the paper was revised since, the ink belongs to the older version: use the flattened PDF instead.
5. **Put the ink back.** With EmberPad closed, use Xcode › Window › Devices and Simulators › EmberPad › Download Container, copy the restored `ink` folder (and `pages.json`, when the script wrote one) into `AppData/Library/Application Support/Library/<new document id>/` (the folder whose `doc.json` names that worksheet), replacing what is there, then Replace Container. Open the worksheet: the ink is editable again, and the next stroke saves it as usual.

The header's **Pages** button (four squares, top left) and a tap on the "2 / 5" page pill open a page-thumbnail popover: every page with its current ink, the current page outlined; tapping a thumbnail jumps to that page and closes the popover. **Notebook tabs** (EP119), as in GoodNotes: every notebook opened from a library card or reopened at launch becomes a tab in a bar above the worksheet header, under the status bar, at the end of the bar (a notebook already open brings its tab forward rather than opening a second). Tap a tab to switch notebooks at once, with no transition; each comes back at the page, scroll position and zoom it was left at, from the same per-notebook store as a card reopen and a relaunch (EP121, `ReadingPositions`). Before the worksheet leaves for another tab it waits, for up to two seconds, for the Pencil to lift and PencilKit to commit every stroke it holds, puts back from the live pen any it never commits, lands every queued ink change and saves its reading position, then takes no more input, so no stroke is lost on a switch. **Add Page** (EP61, the page-with-a-plus icon after the Teacher copy toggle, GoodNotes' slot) adds paper to a Student copy. Squared paper is GoodNotes' grid: 5 mm squares in 0.5 pt light grey (#D9D9D9), centred on the page; Dotted uses the same pitch, and Ruled has 8 mm lines. Added pages are drawn as one-page PDFs and inserted only into the open worksheet's in-memory document, so the ink overlay, thumbnails, the student view and flattened export treat them like any page, at their own paper size; `original.pdf` never changes. A Teacher copy takes no added pages. Adding, duplicating or deleting a page saves the ink first, then reopens the worksheet on its new pages (undo history starts afresh). The Teacher copy panel still shows the paired answers; on an added page it shows "No answer page" over them, because the Teacher copy pairs only with the PDF's own pages. A duplicate of a PDF page keeps its answers.

**Page tools** (EP62) work on the page in view of a Student copy, like GoodNotes'. The header's **bookmark** (GoodNotes' slot, before Add Page) marks or unmarks it: filled Ember red when marked. **Moving the tool palette** (EP100, made floating in EP101, carried with no hold in EP102, carried freely in EP104). GoodNotes 6's Writing Tools menu floats over the page: its support article says to drag the floating menu to a screen edge, where it snaps to the top, bottom, left or right and turns upright on the sides. Ember Slate's tool palette works the same way. It is a rounded capsule as long as its tools, floating 10 pt in from an edge of the worksheet below the header, and the page no longer makes room for it: the page runs under it, as in GoodNotes. As in GoodNotes 6 there is no hold (EP102): touch the palette with a finger (on a tool or between them) and drag, and the palette itself moves with the finger once it has travelled 6 pt (less is a tap's drift), raised a little, with the tool the finger landed on staying under the finger the whole way; that tool is not chosen. A finger held still on it for 0.3 s picks it up too. While it is carried it keeps its shape and goes wherever the finger takes it, and nothing shows where it will land (EP104): no band or outline along an edge and no tick as it nears one; the finger picks it up and lets it go, and only then is its place chosen. Let go and it snaps with a short spring (a 0.2 s ease with Reduce Motion) to the edge nearest the finger, or to where a flick was heading (a finger that held it still before letting go never flicks it on, EP104), and along that edge it lands where it was carried to (straight in to the edge when it stays flat or upright, centred on the finger when it turns), kept whole on the screen. Across the top (the default, centred) or the bottom it lies flat; down the left or right it is a 56 pt column with the same tools in the same order, then the active tool's widths and colours stacked, the eraser's Partial and Whole as two buttons, and no lasso or laser hint (they need a row's width). When its tools are longer than the edge it scrolls. The Teacher copy panel slides over the palette like Slide Over, and on the pull tab's side the palette keeps clear of the tab, so the tab and the edge swipe (EP97) still work. The page pill moves up above a palette at the bottom. The edge and the place along it are kept with the other tool settings (`toolbarDock` and `toolbarAlong`, 0 to 1, in `toolState.v1`; settings stored before EP100 read as the top and before EP101 as centred), so every worksheet and the next launch open with the palette where it was left. Only a finger moves it: Apple Pencil never does, so a Pencil tap on the palette still picks a tool and Pencil writing on the page carries on while a finger moves it. A touch that lifts before it moves is a tap. When the palette is too long for its edge and scrolls, a drag along it scrolls it, and a drag across it (or after a hold) carries it. Every tool, its controls and its settings popover work on every edge, and a popover opens over the page beside the palette. Read-only hides the palette on every edge. VoiceOver offers Move tools to the top, bottom, left and right on the palette. Why EP100's row never moved on the iPad (EP101): a hold on a tool landed on a SwiftUI button, whose own touch recogniser began at once and, because a long press can be prevented by default, UIKit failed the hold within a millisecond, long before 0.3 s. The palette's recogniser now cannot be prevented, and when it begins it cancels the button's touch so the held tool is not tapped. The unit test could not catch this because it fed the drag's phases to the editor directly; `EmberPadUITests/ToolbarFingerDragUITests.swift` now drives real touches through UIKit (XCUITest press and drag, launched with the debug-only `-EmberPadUITestWorksheet` argument, which seeds a synthetic worksheet): it holds a tool and drags the palette to every edge, checks taps still pick tools, and reopens the worksheet to find the palette where it was left. It fails on the EP100 build and passes now. Why EP101's drag felt laggy and stepped (EP102): it was a 0.3 s long press, so nothing moved until the hold ended; it then hid the palette and drew a smaller raised copy centred on the finger, so the tool the finger held jumped away from under it; the copy flipped between a row and a column as the target edge changed, inside a spring animation; and every move rewrote state on the whole editor screen. Now the palette itself is moved by a render-only offset that only the palette reads, from a recogniser that begins after a few points of travel. `EmberPadUITests/ToolbarDragTrackingUITests.swift` measures it with real touches through the debug-only `ToolbarDragProbe`, which on every display frame compares where the held point of the palette is drawn with the finger. In the Simulator, a held drag on the EP101 build drew the held tool up to 129 pt from the finger (median 115 pt) and dropped frames (50 ms gaps), and a drag with no hold never moved it; now a drag with no hold picks it up within two frames, it is drawn a median 7 pt from the finger at 400 pt/s, which is exactly the one frame any drawing takes to show the finger's latest move, and never more than that one frame behind, with no dropped frames. `EmberPadUITests/ToolbarFreeDragUITests.swift` (EP104) carries it with real touches to the bottom and to the right side, and lets it go mid-page, near the left, and across from the left side to the right (where, held still before the lift, it lands as far down the side as it was carried, not flicked on by its last move), with the probe also comparing the window during the carry against the window at touch-down everywhere but round the palette: on the EP102 build the target edge's band changed about 4,500 square points of it and the tests fail; now nothing does. Let go mid-page, it flies to the nearest edge over about 20 frames, the largest step about 50 pt of a 370 pt flight, at rest in about half a second, where it was carried to along that edge. See the Simulator captures (synthetic worksheet): the [palette at the top](docs/screenshots/ep100/top.png), [carried over the right edge](docs/screenshots/ep100/lifted.png), floating on the [right](docs/screenshots/ep100/right.png), [bottom](docs/screenshots/ep100/bottom.png) and [left](docs/screenshots/ep100/left.png), the [eraser down the left](docs/screenshots/ep100/left-eraser.png), and the pen's settings from the [right](docs/screenshots/ep100/right-pen-settings.png), [bottom](docs/screenshots/ep100/bottom-pen-settings.png) and [left](docs/screenshots/ep100/left-pen-settings.png). The feel of the drag and the snap still need the device check.

**Straight lines (always straight, draw and hold).** The highlighter's "Always straight" switch is on by default, like GoodNotes' "Draw in Straight Line": a highlighter stroke drawn with the Pencil that already looks like a line (its ends at least 80% of its length apart, the pen's test) becomes a straight line from its first to its last point when the Pencil lifts, with no guide while it is drawn (EP71); a stroke that doubles back or scribbles over a word stays as drawn, and strokes brought back by undo or redo are left alone. The fountain pen's "Draw and hold: straight line" switch (on by default, like GoodNotes' pen Draw and Hold) snaps a held pen stroke the same way, but only when the stroke was already close to a line when the hold latched (its ends at least 80% of its length apart) and does not bow clearly to one side; a held curve, closed shape or arrow becomes that clean shape instead (EP116, below), a held letter or scribble stays as written, and a held closed loop round ink is still circle to lasso. As in GoodNotes (EP96), the moment a pen hold latches the stroke is drawn as that straight line, in the pen's own ink, colour, width and pen feel, with no guide; while the Pencil stays down the line's end follows it (led by the Pencil's predicted touches), its start stays put, and the lift commits exactly the line last drawn, with its end tip, as one undo step named "Straight Line". The line's end keeps up with the Pencil however long the line is (EP103). PencilKit redraws the whole line for every move and used to queue the moves it could not keep up with, so a long held line fell up to 2 s behind the Pencil and went on moving after it stopped; now the line's layer has one drawing in flight and only the newest waits. In the Simulator, with a 60 Hz synthetic Pencil and a screen recording, the end of a 520 pt held line lags the Pencil by a median of 0 ms and a p90 of 17 ms, against 367 ms and 900 ms before on a blank page (82 ms and 300 ms before on a 3000-stroke page). The line is drawn from its two ends, so moving it about costs the same however long the Pencil was held, and a held line is never taken for a scribble to erase, however its end was moved over writing (before EP96, moving a held line round and back over a 3000-stroke page erased 679 strokes on lift). Measured in the Simulator on a 3000-stroke page, EmberPad's own work per Pencil move after the hold went from a median of about 2.1 ms, with stalls of 89 to 236 ms, to about 1.2 ms with none over 17 ms (`HoldToLineTests`). See [the result](docs/screenshots/straight-lines-light.png). With the highlighter's "Draw and hold: straight line" switch on (the default; it is greyed while "Always straight" is on), holding the Pencil still (within 1 pt) for 0.5 s during a highlighter stroke marks it to snap; a dashed accent guide then shows the line, and further movement only moves its end. On lift, the marker stroke is replaced by a straight one from its first to its last point with the same ink and median width. A highlighter line within ±3° of horizontal is laid flat halfway between the heights of its ends (EP71, as GoodNotes); a held pen line within ±8° is laid flat at the height it began. The stroke and its snap are one undo step: one undo removes the straight line and redo restores it. Each page canvas carries a passive `HoldRecognizer` beside PencilKit's drawing recogniser that never recognises, cancels or delays touches, and the swap happens only after PencilKit commits the stroke and holds no other, at the first safe display frame (EP94), so ink is never held back or lost. The geometry is pure (`StrokeSnap`) and unit-tested; `HoldRecognizer` only reports holds; circle to lasso reuses it. First-stroke latency and undo on the actual iPad still need the device check.

**Draw and hold: shapes** (EP116, GoodNotes' Draw and Hold). With the pen's "Draw and hold" switch on, a pen stroke held still at its end (the same 0.5 s hold) becomes the clean shape it was drawn as, in the pen's own ink, colour and width: a closed stroke a triangle, a rectangle or square, a polygon of up to eight corners, or an ellipse or circle (the Shape tool's recogniser, `ShapeRecognizer`, with its level and square rules); an arrow drawn in one stroke an arrow; and a curve a smooth curve, one cubic Bézier from where it began to the Pencil, as GoodNotes draws parabolas and lines of best fit. A stroke close to a line is still the straight line above unless it bows clearly to one side (at least 10% of the distance between its ends) and a curve fits it at least twice as closely, so a long, wobbly or slightly bowed line stays a straight line, never a thin rectangle or a curve. A scribble, a word, a zigzag, a spiral or a nearly closed loop is no shape and stays as written, and a closed loop round ink with "Circle to lasso" on still selects that ink. The shape shows the moment the hold latches, and, as GoodNotes lets the scale and angle change before the lift, it follows the Pencil while it stays down: a closed shape scales and turns about its middle (a drift of under 4° or 3% is ignored, so a level square stays level), a curve or arrow about its far end, so its near end stays at the Pencil. The lift commits exactly the shape drawn as one ordinary fountain-pen stroke (a closed shape without end tips, so it is as wide where it closes as elsewhere), one undo step named for the shape ("Square", "Circle", "Curve" and so on), so the eraser, the lasso, export and the student view treat it as any other ink. Recognition is pure (`ShapeRecognizer.heldShape`), the shape while held is `HeldShape` (`LivePen.swift`), and `HoldToShapeTests` draws each shape with stand-in Pencil touches through real PencilKit. Recognition on a real hand needs the device check.

**Highlighter and eraser as in GoodNotes** (EP71). The page ink multiplies into the PDF page instead of covering it, on the iPad, in the flattened export, in page thumbnails and on the student display, so black print stays black under a highlight instead of turning olive. On white paper multiplying changes nothing, so pen ink there looks as before; pen ink drawn after a highlight still sits on top of it. The highlighter's three widths are 7.5, 8 and 19.6 page points (the middle, GoodNotes' 2.8 mm, is the default; the thick is its 6.9 mm). PencilKit draws a marker no thinner than 7.5 points, so the thin one is 7.5 and no width changes when the Pencil lifts (EP75). Its presets are GoodNotes' five (#FFFF82, #00FF00, #FFDEEB, #00FFFF, #FF00FF) at an alpha that shows yellow as GoodNotes' #FFFFC1 on white; saved settings map the old yellow, green and pink to the new yellow, green and pink, keep custom colours and the selected colour, and gain cyan and magenta. Saved width and eraser-size choices keep thin, middle or thick and small, medium or large. "Erase highlighter only" now removes highlighter ink in both eraser modes and leaves every pen stroke (before EP71 it erased nothing). The eraser defaults to Whole stroke for a new install; a saved choice is kept. The stored ink format is unchanged.

**Shapes** (EP64, after the highlighter, GoodNotes' slot) turns a Pencil stroke into a clean shape when the Pencil lifts: a line, an arrow (a shaft with a barb on each side, drawn in one stroke), a rectangle or square, a triangle, a polygon of up to eight corners, or an ellipse or circle. Lines, rectangles and ellipses within 8° of level or upright are set level or upright, and a rectangle or ellipse within 10% of equal sides becomes a square or circle. A stroke that is none of these (a scribble, a word, a curve) stays as drawn. Shapes take the pen's three widths and its colour presets, shown in the strip as for the pen, and are drawn as wide as the fountain pen's line. Tapping Shapes again opens its settings, as GoodNotes': **Snap to other shapes** (on by default) moves a new shape's corners and line ends onto another shape's corner or line end within 12 pt (a rectangle or square moves whole so it stays square), and **Fill colour** (off by default) tints closed shapes with their stroke colour at 20%. Both are kept in `toolState.v1`; settings saved by an earlier build read them as their defaults. Recognition is pure (`ShapeRecognizer.swift`) and runs in the same swap as draw and hold: the freehand stroke and its clean shape are one undo step named after the shape. Shapes are ordinary PencilKit strokes (`ShapeInk.swift`), so lasso, eraser, undo and redo, export, thumbnails, the student view and the ink backup treat them as other ink and the stored drawing format is unchanged: an outline is one stroke in PencilKit's plain pen ink, which no other tool writes, and a fill is one more stroke under it, a translucent disc of the same ink clipped to the shape by a stroke mask (the kind PencilKit's own eraser leaves), so a worksheet written on an earlier build opens as before and a build without the Shape tool shows shapes and fills as they look here. A lasso around a shape takes its fill with it, and recolouring keeps the fill translucent. Read-only mode blocks the Shape tool with the other tools. See each [freehand stroke beside its clean shape](docs/screenshots/ep64/freehand-beside-clean.png), the [shapes on a worksheet](docs/screenshots/ep64/clean-shapes.png), [fill on with a snapped line](docs/screenshots/ep64/fill-and-snap.png), the [settings](docs/screenshots/ep64/settings-popover.png) and the [student view](docs/screenshots/ep64/student-view.png), from a synthetic worksheet with strokes sent through the real page controller (Simulator cannot synthesise Pencil touches). Recognition on a real hand needs the device check.

**Eraser circle** (EP68, as GoodNotes shows it). While the eraser touches a page, a light grey see-through circle with a thin outline is centred on the Pencil tip and follows it, and it goes on lift. It is the area the eraser erases at the zoom on screen. The partial eraser's circle is the PencilKit tool's own width in screen points, because PencilKit erases the same on-screen width at every zoom: zooming in leaves the circle the same size and it covers less of the page. PencilKit's partial eraser takes only 16.4 to 80.4 points (iOS 26.5) and raises anything smaller to 16.4, so the old 8 and 16 pt sizes erased the same width. EP68 made the three sizes 16.4, 32 and 64 pt; EP71 makes them GoodNotes' 25 (small), 50 (medium, the default) and 80.4 pt (large: GoodNotes erases about 100, but 80.4 is PencilKit's maximum), so each size erases, and shows, its own width. Saved settings keep their small, medium or large choice. The whole-stroke eraser's circle is its chosen size too (EP99, below). On an iPad with Apple Pencil hover the same circle shows while the Pencil hovers over a page with the eraser chosen; elsewhere the hover recogniser never fires. Erase highlighter only and back to last tool work as before. On iOS 26.5 PencilKit itself draws a faint grey ring for the partial eraser, which the circle covers exactly. **Whole-stroke eraser sizes** (EP99, as GoodNotes). The whole-stroke eraser comes in the partial eraser's three sizes, 25, 50 and 80.4 points across on screen, chosen with the same size dots in the toolbar, and every stroke its circle touches goes, whole, as the Pencil passes over it. GoodNotes' eraser has one size whichever mode is chosen, so both modes share one size choice: a size picked in one mode is the other's too, and it is saved with the other tool settings (`eraserSizeIndex`, unchanged), so a saved small, medium or large keeps its meaning. Like the partial eraser it erases the same on-screen width at every zoom, so zooming in erases more finely. PencilKit's own whole-stroke (vector) eraser has no width (its `validWidthRange` is 0...0 on iOS 26.5 and every width asked for erases the same 3.5 page points either side of the tip), so the whole-stroke eraser is EmberPad's own (`WholeStrokeErase.swift`): while it is chosen PencilKit's drawing recogniser is off and a recogniser like the laser's takes the Pencil, so the Pencil neither inks nor scrolls the pages, and fingers still scroll and zoom. A stroke goes when its ink (its line plus half its width) comes within the circle anywhere along the Pencil's path; a stroke the partial eraser cut counts only where it still shows. Each eraser stroke is one undo step named "Erase". It changes a page only while PencilKit holds no uncommitted stroke (EP94): a pen stroke written just before the eraser was chosen is committed first and the sweep waits for it, so it is never thrown away. Erase highlighter only removes only highlighter strokes and leaves pen ink, and Back to last tool on lift switches back once the erase is done. The partial eraser, scribble to erase and the ink-edit gate are unchanged. See the Simulator captures mid-erase with the [small](docs/screenshots/ep99/whole-stroke-small.png) and [large](docs/screenshots/ep99/whole-stroke-large.png) whole-stroke eraser (synthetic worksheet).

**Fountain pen feel and tip sharpness.** The fountain pen aims at GoodNotes' Fountain Pen at Tip Sharpness maximum and Pressure Sensitivity minimum: a fine, even, pure-black line about 1.22 pt wide at the middle width (2.5), as GoodNotes draws 0.3 mm, the same width in every direction at Min (within 4%; a little thinner on up-right diagonals as pressure sensitivity rises), barely swelling with pressure, with ends that thin to sharp points over about 9 pt. The ink does not change when the Pencil lifts (EP56): only the end tip is added. PencilKit has no public hook into its own live stroke, so PencilKit still takes the Pencil (palm rejection, the commit, undo) in a clear monoline nobody sees, while `LivePen.swift` draws the stroke from the same coalesced and predicted Pencil samples (position, time, force, tilt) with the shape below, in a passive PencilKit layer of its own above the page's ink, drawn at the page's ink zoom. The start tip grows in while the stroke is written; predicted samples are drawn and dropped on lift. Once PencilKit has committed the stroke it is swapped for exactly the stroke drawn live plus its end tip, keeping its creation date. No swap, and no other change to the page's ink (draw and hold, a shape, scribble to erase, circle to lasso), lands while PencilKit holds a stroke it has not committed or the Pencil is down: setting the drawing then makes PencilKit throw that stroke away, and that was the bracket that vanished in class (EP94). The pen's swaps wait for half a second's pause in the writing (or until 32 are waiting) and land together on a display frame once the latest commit has settled (0.1 s, so a change cannot catch PencilKit still finishing a quick stroke, EP123), each as its own undo step. Meanwhile the live layer keeps drawing each waiting stroke, and the page saves it visible, so the file and the student view never show a gap. Since EP156 the page saves it as the live layer's own stroke, the very one that lands, as soon as the live pen has seen the lift (PencilKit's copy made visible only when the live pen has none for it), so the landing changes nothing the student view or the Mac shows; before, it resent the page's ink and the Mac redrew it all, a blink in the projector and the lesson recording half a second after each lift (`PenFeelMirrorTests`). If PencilKit throws a stroke away all the same, the live layer's copy goes on the page as its own undo step, never twice. On a slow run loop (a slow device, or a loaded CI runner) PencilKit can also group a burst's undo steps out of order, make a stroke's step only after the stroke has landed with its own (a late step that then takes back nothing, or only that stroke), leave a step that changes nothing for a stroke it threw away, or take a stroke it has committed back off the page, outside undo, as it commits the next one. The stroke taken back goes back on the page, every stroke still lands with the pen feel as its own undo step, and PencilKit's steps that change nothing or only repeat a landed stroke's own are dropped, so no stroke is lost and every tap of undo takes back one stroke (EP98). Before, a stroke taken back was lost and the strokes after it stayed in PencilKit's monoline: on the CI runner, 1 of 24 fast brackets. If a swap cannot apply (the page changed some other way), the clear stroke is given back the pen colour at full opacity, outside the undo stack. A clear stroke in a file saved by an earlier build is made visible when its page opens, so a written stroke is never left invisible. The student view's provisional line takes the pen colour and the shaped stroke's middle width. Each point's width is rebuilt from the pen width the stroke was drawn with, its force (smoothed; at Min pressure only reduces the change, within about 0.65 to 1.45 times), the stroke direction and the tip taper, and its nib is turned across the stroke, because PencilKit's committed fountain ink draws 2 × (size − 2) points across the nib and a quarter of that along it (measured in the Simulator). Position, timing, force, altitude, opacity, colour, transform and random seed stay as written. The ink is a new fountain-pen ink, never the committed one: PencilKit commits live fountain-pen strokes with an older ink (content version 2) whose seeded grain, at about 1 pt, breaks into a beaded grey fringe with about half the ink; the new ink draws the same points as one clean line at every zoom. The pen settings popover keeps its Tip sharpness slider: 0 to 100% in five ticks, default 100%, with the footer "Applied when the Pencil lifts." At 100% each end tapers over 9 pt at the middle width (3.6 pt per point of pen width), never more than half the stroke, to a quarter of the width; lower settings taper less, and 0% keeps blunt ends while still drawing the fine line. Strokes shorter than 3 pt at the middle width (dots, decimal points, charges, short arrowhead barbs) keep blunt ends. A pen stroke snapped straight by draw and hold takes the same pen feel in the same swap. Strokes already cut by the eraser, loops taken by circle to lasso and highlighter strokes are left alone. The stroke and its new shape are one undo step named "Ink": one undo removes the stroke and redo brings back the reshaped one. The pressure sensitivity setting (default Min) is read by the reshape but has no slider yet. Settings saved by an earlier build keep a tip sharpness the user chose; the old default (50%), saved before the choice was recorded, becomes 100%, so a 50% the user had picked by hand also moves to 100% once. While it is written the stroke already has its width, its thick-thin variation and its start tip; unit tests check that lift changes no ink away from the end tip. Strokes written on an earlier build keep the older ink. See a [worksheet at 0, 50 and 100%](docs/screenshots/pen-feel-tip-sharpness.png) (synthetic strokes committed through the real page controller in the Simulator). On the iPad Air 4 the ink no longer changes at lift and long strokes do not stutter. Each stroke stays in its own live layer from pen-down until the page has drawn it (EP103), so the lift no longer hides it for a moment while another layer catches up (before, it vanished for 70 to 80 ms on a fresh page), and what lands is pixel for pixel what that layer showed. The live layer is reshaped at most 60 times a second, not on every Pencil move (EP114): every drawing PencilKit is given stays in its replica record, which the main thread waits on while PencilKit saves it, so one drawing per move (about 120 a second) grew that record to megabytes and stalled the page for 100 to 300 ms after minutes of writing (`LivePenMakesFewDrawingsTests`). When a stroke lands, PencilKit redraws the page in 256 pt tiles, from the middle of the screen outwards, over up to a quarter of a second, and only then reports it; the stroke's layer is masked off each tile under it as soon as that tile has been redrawn, and hidden once all have been, so the stroke is no longer drawn twice, bolder, until the report (on a 3000-stroke page, 5 to 7 doubled frames before, 0 or 1 after). If an earlier redraw is still under way when the stroke lands, as for a held line landing at once on a busy page, the layer waits for the report as before (about 60 to 100 ms doubled). Measured in the Simulator with a 60 Hz synthetic Pencil and a screen recording, the ink tip stays about a frame behind the Pencil (median 16 to 17 ms, worst 19 to 39 ms, against up to 1.8 s before), and the longest main-thread gap while writing fell from 125 ms to 78 ms (`InkFollowsThePencilTests`). In the Simulator, a long slow stroke shows one or two screen freezes of 100 to 245 ms that the old monoline did not, with the main thread free and each live update about 5 ms (compositing between PencilKit's hidden live stroke and the live layer); watch for it on other iPads. The real Pencil force range needs the device check.

**Scribble to erase** (EP82, made more eager in EP90; GoodNotes' pen gesture; on by default, tap the pen twice, Pen gestures). Scribbling with the fountain pen over ink erases the strokes it goes through, and the scribble leaves no ink. GoodNotes asks for "a tight zigzag over the strokes" or "horizontal lines back and forth over the strokes"; both work, as do a loose zigzag of two or three peaks, a row of loops along the word and a quick scrub of three passes over one word. A stroke has a scribble's shape when it turns back on itself along one axis at least twice (three passes), the passes going back over the same ground. A circle, oval or loop drawn round ink does not (EP161). Closed and carried on a little past where it started, it too turns back twice along any axis, and before EP161 a loop drawn close round a handwritten expression or a graph, clipping a letter at its edge, erased everything it went round. A stroke whose every turn goes the same way, as a loop's do (a zigzag's and a scrub's alternate), and whose loops stay in one place (each loop and the next moving apart by less than 0.8 of a loop's width that way) is kept as ink; loops along a word turn one way too, but move along, and still scribble. A stroke on the page then goes, whole, pen, highlighter and shape ink alike, when the scribble crosses it (not only near one of its ends) and at least half of it is near the scribble's line and within its reach (a third, when four or more passes cross it, as for a tall h or l under a thin scrub). So does a stroke at least half inside the scribbled area (between one pass and the next), and a short stroke crossing one that goes (a t's bar, the second stroke of an x). A scribble only acts on ink: it must go through ink with at least three of its passes, or with two passes through two strokes. One over empty paper, beside ink, round it (a lasso loop), as shading inside a box, or written with the switch off stays as drawn. One letter can have a scribble's shape (m, n, u, w), but handwriting only touches other ink (a joined letter, a t's bar, a descender from the line above), which is too little, or too near the other stroke's end, to erase it. The synthetic fixtures (`ScribbleFixtures.swift`) hold the proof: 582 scribbles drawn at Pencil rate over words in print and joined up, at three sizes and speeds (EP82's rule erased 298 of them), each erase exactly their word and nothing on the lines above and below or beside it, and 179 cases of handwriting near ink and 3 scribbles over empty paper erase nothing, at any point while they are written. `ScribbleRoundInkTests` adds 2,916 loops drawn round handwriting, a handwritten expression, a sketched graph and a line of writing, from cutting the ink's edge to 8 pt clear of it, from one to three turns and spiralling in, either way round at a hand's writing speed: none erases or outlines anything while it is drawn (before EP161, 1,712 erased and 850 outlined something part way), and zigzags, scrubs and loops along the word over the same ink still erase it; one of them draws a loop round an expression with stand-in Pencil touches through PencilKit, which before EP161 erased all of it. **The preview** (EP90): while the scribble is drawn, as soon as it would erase anything, the ink it will erase is outlined with the toolbar lasso's own line (the same dashed accent line and faint fill, from the same code), round all of it. The outline follows the scribble as it grows, goes when the stroke stops being a scribble or is cancelled, and never shows for handwriting or over empty paper. When the Pencil lifts, exactly the outlined strokes are erased, and at the lift they leave the page at once with the scribble's own ink and the outline (EP108), though the erase lands a few frames later; a scribble whose commit never comes shows them again after a second. The outline holds steady through a brief wobble in the scribble's shape, and PencilKit's own finger selection (Select All, Insert Space) is turned off, since EmberPad has its own lasso. It is judged against the page's ink near the scribble only, so it keeps up at Pencil rate on a page of 1,500 strokes. **A long scribble keeps the screen moving** (EP140). Two things the main thread did for every Pencil move took longer the longer the scribble: the preview judged the whole stroke so far, and the live pen reshaped it from all its samples. Once that work outlasted the 4 ms between two Pencil moves, the run loop never slept, Core Animation never committed, and the screen froze until the Pencil lifted, then caught up in a burst. On the iPad Air in a Debug build (as Ember Slate is built), a three-second scribble froze the screen for all 2.9 s of it and a nine-second one for 11.2 s; the lift and the erase itself were quick (about 120 ms from the lift to the erased ink leaving the screen) and are unchanged. Now, while the scribble is drawn, the preview is judged off the main thread, one judgement at a time, each of the whole stroke so far, and the live pen keeps each move as it is and shapes the stroke off the main thread only for the moves it draws (`PageInkView.LivePenShape`). The longest frame in the same nine-second scribble is 45 ms. The lift still judges the whole scribble once, on the main thread, so what it erases is unchanged (`ScribbleKeepsUpTests`). See the EP90 frame strip from the iPad Simulator (synthetic worksheet): [scribble preview](docs/screenshots/ep90/scribble-preview.png). The erased strokes and the scribble go as one undo step, "Scribble to Erase": undo brings the ink back without the scribble, and redo erases it again. It runs once PencilKit has committed the stroke and holds no other, at the first safe display frame (EP94), and the scribble's ink is never on the page: PencilKit's copy is clear, and the live pen draws it until the page has drawn the erase, so the scribble and what it erases vanish together. A scribble that erases comes before draw and hold and circle to lasso, so the outline is kept even if the Pencil rests at its end; every other stroke snaps and lassos as before. The highlighter, the Shape tool and Apple's Scribble (handwriting to text) do not scribble to erase. The geometry is pure (`ScribbleErase.swift`; the page side is `ScribblePreview.swift`) and unit-tested; a test also drives a zigzag through PencilKit's own recogniser with stand-in Pencil touches. Recognition on a real hand needs the device check.

**Circle to lasso and the selection.** With the pen's "Circle to lasso" switch on (the default; tap the pen twice, Pen gestures), a pen stroke that ends closer to its start than 30% of its larger side (and at least 16 pt across), held still for 0.5 s at the end, selects the ink inside it. GoodNotes' form works too: lift the loop, then within 4 s long-press its line with the Pencil (0.5 s still, within 20 pt of the line); the press leaves no dot. A stroke is inside when at least half of the points sampled along it are, by the nonzero winding rule, so a loop drawn twice round or a figure of eight still holds its middle. The loop is not kept as ink and never returns on undo or redo; a held loop round nothing is the pen's draw and hold shape (a circle, say; EP116), or stays as drawn with draw and hold off. A "Circle to lasso · selected" toast shows, and the tool stays on the pen. The toolbar lasso selects the same way, by drawing round ink with the Pencil (the loop need not close). PencilKit has no public API to set a lasso selection or to give its own lasso resize and rotate handles, so both use EmberPad's own selection layer (`SelectionOverlay.swift`, geometry in `SelectionGeometry.swift`); PencilKit's drawing recogniser is off while the lasso tool is chosen. The selection works like GoodNotes': on lift only the dashed lasso shows, with no box, handles or menu. A tap inside the selection opens a one-line menu beside it, above or, when there is no room above, below: Cut (Copy then Delete), Copy (PencilKit drawing data plus a PNG on the pasteboard), Delete, Duplicate (a copy 20 pt down and right, then selected), Resize and Color (the current pen colour presets; a highlighter stroke keeps its ink type and transparency). GoodNotes' overflow items (Take Screenshot, Add Element, Convert) are not offered yet. Drag inside to move. Resize draws the box round the ink with a red × at the top left, which goes back to the lasso, and one round handle at the bottom right: one drag on it scales the ink (keeping proportions) and turns it about the top-left corner, snapping to quarter turns within 4°. Dragging inside still moves. Each move, Resize drag, Cut, Delete, Duplicate and Color is one undo step; a move or Resize is one `PKStroke.transform` change on the selected strokes. With EmberPad ink copied, a finger long-press on a page offers Paste: the ink is centred on the touch, kept on the page where it fits, selected, and is one undo step. The selection is dropped by new ink, undo or redo on its page, a tool change, its page scrolling away, or a Pencil touch or finger tap elsewhere; scrolling and zooming keep it. It sits above the pages in the teacher's view only and never reaches the student view, which sees each change when it is committed. See the [Resize box](docs/screenshots/circle-lasso-selection-light.png), and Simulator captures of the [lasso on lift](docs/screenshots/ep42/01-lift-shows-only-the-lasso.png), the [menu on a tap inside](docs/screenshots/ep42/02-tap-inside-opens-menu.png), [Resize](docs/screenshots/ep42/03-resize-mode-handle-and-x.png), a [Resize drag that scales and turns](docs/screenshots/ep42/04-resize-drag-scaled-and-turned.png), the [× back to the lasso](docs/screenshots/ep42/05-x-back-to-lasso.png), [Color](docs/screenshots/ep42/06-color-red.png), the [menu below a selection near the top](docs/screenshots/ep42/07-menu-below-near-top.png), a [lifted loop](docs/screenshots/ep36/04-loop-lifted.png) and the [Paste menu](docs/screenshots/ep36/06-long-press-paste-menu.png) (a test drives the gestures, since Simulator cannot synthesise Pencil touches). **A tap on the status bar leaves the page alone (EP157).** iPadOS scrolls a scroll view to its top when the status bar is tapped, and PDFKit's has that on by default, so a finger or Pencil brushing the clock sent the worksheet (or the Teacher copy's answers) back to page 1 mid-lesson. Both PDF views now turn it off (`scrollsToTop = false`); `StatusBarTapUITests` taps the status bar after scrolling down and checks the page is unchanged.

**Teach (EP153).** Lasso part of a question with the toolbar lasso and tap inside: Teach puts it on a new page of the A3 squared paper (portrait, white, as Add Page's first choice) straight after the page in view, and turns to that page with the pen in hand, its top just below the floating palette so the question shows at once, and the working goes underneath. The lasso selects the worksheet's printed content as GoodNotes' does: a loop round print with no ink inside it selects that area (the dashed lasso only; it does not move) and its menu is Teach alone, and a loop round ink and print adds Teach after Color, taking the place of GoodNotes' Take Screenshot. A loop round blank paper still selects nothing, and a pen loop (Circle to lasso) still needs ink inside it, so circling a printed word with the pen stays the pen's circle. The question lands at the top left, with the loop's top left on the second grid line in from each edge (about 10 mm), at its own size, since a point is the same size on A4 and A3; only a question wider (or taller) than the page inside that margin is scaled down, in proportion, to fit. Only what is inside the loop shows, on white, over the grid. It is not a screenshot: the page's `pages.json` entry keeps which page of `original.pdf` it shows, the loop and where it goes (`PageExcerpt`), and the page is drawn from the PDF as vectors (`TeachPage.swift`) each time the worksheet opens, so the question is as sharp as the worksheet at any zoom, on the projector and in exports, and Search finds its text (only where it shows). The picture is copied into the app's container at `Application Support/Backdrop/Projector Backdrop.jpg` (`StudentBackdropStore`): a JPEG no more than 3840 pixels across as it is, anything else as an upright JPEG scaled to at most that. The folder is outside the Files-visible Documents folder and is marked as excluded from iCloud and computer backups, and the picture is never sent to the Mac (it is no part of `PresentedView`), synced or put in the ink backup; no backdrop picture is kept in this repository or bundled in the app. `StudentBackdropModel` reads it off the main thread when a projector's scene connects or the choice changes, decoded for that display (at least 1920 and at most 3840 pixels on the longer side), hands the decoded picture to `StudentDisplayModel.backdrop` and lets it go when the projector disconnects, so the scene never reads the file and a worksheet page has no backdrop view behind it at all: writing costs nothing extra. With no picture, or one that cannot be read (an alert in the library then says so), the screens are exactly as before. `StudentBackdropTests` (EmberPadTests, synthetic pictures only) cover a missing, present, oversized, turned and corrupt picture, a refused pick keeping the old one, removing it, the read on connect and the release on disconnect, that the idle screen is the picture alone and Paused adds only the small label, that pages and the Teacher copy placeholder never show it, that the plain screens are pixel for pixel as before, and that what Present on Mac sends is unchanged.

**Laser pointer (Dot and Trail).** The laser pointer, which sits after Image on the toolbar strip, shows a red dot under the Pencil on the iPad and at the same page point on the student view, in both framings. It is never ink: while it is chosen PencilKit's drawing recogniser is off on every page and a Pencil-only `LaserPointerRecognizer` on the PDF view takes the Pencil, so nothing is written and the pages do not scroll under it; fingers still scroll and zoom. Lift and the dot goes. On the iPad the dot keeps the same size at every zoom; on the student view it is sized from the shown area so it stays visible on a projector. Off the pages the iPad dot still follows the Pencil and the student view shows none. The student view's dot is held in `StudentLaserPointer`, built only through `StudentSafeDocument` like live ink, so a Teacher copy's dot stays on the iPad. Tap the laser again for its settings: Dot (the default) or Trail, kept in `toolState.v1` with the other tool settings. See the [iPad worksheet](docs/screenshots/laser-ipad-worksheet.png), the student view in [presenter](docs/screenshots/laser-student-presenter-page.png) and [full-page](docs/screenshots/laser-student-full-page.png) framing, [after lift](docs/screenshots/laser-student-after-lift.png), a [Teacher copy](docs/screenshots/laser-student-teacher-copy.png), the [strip](docs/screenshots/toolbar-strip-laser-light.png) and the [settings](docs/screenshots/tool-settings-laser-light.png). The student captures host the real `StudentDisplayView` at 1920 × 1080 in the test app, and the dot enters through the controller's laser events because Simulator cannot synthesise Pencil touches. In **Trail** mode the dot also leaves a red glowing line, a red core over a wider faint glow, on the iPad and at the same page points on the student view. Each point fades out over 1 s after it is drawn, so the line shortens behind the Pencil, and a second after lift nothing is left; putting the laser away or leaving the worksheet clears it at once. The trail is pure (`LaserTrail`), drawn by `LaserTrailLayer` in ten opacity steps of two shape layers each, so moving or fading it only replaces paths and never re-rasterises the page. A lift or leaving the page breaks the line, and the student view's trail never joins two pages. The student trail is held in `StudentLaserTrail`, gated through `StudentSafeDocument` like the dot, so a Teacher copy's trail stays on the iPad. Trail mode only changes what is drawn: it never inks and never adds an undo step. See the Trail on the [iPad worksheet](docs/screenshots/laser-trail-ipad-worksheet.png), the student view in [presenter](docs/screenshots/laser-trail-student-presenter-page.png) and [full-page](docs/screenshots/laser-trail-student-full-page.png) framing, half a second after lift on the [iPad](docs/screenshots/laser-trail-ipad-fading.png) and the [student view](docs/screenshots/laser-trail-student-fading.png), the student view [after the fade](docs/screenshots/laser-trail-student-after-fade.png) and the [settings with Trail chosen](docs/screenshots/tool-settings-laser-trail-light.png); a test holds and steps both clocks so the captures show a set fade. Pointing feel and the trail's fade on a projector need the device check.

Debug builds expose **Device checks** in the library's Debug section, with pass/fail results for the scene, log, PDF and Pencil checks. The probe appends scene and capture snapshots to `Documents/device-checks.log`, provides a runtime-generated synthetic writing-trial PDF, and can replace the external student scene with a solid-colour, role-labelled test pattern. Its scribble recorder accepts Pencil or touch input, labels each saved drawing `erase` or `keep`, and exports the collected stroke samples as versioned JSON through Files. Samples are held in recorder state and are not persisted unless exported; they are not added to the device-check log or uploaded. Its **Pen feel probe** takes Pencil input only: write one line with the fountain pen at each of the three widths, saving each, then export `pen-feel-probe.json` (`ember.pen-feel-probe/v1`) through Files. It records each point's PencilKit size, force, azimuth, altitude and time offset with the line's tool width, for calibrating the pen feel; it is held the same way and never uploaded. Scribble exports now carry each point's size too; older exports without it still load. These controls are compiled out of Release builds.

The student view's page snapshot can only be built through `StudentSafeDocument`, whose failable initializer accepts only a Student-role record, from a session that supplies that record's own pages and drawings, in both framings. Live strokes are held in `StudentLiveInk`, which is built the same way and is drawn only over the same session's published page, so a Teacher copy never shows live ink. A Teacher copy opened as the main page therefore shows **Teacher copy · private** on the student view, never its pages. The one way a Teacher copy's pages reach the student view is the teacher's own swap while presenting (EP130, below), which shows the class the Teacher copy paired with the open Student worksheet. Private content is hidden while another screen is attached to the iPad without the student view on it (AirPlay or HDMI mirroring, or an extended display; `UIScreen.screens`, re-read when the capture trait or a scene changes), and whenever inactive. Private content is also hidden from the moment the screen is captured until the screen list settles (about 1 s), since a mirrored screen may not be listed yet. Once settled, the iPad's own Screen Recording attaches no screen, so the answers show again for the teacher's recording, and the app shows no capture message, since iPadOS shows its own recording indicator (EP54). A Mac recording over QuickTime or a ReplayKit broadcast is also treated as recording. When hidden, a Teacher copy's pages and the private-answer pane then leave the view hierarchy and draw no pixels, rather than being blurred or covered. The editor assigns the paired Teacher copy's URL as the private answer only for the teacher's main scene, and clears it when the editor disappears. AirPlay/HDMI, QuickTime, recording and capture-trait behavior must be checked with the teacher. Leaving the app can restore system mirroring; stay in EmberPad while sharing. There are no private UIKit capture-hiding tricks or iOS 27 APIs.

The Teacher copy appears as a Slide Over style panel over the worksheet (`Apps/EmberPad/TeacherCopyCard.swift`), only in the iPad's main scene: the external student scene draws from `StudentPageSnapshot`, which has no answer URL. ### Present on Mac (EP93)

Present on Mac shows the student view on the Mac over the pairing's direct wireless link, for a Mac driving a projector over HDMI, with no Wi-Fi network and no cable. It sends what the student view shows, not video: the page's paper once, then ink, page turns, scroll and zoom, the stroke being written and the laser, and the Mac draws them. It reuses the pairing, the TLS-PSK channel and the sync server; there is no new pairing step.

**On the iPad.** In a worksheet, the Sharing menu (the AirPlay icon in the header, and the More menu) has a **Present on Mac** switch, with a status row under it and a footer "Shows the student view on your Mac over a direct wireless link. No Wi-Fi network needed." A small light on the AirPlay icon shows the state: green when presenting, amber while connecting or reconnecting, none when off. Nothing connects and nothing is sent until the switch is on, and turning it off stops at once and stops retrying. Without a pairing the row says "Pair this iPad with your Mac first" and nothing connects. An older Companion gets "Update Ember Companion on your Mac to present", Present turns itself off, and sync is unaffected.

**What is sent.** Everything comes from the same Student-only model the external student scene draws (`StudentDisplayModel`, built only through `StudentSafeDocument`), as `PresentedView` values plus that page's paper and ink; the Teacher copy goes only when the teacher swaps the class onto it (EP130, below). A Teacher copy opened as the main page sends only **Teacher copy · private**: no page, paper, ink, live stroke or laser. The library sends only the idle screen (the Ember star alone), and an inactive iPad sends **Paused**. No title, answer URL, toolbar, popover or library name is ever encoded. `PresentControllerTests` encode a Teacher copy with ink, a live stroke and the laser and check that its ink and any PDF are absent from the bytes, which are under 300.

**Messages.** `PresentEncoder` compares what the iPad shows with what the Mac holds and sends only the difference. A paper goes once per page, as a one-page PDF of that page (a JPEG at most 2,400 px on its long side if the page's PDF is over 6 MB), named by its SHA-256 so the Mac never needs it twice. A page's ink goes whole once, then as only its new strokes on top of the revision the Mac holds; an erase or anything else that is not an append resends the page's drawing. The stroke being written goes as its new points only, with its predicted tail replaced each frame; the encoder remembers how many of its points the Mac holds and reads only the ones after them, so a frame costs the iPad's main thread the same however long the stroke has grown (EP142, `PresentLiveStrokeTests`). Every update carries a sequence number. On every (re)connect the iPad sends a snapshot (everything the Mac does not hold, which after a reconnect is usually not the paper), then deltas; an update the Mac cannot apply in order, or an append on top of a revision it does not hold, gets a resnapshot request instead. An idle link sends a 65-byte heartbeat each second and the Mac acknowledges each one. The iPad builds updates on a `CADisplayLink` at 30 to 60 Hz and encodes and sends them on its own queue, never on the main thread; while 256 KiB are still waiting to leave it skips frames, and the next update carries everything that changed, so a weak link coalesces rather than loses.

**Reconnect.** The iPad reconnects by itself while the switch is on: a link silent for 3 seconds is dropped (the Mac's replies and each 64 KiB chunk the transport accepts count as life, so a large first snapshot over a weak signal is not cut off), and it tries again after 0.25, 0.5, 1, 2 and then every 3 seconds. Even attempts dial the paired Mac's Bonjour service directly and odd ones browse for it, both with peer-to-peer Wi-Fi on (`includePeerToPeer`). The Mac shows an amber light and keeps the last picture up while it waits; the new link's snapshot brings anything written meanwhile, so no ink is lost. Measured in process, the picture was back about 0.3 s after a dropped link. The Mac closes a present connection it has not heard from for 6 seconds, and a newer present connection replaces an older one.

**Lock and background.** When the iPad locks or EmberPad goes to the background, the student view turns to **Paused** (as for HDMI), the iPad sends that, and closes the link about 0.8 s later. Network.framework connections do not survive suspension, so Present does not try to keep one. The Mac shows **Paused** with an amber light until the iPad comes back. On return the iPad reconnects straight away (the light goes amber, then green) and the new snapshot brings the page and any ink written meanwhile. Present stays switched on across a lock.

**On the Mac.** The Companion's menu window has a **Present on Mac** section with the status, a **Show on** picker (Automatic picks the projector, the first display that is not the built-in one, else the main display) and, after the teacher left the presentation, **Show presentation**. When the iPad starts presenting, the Companion opens its presentation window on that display by itself: covering an external display while the Mac has another display, or a full-screen-capable "EmberPad Presentation" window on the built-in display or on an external display that is the Mac's only one (so the Mac never loses its menu bar). Since EP135 it covers the external display the way Keynote or a full-screen browser does: in native full screen, in a Space of its own on that display, so the trackpad's three-finger swipe between full-screen apps moves the projector to the next Space or desktop and swiping back returns to the presentation, still live. Swiping away is not leaving: the presentation, the iPad's Present and a lesson recording carry on. Entering full screen makes the Companion the active app, as any full-screen app is while its Space is shown. When the Mac's displays share one Space (Displays have separate Spaces off in Desktop & Dock), full screen on the projector would blank the Mac's own display too, so the window is then the borderless panel used before EP135, above the menu bar and Dock on every Space, and cannot be swiped away. It shows the page aspect-fit on black with no chrome, the paper from its PDF, the ink from the sent PencilKit drawings, the live stroke and the laser dot and trail, and a small light in the corner: green when presenting, amber while reconnecting. While shown, it keeps the display awake. When the iPad stops presenting the window closes.

**Smooth motion (EP141).** Updates arrive over the air late and in bunches, so the Mac does not draw each one as it lands. Each update carries the time the iPad took it (`PresentUpdate.time`), and the Mac plays the scroll and zoom back on that clock (`PresentPlayback` in `PresentMotion.swift`), interpolating between frames on a display link, about 100 ms behind the quickest delivery it has seen: a delayed copy of the iPad's motion rather than a stuttering one. When frames come later than that (a Wi-Fi stall), the picture waits where it is and carries on from there instead of jumping, adding at most 250 ms more, which it makes up at 5% of real time and drops once the page is still. Ink, the stroke being written, the laser and page turns, and any cut (another worksheet, Paused, the library, a page with nothing in common) are shown at once, as before. Measured over TLS-PSK on loopback from the Simulator's real scroll, the projector steps now vary by 15% at 60 Hz (106% drawn on arrival, standing still on half of the refreshes) and run about 101 ms behind the iPad. An older iPad that sends no times is played back on the times its updates arrive. `PresentMotionTests` (EmberSyncKit) and `PresentSmoothScrollTests` (EmberPadCompanionTests) fail on uneven steps.

**Sharp ink after the lift (EP156).** The stroke being written is a vector path, sharp at any zoom; committed ink is a bitmap per appended set of strokes. That bitmap was drawn at the paper's scale, about one bitmap pixel per screen pixel on a 1080p projector and in the lesson recording (coarser still zoomed in past the paper's 4,096 px cap), and the GPU's resampling at a fractional pixel offset doubled its edge: every stroke went soft the moment the Pencil lifted. Committed ink is now drawn at twice the page's shown scale (rounded up to a power of two), each bitmap capped on its own at 4,096 px on its longest side and 16 megapixels, falling back towards the paper's scale at that cap, never below it. The paper is unchanged. Once a page holds more than 24 such bitmaps, all its ink is drawn again together. That merge used to be one bitmap at the paper's scale, so every older stroke went soft again about every 24 strokes. It is now cut into tiles where the page has ink, each at most 4,096 px a side, at up to twice the page's scale. Each page's sharper ink is kept within 48 megapixels, of which the merged tiles leave 8 for strokes written since: an A4 page full of ink merges at about 8.9 px per point. All the pages the Companion holds at once, in the projector window and the lesson recording together, are kept within 96 megapixels (384 MB). A page beyond either budget is drawn at its paper's scale, as before. The tiles take about four times the pixels of the old merge, so they are cut and drawn off the main thread: until they land, about an eighth of a second later, the page keeps its own bitmaps and nothing on it changes. The main thread does no more than before: 29 ms against 29 ms for a page of 300 strokes shown afresh, and while writing on such a page the worst frame drops from about 28 ms (the old merge) to about 12. Drawn on the GPU as the recorder draws it, at the recording's 4.9 px per point, a committed edge (10 to 90%) is now about 1.15 px against the live stroke's 1.33, where it was 2.1, and merged ink measures the same. `PresentInkSharpnessTests` (EmberPadCompanionTests) check it at 4.9 and 6.5 px per point, after a merge, and within both budgets.

**Leaving the presentation on the Mac (EP127).** As in macOS presentation apps, the teacher can leave it from the Mac at any time, whichever app is in front:

- **Esc**, **Command-W** or **Command-period**. The projector window takes the keyboard when it opens, so these keys reach it at once: in full screen because the Companion is then the active app, and as the panel (displays sharing one Space) without making the Companion active, the Companion being a menu-bar app that is never in front by itself; after the teacher has typed in another app, a click on the presentation gives it the keyboard back, and the panel does so without switching apps. Before EP127 the projector window ignored them unless the Companion had first been made active by clicking the projector, and Command-W never worked. Command-Q still quits the Companion, as in any app.
- The **Exit presentation** control, a dark pill in the top-left corner that fades in when the pointer moves over the presentation, even with another app in front, and fades out once the pointer rests for 2.5 seconds; one click exits. The class sees it only while the pointer moves on the projector.
- **Exit presentation** at the top of the Companion's menu-bar window, beside where the presentation is shown, while it is up.
- The window's Close button on the Mac's own display, or in the title bar that full screen shows when the pointer reaches the top of the projector. A window in native full screen leaves full screen before it hides, so no empty Space is left behind.
- Leaving native full screen the system's own way (the title bar's green button, or Control-Command-F). It ends the presentation as Esc does, as Keynote ends play, rather than leaving a windowed presentation on the projector; it does not re-enter full screen.

Leaving hides only the Mac's window, as the menu's Hide did before: the iPad is not told and keeps presenting (Present on Mac is the iPad's own switch, and a dropped link would only reconnect). **Show presentation** brings the window back, and the next Present from the iPad shows it again by itself. `PresentExitTests` (EmberPadCompanionTests) cover each key, the Exit control appearing, fading and exiting, the close button, which display is covered and how (full screen, or the panel when the displays share one Space), that showing again never pulls a full-screen presentation back from another Space, that leaving from full screen leaves it first (also mid-transition), that leaving full screen the system's way ends the presentation, that a Space change or another app taking the keyboard does not leave, and that leaving hides only the Mac and the next Present shows it again. Under unit tests the controller reports full screen entered or left at once instead of making a Space. A Debug Companion launched with `-EmberPresentFake YES` presents a synthetic worksheet with no iPad and no pairing (`CompanionPresentFake`; `-EmberPresentFakeStopAfter N` stops and presents again), which is how leaving was checked against other apps in front. Native full screen and the three-finger swipe were not exercised on the development Mac: CI cannot drive the gesture or Spaces.

**Projector backdrop (EP131).** The Present section of the Companion's menu-bar window has a **Backdrop** row: **Choose picture…** (or **Change…**) makes any picture on the Mac the backdrop, and **Remove** goes back to the Ember star alone. With a backdrop, the presentation's idle screen (no worksheet presented, as while the teacher is in the library choosing the next one) shows the picture alone, full-bleed and aspect-fill, with no Ember star, and the Paused screen shows it with a small, quiet "Paused" in the bottom-left corner on a dark rounded badge, so it reads on any picture and stays clear of the Exit control (top left) and the status light (bottom right). The Teacher copy screen and worksheet pages never show it. The chosen picture is copied to `~/Library/Application Support/EmberPad/Projector Backdrop.jpg` (a JPEG as it is; any other picture is saved as a JPEG), read off the main thread when the Companion starts or the choice changes, decoded at most at the largest display's resolution (at least 3840 pixels across) and kept, so presenting never waits on the file. It stays on that Mac: it is never sent to the iPad, synced, backed up or put in a lesson recording (the recording draws its own canvas, which never has a backdrop), and no backdrop picture is kept in this repository. With no file, or one that cannot be read (the row then says so), the screens are exactly as before: the star alone on black, and the large "Paused". The iPad's own external student scene (HDMI or AirPlay) has a backdrop of its own, chosen on the iPad (EP145, below); neither device sends its picture to the other. `PresentBackdropTests` (EmberPadCompanionTests, synthetic pictures only) cover a missing, present, oversized and corrupt backdrop, a refused choice keeping the old one, clearing, falling back to the star, that the idle screen is the picture alone and that Paused puts only the small label in the bottom-left corner. In a Debug Companion, `-EmberPresentBackdrop <path>` uses that file instead of the one in Application Support, and `-EmberPresentFakeScreen idle` or `paused` makes `-EmberPresentFake` present that screen instead of the worksheet.

**Data.** Measured over TLS-PSK on loopback against the real `SyncServer` (`presentOverTheRealServerMeasuresBytesPerSecond`), payload bytes: idle, about 99 B/s up and 110 B/s down; writing without a break (120 Pencil samples a second sent at 60 Hz, a stroke committed every 1.5 s), about 8.2 to 8.3 kB/s up and 220 B/s down. The one-time paper for a synthetic worksheet page was about 11.5 kB. Apple's mirroring streams video of the whole screen, typically megabits per second.

**Tests and captures.** `PresentTests` in EmberSyncKit cover the round-trip of every message, Teacher copy and library content, delta sequencing and the gap resnapshot, appends that do not fit, live points, an older Companion reporting unsupported while sync still works, and a dropped link catching up with no lost strokes over an in-process loopback. `PresentEndToEndTests` (skipped unless `EP93_E2E_DIR` is set) drive the real editor in the Simulator over real TLS-PSK on loopback to a Mac-side host running the real `SyncServer`, `PresentHost` and the Companion's presentation canvas. See the [worksheet on the iPad](docs/screenshots/ep93/worksheet-ipad.png) and [on the Mac](docs/screenshots/ep93/worksheet-mac.png) (the live stroke and laser are fed in at the student model, because Simulator cannot synthesise Pencil touches), the Mac with the [Teacher copy open](docs/screenshots/ep93/teacher-copy-mac.png), [while the iPad is locked](docs/screenshots/ep93/paused-reconnecting-mac.png) and [after it came back, caught up with a stroke written meanwhile](docs/screenshots/ep93/caught-up-mac.png), and the [Present control](docs/screenshots/ep93/present-control-ipad.png). Range, a walking iPad and the projector need the device check.

### Showing the Teacher copy to the class (EP130)

While presenting (Present on Mac on, or a projector showing the student view), a Student worksheet with a paired Teacher copy has a swap control in its header, before the Sharing icon: **Class sees: Student** (**Student** in portrait). A tap shows the class the Teacher copy and the control turns the private colour and reads **Class sees: Teacher**; another tap goes back. GoodNotes' Presentation Mode has no comparable control (it only picks Mirror Presenter Page, Mirror Full Page or Mirror Entire Screen), so this follows Keynote's presenter display, whose switch-displays button (X while playing) swaps what the audience sees, applied to the two copies of one paper: the iPad keeps the worksheet, its tools and its ink, and only the class's picture changes. While the class sees the Teacher copy, the panel's header reads **Shown to the class** (an eye instead of the lock) and a projector's share pill reads **Students see: Teacher copy**.

The class sees the Teacher copy page that answers the Student page in view (its PDF page, so pages added in Ember Slate have none), placed and zoomed exactly as the Student page is when the two papers' pages are the same size, and whole otherwise or under Mirror Full Page. A page added in Ember Slate has no answer page, so the class keeps seeing the Student page there and the control reads **Class sees: Student** (a tap there ends the swap); the choice stays on, so the control and the share pill read Teacher again when the teacher turns to a page that has one. The control and the pill always say what the class actually sees. The Teacher copy shows no ink, live stroke or laser: those were written on the Student copy, so they stay off the answers and come back with the Student page.

Every presentation starts on the Student copy, as before EP130: turning Present on Mac on or off, a projector joining or leaving, opening or leaving a worksheet, and losing the paired copy all put the class back on it. The Teacher copy's pages reach the student view only through `TeacherCopyReveal`, which only `PresentationState.setClassCopy` makes, from the copy paired with the open Student worksheet (`TeacherCopyFrame`, in `Presentation.swift`).

**When the two copies' pages differ (EP158).** An Ember Teacher copy keeps every question word for word but swaps the blank answer space for worked answers, and an answer key may have a cover page, longer answers that run on to a page of their own, two answers to a page, or a data booklet at the end; page numbers then name different questions. So the class sees the Teacher copy page the teacher's own view of it shows: the swap opens the private Teacher copy panel (or turns it, if it is open) on the page holding the question at the top of the Student page in view, and from then on the class follows the panel as the teacher scrolls it, through every one of its pages, however many more it has than the worksheet (before EP158 the class followed the Student page's number, so a 9-page Teacher copy of a 6-page worksheet could never show its last three pages, and past the end of a shorter one the class saw the Student page). Turning the worksheet's pages meanwhile moves only the worksheet. Swapped back, the worksheet turns to the Student page whose question the teacher ended on in the Teacher copy (on a page an answer carries on to, that question); when nothing matches (an answer key's cover, a scanned copy) or the matched page is no longer in the worksheet, it goes back exactly to where it was when the swap began. The Teacher page is placed and zoomed as the Student page only when it is that page's own page number and size; a page matched elsewhere is shown whole.

The match (`TeacherCopyPageMatch`, `Apps/EmberPad/TeacherCopyPageMatch.swift`) reads each page's text (`PDFPage.string`), takes the first three lines of each Student page, drops lines that repeat on most of its pages (a running header or footer), cuts them into three-word pieces, and picks the Teacher page holding the most of them (at least two, and 30% of them), leaving out pieces found on most Teacher pages. A Student page with no text of its own (only answer space) follows the page before it. It is made off the main thread the first time a pair opens and kept in the app's caches under both PDFs' SHA-256 (`TeacherCopyPageMatches`), so a changed copy is matched again. A scanned (image-only) copy has no text and matches nothing: the panel then keeps the page-number rule above, and the swap opens where the panel was last left, else on the page of the same number, held to the Teacher copy's pages. `TeacherCopyAnswerPage` holds both rules, so the panel and the swap always agree. The swap and its way back go through `PresentationState.setClassCopy`, `TeacherCopyLanding` (what the panel turns to) and `ClassSwapWorksheet` (the editor, which turns the worksheet back); the panel reports the page showing the most of itself (`RememberingPDFView.shownPage`, the last page at the very end) to `StudentDisplayModel.showTeacherPage`. Not done yet: a "this page matches" correction for a pair the words cannot match, reading scanned copies (OCR), and landing on the question's exact line rather than its page's top.

**On the Mac.** The Teacher copy goes as ordinary paper under its own session, so the Mac drops the worksheet's ink rather than drawing it over the answers, and it needs no Companion change. Every presented page now says whose it is: `PresentedView.Page.role` is `student` or `teacher`, always written, and `PresentedView.showsTeacherCopy` is true for a Teacher copy page, so anything that keeps or passes frames on can hold the Teacher copy back; the lesson recording (EP129, below) holds every such page. A page from an iPad before EP130 has no role and reads as `student`, which is all it could show.

**Tests.** `PresentTests` (EmberSyncKit) cover the role on the wire and an older page without one, and a swap to the Teacher copy and back keeping the worksheet's ink off the answers. `ClassCopySwapTests` cover the swap on the same page and zoom and back, straddled pages, an added page (and the control reading Student there), every reset to the Student copy, live ink and the laser staying off the Teacher copy, Present sending it as paper only and marked as the teacher's, and the panel's width and grip. `PresentTeacherCopyUITests` drive the swap control and the grip in the Simulator; `-EmberPadUITestPresenting` (Debug only) stands in for Present on Mac being on, since the Simulator has no Mac to present to. EP158: `TeacherCopyPageMatchTests` match synthetic pairs with a cover page, answers carried on to pages of their own, two answers to a page, an appendix, a scanned copy and a page of only answer space, both ways, and keep a match per pair of hashes; `ClassCopySwapTests` swap a 6-page worksheet with a 9-page Teacher copy on every question, scroll the class to the ninth page and swap back to the matching question, or to where the worksheet was. `TeacherCopyMatchUITests` do the same in the Simulator with `-EmberPadUITestAnswerKey` (Debug only), which gives the UI test worksheet that 9-page Teacher copy.

### Freezing the class view (EP152)

While presenting (Present on Mac on, or a projector showing the student view), the teacher can freeze what the class sees: the projector, the Mac and the lesson recording keep the picture they show, while the teacher scrolls, turns pages, opens another worksheet or a Teacher copy, writes or opens menus on the iPad. GoodNotes' Presentation Mode has no freeze, so this follows a projector remote's Freeze button and Zoom's Pause Share: the audience stays on the last frame, and the presenter's own screen says the share is paused and resumes in one tap.

**On the iPad.** The worksheet header has a **Freeze** button (a snowflake) between the class-copy swap control and the Sharing icon, shown only while presenting; one tap freezes, and the button stays highlighted. The Sharing menus (the AirPlay icon and More) have a **Freeze class view** switch with the footer "The class keeps seeing this picture while you move around. Unfreeze to show them your iPad again." While frozen, every screen of the iPad shows a blue **Frozen · Tap to unfreeze** badge in the bottom-left corner, beside the REC badge when the Mac records; one tap on it, on the header button or on the switch unfreezes. Like REC, it is drawn in the iPad's main scene only, never on the student view or the Mac's picture. See the [header button](docs/screenshots/ep152/ipad-freeze-control-off.png) ([frozen](docs/screenshots/ep152/ipad-freeze-control-on.png)), the [Sharing menu switch](docs/screenshots/ep152/ipad-freeze-row-on.png) and the [Frozen badge beside REC](docs/screenshots/ep152/ipad-frozen-badge.png).

**What the class sees.** Freezing takes the student view's whole picture at that moment (`StudentPicture`, in `Presentation.swift`: the page, its ink, a stroke in progress, the laser and its trail, the framing, a Teacher copy the teacher was showing, and the open document's name for the lesson's record). The external student scene draws it and Present on Mac sends it until the unfreeze, while the student model itself keeps following the iPad. So nothing the teacher does while frozen reaches the projector or the Mac: Present sends only its one-a-second heartbeats, and Start lesson and End lesson, which still work. On unfreeze the class sees the iPad as it is then, at once: the iPad sends one whole snapshot (without the paper the Mac already holds), which the Mac shows as a cut, so it never replays the hidden changes or moves through anything between the frozen frame and the new one (EP141's smooth playback starts afresh from it).

**Lesson recording.** The recording follows the projector, as it always has: it draws the same frames the Mac is sent, so while frozen it records the frozen picture, and the lesson's record names the worksheet the class sees, not the one open on the iPad. A frozen Student page goes on being recorded while the iPad shows another worksheet or a Teacher copy.

**Teacher copy.** The rules of EP130 are unchanged. A frozen picture holds only what the class was already shown, built through the same Student-only gates, so it never newly exposes a Teacher copy: a Teacher copy opened while frozen sends no page, paper or ink, and once unfrozen the class sees **Teacher copy · private** as for any opened Teacher copy. Swapping the class onto the Teacher copy while frozen keeps the frozen Student page until the unfreeze (the swap control then reads **Class sees: Student**, because that is what the class sees), and the unfreeze shows the Teacher copy exactly as the swap does. A Teacher copy the teacher was showing when they froze stays frozen on the projector until the unfreeze, and the recording holds it back as it always does.

**When it clears.** The freeze clears by itself, and the class sees the iPad as it is then, when Present on Mac turns on or off, a projector joins or leaves (so a new presentation never starts frozen, and starts on the Student copy as EP130 says), the Present link drops (the new link's snapshot catches the Mac up), the Mac's Companion is too old to present, or EmberPad leaves the screen or the iPad locks (the student view and the Mac then show **Paused** as before). A brief interruption that does not leave the screen, such as Control Center, keeps the frozen picture.

**Tests.** `ClassViewFreezeTests` cover the frozen picture holding while the iPad turns pages, writes and points; the projector scene drawing the frozen page; nothing but heartbeats reaching an in-memory Mac (`PresentHost`) while frozen; the unfreeze arriving as one snapshot that the Mac's playback treats as a cut; the recording (`LessonPicture`) following the frozen projector and the worksheet it names; lesson commands while frozen; a Teacher copy opened while frozen never encoded; a swap to the Teacher copy while frozen; a projector joining while frozen on the Teacher copy; and the freeze clearing when the link drops, Present turns off, a presentation starts, or EmberPad leaves the screen. `anUnfreezeIsACutNotAMove` (`PresentMotionTests`, EmberSyncKit) checks the snapshot's cut at the wire. `testCapturesTheFreezeControls` saves the pictures above into `EP152_SHOTS_DIR` when it is set.

### Lesson recording (EP129)

The Mac Companion records a lesson from its own Present on Mac picture and the BOYA microphone into one file on one clock, in place of Voice Memos and the iPad's screen recording. Nothing is uploaded, edited or processed in EmberPad: the voice stays on the Mac, and the video pipeline picks the lesson up from its folder (below).

**Starting and ending.** On the iPad, while presenting to a Companion that records, the Sharing menu (the AirPlay icon and the More menu, where the old disabled "Record lesson" placeholder was) has **Start lesson**, then **End lesson** with a line "Recording 12:03 · BOYA BY-M1". While the Mac records, every screen of the iPad shows a red **REC 12:03** badge in the bottom-left corner (tap it for End lesson); it is drawn in the main scene only, never on the student view or the Mac's picture. An older Companion gets "Update Ember Companion on your Mac to record lessons" and presents as before. The Companion's menu-bar window has a **Lesson recording** section with the same **Start lesson** and **End lesson**, the time and microphone, and **Show recordings**; while it records, its menu-bar icon becomes a record symbol. A command carries an id and is sent again on a new link until the Mac's status names it, so a dropped link neither loses nor repeats it. End lesson pressed while a start is still waiting on the microphone prompt cancels that start: nothing records and the End is reported handled once the Mac is idle. Starting, failing and ending never wait on the Mac's sound system on the main thread (EP134): the microphones are listed, opened and closed in the background, so the Companion always answers the iPad. If macOS does not list its microphones within 5 s, Start lesson fails at once with "The Mac's sound system is not answering, so nothing is recording" on both devices. See the iPad's [Start lesson](docs/screenshots/ep129/ipad-start-lesson.png) and [End lesson](docs/screenshots/ep129/ipad-end-lesson.png) rows, the [REC badge and its warning](docs/screenshots/ep129/ipad-rec-badge.png), and the Companion's section [while recording](docs/screenshots/ep129/companion-recording.png) and [when the BOYA is missing](docs/screenshots/ep129/companion-boya-missing.png) (Simulator and test captures with the fake microphone; `testCapturesTheLessonControls` and `testCapturesTheMenuSection` write them to `EP129_SHOTS_DIR`).

Turning Present off on the iPad while the Mac records asks first: **End lesson and stop presenting**, **Stop presenting, keep recording** (end it from the Companion), or Cancel. Leaving the presentation on the Mac (Esc, the Exit control, **Exit presentation**; EP127) only hides the Mac's window and never stops or pauses a recording, and neither does the link dropping or the iPad stopping: the audio goes on and the picture holds (below). Only **End lesson** ends a recording, or quitting the Companion, which first finishes the file and closes `lesson.json` (as complete, or as failed when no video was saved; below).

**Microphone.** The BOYA is found by name (any input whose name contains "BOYA"), whatever the Mac's default input is. When it is not connected, Start lesson records nothing and asks, on the device it was pressed on: "BOYA microphone not connected", with **Record with built-in mic anyway** and Cancel. The built-in microphone is never used without that choice, and `lesson.json` then says `"preferred": false`. Audio is taken as the microphone delivers it at 48 kHz, mono or stereo as the device has it, with no gain, level gate, noise reduction or other processing in-app, so quiet speech is kept as it comes in. Only macOS's own microphone mode (Control Center) applies: Standard keeps soft speech, Voice Isolation would suppress it, and the Companion logs the mode each time the microphone opens. The audio is encoded once as AAC-LC at 192 kbit/s per channel where the Mac's AAC encoder takes that rate, otherwise at the most it takes below: 192 kbit/s mono and 320 kbit/s stereo, the encoder's stereo maximum at 44.1 and 48 kHz (EP134). The rate is asked of the encoder (`LessonAudioBitRate`). EP129 asked for 384 kbit/s for the stereo BOYA mini 2; the encoder refused it when the first sound arrived, and the first live lesson saved nothing. If the encoder refuses the rate and no file of the lesson has saved anything yet, whether or not sound had arrived (silence fill counts), the next file uses 128 kbit/s, which it takes for mono and stereo, and `audio.bitRate` says so. If the BOYA is unplugged during a lesson and plugged in again, recording from it resumes by itself. The Companion's Info.plist declares `NSMicrophoneUsageDescription`, and asks macOS for microphone access when it launches, because macOS draws its dialog under a full-screen presentation (EP137). It never asks for the first time while a presentation is on screen: a lesson started then records its picture at once, the Mac and the iPad warn that there is no sound yet, and the dialog comes when the teacher leaves the presentation on the Mac. If access is off, the Companion and the iPad say so, naming System Settings > Privacy & Security > Microphone > Ember Companion, and nothing records.

**Picture.** The picture is drawn by a second, offscreen copy of the presentation canvas from the same PRESENT frames as the projector, never captured from the screen, so it holds only worksheet pages and ink: no library, menus, Exit control, status light or other apps. 1920 by 1080, H.264, a new frame whenever the picture changes or moves, up to 30 a second, and at least one a second when it is still. The recording canvas plays scrolling back as the projector does (EP141, above), so each frame is the picture the class saw at that moment, and audio lines up as it did in the room. Frames are drawn on the GPU (`PresentFrameRenderer`, about 2 to 3 ms each); drawing them on the CPU took about 180 ms at 1080p on the main thread, which held recordings to 5 or 6 frames a second while the teacher scrolled or wrote and held up the projector with it. `LessonRecordingSmoothTests` record a bunched 30 Hz scroll and a live stroke and check the file holds at least 24 frames a second, an even scroll and the main thread free. Before the iPad presents, after it stops, and in the library, the recording shows the neutral card (the Ember star on black).

**Teacher copy.** The recording never shows a Teacher copy. Each frame is checked on its own (`LessonPicture`): a page marked as the Teacher copy's (`PresentedView.Page.role == .teacher`, which the iPad sets when the teacher swaps the class onto the Teacher copy; EP130, above) is never recorded, whatever the link version; otherwise a page is recorded only when its document is one the iPad named as a Student copy. A Teacher copy, a swapped-in Teacher copy page, or a page whose document the Mac was not told about holds the last Student frame instead (the neutral card if there was none), while the audio carries on. **Paused** and **Teacher copy · private** hold the last Student frame too. The rule is keyed on each frame, not on what the projector may show, so the projector showing the Teacher copy (EP130) never puts it in the recording. The live projector is unchanged. `lesson.json` lists the Teacher copy's name and times, so the pipeline knows what was open; a Teacher copy swapped in for the class is listed under its worksheet's `id` with the role `teacher` and its own times.

**Audio health.** The Companion checks the microphone once a second. Digital silence (every sample in a buffer below -80 dBFS, a peak under 0.0001 of full scale) or no audio at all (unplugged, or nothing for 2 s) for 60 s raises a warning on the Mac (the menu-bar icon turns to a warning triangle, and the warning row at the top of the menu-bar window says "Microphone silent", then "Microphone silent for 3 minutes", or "Microphone disconnected for…") and on the iPad (the REC badge turns amber with the same words). A microphone that has sent nothing at all since the lesson started (it never opened) is warned about after 6 s instead: "Microphone disconnected: no sound is coming in". The level check is the only one, and -80 dBFS is far below quiet speech or a quiet room on a working microphone, so in practice only a dead, muted or zero-signal input reads below it. It clears when sound comes back. Every warning is kept in `lesson.json`. While the microphone sends nothing the audio track is filled with silence, so it stays as long as the picture and in step with it.

**Robustness.** The video is a fragmented MP4 that closes a fragment every 2 seconds, and `lesson.json` is rewritten (atomically) every 5 seconds and at every change, so a crash, a forced quit or power loss loses at most the last 2 seconds: the file plays up to its last fragment. At the next launch the Companion closes any lesson left "recording" as `"interrupted"`, at its last write, once nothing has written to it for 60 s (so another running Companion's live lesson is never closed). While recording, the Companion keeps the Mac from idle sleep. If the Mac sleeps anyway (the lid closed), the file is finished as the Mac sleeps and recording continues in a new file, `lesson-2.mp4`, when it wakes. Every second the Companion also checks that the video is being saved (EP134): the file's writer has not failed, its bytes on disk grew in the last 4 s (twice the fragment interval, plus 2 s), and the picture and the sound were both taken in the last 4 s. When one is not so, or a new file cannot be started (for example the disk is full), the Mac and the iPad show "Recording stopped: the video is not being saved. Trying again." at once, `lesson.json` records a `notRecording` warning from when saving stopped, and the file is closed with what it holds; a file that holds nothing is deleted and taken off the list, and its name used again. The next file is tried at once after a file that had saved media, otherwise after 2, 4, 8 and 16 s and then every 30 s, so a failing encoder never makes a new empty file each second. The warning ends when a new file has media on disk. At End lesson every video file in the folder that holds nothing is deleted, listed or not, and the folder is swept once more 2 s later, since a file opened just before End can land a moment late. A lesson that ends with no playable video is closed as `"failed"`, never `"complete"`, and the Mac and the iPad say "The last lesson was not recorded". The recorder logs each step: `log show --last 1h --predicate 'category == "lesson"'`.

#### Output contract

Each lesson lands in its own folder, named for the Mac's local time when it started:

```
~/EmberRecordings/<YYYY-MM-DD>_<HHMM>/       e.g. ~/EmberRecordings/2026-11-16_1430/
  lesson.mp4        the lesson; lesson-2.mp4, lesson-3.mp4… only after the Mac slept or the encoder restarted
  lesson.json       the record below
```

A second lesson started in the same minute gets `_1430-2`, and so on. A folder is finished when its `lesson.json` says `"status": "complete"`, `"failed"` or `"interrupted"`; while it says `"recording"` the Companion is still writing it (read nothing until then, or expect it to grow). Each MP4 holds one H.264 video track and one AAC-LC audio track that start together at the file's start; files follow one another on the lesson's timeline at their `startOffset`, and a gap between them is time the Mac was asleep.

`lesson.json` is UTF-8 JSON with sorted keys. Times are ISO 8601 in UTC with milliseconds and a `Z` (for example `"2026-11-16T06:30:00.000Z"`); offsets are seconds since `startedAt`, rounded to the millisecond, on the same clock as the video, so an offset is the time in the lesson's video. A key whose value is not known yet is absent, never `null`.

| Field | Type | Meaning |
| --- | --- | --- |
| `schema` | string | `"emberpad.lesson/1"`. A later incompatible change gets a new name. |
| `status` | string | `"recording"` while the Companion writes it, `"complete"` after End lesson or quit with at least one playable video file, `"failed"` after End lesson or quit with none (`files` is then empty and `audioWarnings` says why), `"interrupted"` when it was closed at the next launch after the Companion stopped without finishing. |
| `startedAt` | time | When recording started. |
| `endedAt` | time | When it ended; absent while recording. |
| `updatedAt` | time | When this record was last written. |
| `timeZone` | string | The Mac's time zone, an IANA name such as `"Asia/Singapore"`. |
| `utcOffset` | string | That zone's offset from UTC at `startedAt`, such as `"+08:00"`. |
| `startedFrom` | string | `"ipad"` or `"mac"`: where Start lesson was pressed. |
| `microphone.name` | string | The input device recorded, as macOS names it, such as `"BOYA BY-M1"`. |
| `microphone.preferred` | boolean | True for the BOYA; false when the teacher chose the built-in microphone because the BOYA was missing. |
| `microphone.sampleRate` | number | Hz, `48000`. |
| `microphone.channels` | integer | 1 or 2, as the device delivers. |
| `video.codec` | string | `"h264"`. |
| `video.width`, `video.height` | integer | `1920`, `1080`. |
| `video.maxFrameRate` | integer | `30`: frames come when the picture changes or moves (30 a second while it scrolls or ink is written), at least one a second, so the rate varies up to this. |
| `audio.codec` | string | `"aac"` (AAC-LC). |
| `audio.sampleRate` | number | Hz, `48000`. |
| `audio.channels` | integer | As `microphone.channels`. |
| `audio.bitRate` | integer | Bits per second given to the AAC encoder: `192000` mono, `320000` stereo (192000 per channel, capped at what the encoder takes), or `128000` when the encoder refused that and the lesson's video uses the safe rate. |
| `files` | array | The video files in order. A file that saved nothing is deleted and not listed. |
| `files[].name` | string | `"lesson.mp4"`, then `"lesson-2.mp4"`… |
| `files[].startedAt`, `files[].endedAt` | time | When the file's recording started and ended; `endedAt` is absent while it records. |
| `files[].startOffset`, `files[].endOffset` | number | The same on the lesson's timeline. |
| `files[].interrupted` | boolean | Present, and true, only on a file that was cut off by a crash; it plays up to its last fragment. |
| `documents` | array | Every document open on the iPad while recording, in the order first opened, Teacher copies included. Empty when the iPad's EmberPad is too old to say. |
| `documents[].id` | string | The document's UUID in the iPad library. A worksheet's Teacher copy swapped in for the class (EP130) is listed under the worksheet's UUID, with the role `"teacher"`, as an entry of its own. |
| `documents[].title` | string | Its title, as the library shows it. |
| `documents[].subject` | string | Its subject, such as `"H2 Chemistry"`. |
| `documents[].classTag` | string | Its class, such as `"MI PU3"`; absent when the library has none. |
| `documents[].role` | string | `"student"` or `"teacher"`. A Teacher copy's pages are never in the video. |
| `documents[].ranges` | array | Each time it was open: `from` and `to` (times), `startOffset` and `endOffset` (numbers). `to` and `endOffset` are absent while it is open. |
| `audioWarnings` | array | Each audio-health warning, in order. Empty when there was none. |
| `audioWarnings[].kind` | string | `"silent"` (digital silence), `"disconnected"` (unplugged, or no audio) or `"notRecording"` (the video was not being saved: a file could not start, its writer failed, or it stopped growing or taking picture or sound; picture and sound of that stretch were not kept). |
| `audioWarnings[].from`, `audioWarnings[].to` | time | When the problem began (the last sound before it, or when saving stopped) and when it ended (sound came back, or a new file saved media) or the lesson ended; `to` is absent while it lasts. |
| `audioWarnings[].warnedAt` | time | When the warning was raised: about 60 s after `from` for `silent` and `disconnected`, 6 s after the lesson started for a microphone that never sent sound, and when it was noticed (within a few seconds) for `notRecording`. |
| `audioWarnings[].startOffset`, `audioWarnings[].endOffset` | number | `from` and `to` on the lesson's timeline. |

### Peer-to-peer hello (Debug only)

The Device checks screen's **Peer-to-peer hello** section and the Companion window's **Peer-to-peer hello (debug)** section (shown only in a Debug Companion launched with `-EmberPeerHelloPanel YES` or `-EmberPeerHelloAutostart YES`) are used to check that the Mac and iPad can talk with neither joined to a network. The proof is a successful on-device run while neither device is joined to a network. The Companion's **Start** button opens an `NWListener` advertising `_emberws._tcp` as `EmberPad Companion (debug)`. The iPad browses for it, then **Echo and time 50 MB** connects, checks a 64-byte echo and sends 50,000,000 synthetic bytes. The Companion acknowledges the byte count and SHA-256, and the screen reports decimal MB/s plus the path interface Network.framework reports for each connection; this does not prove peer-to-peer Wi-Fi was used. Results go to the pass/fail list and `Documents/device-checks.log`. The listener, browser and every connection set `includePeerToPeer`. Keep Wi-Fi on on both devices; neither needs to join a network. Both Info.plists declare `NSLocalNetworkUsageDescription` and `NSBonjourServices`, so each app asks for Local Network access the first time; if it is denied, the screens say so. There is no pairing, key or TLS (that is EP-22): any device in range can connect to a running Debug listener, so start it only for the check. The framing, server, browser and client live in `EmberSyncKit/Sources/EmberSyncKit/PeerHello*.swift` under `#if DEBUG`. A Release build contains none of them and does not link `Network.framework`.

`swift test --package-path EmberSyncKit` runs the framing tests and an in-process 50 MB loopback transfer. To time the real Companion on one Mac, launch the Debug build with `-EmberPeerHelloAutostart YES`. It logs `EmberPad peer hello listening on port N`. Then run the skipped live test:

```sh
EMBERPAD_PEER_HELLO_PORT=N swift test --package-path EmberSyncKit --filter liveCompanion   # 127.0.0.1
EMBERPAD_PEER_HELLO_BROWSE=1 swift test --package-path EmberSyncKit --filter liveCompanion # via Bonjour
```

The library reads `embedded.mobileprovision` best-effort: amber at 48 hours or less, red below 24 hours, unknown when absent/malformed (normal for unsigned Simulator builds). This parses only a reminder, not a signature or security decision. The library shows the Inbox delivery time and, once paired, the last completed sync time; neither is shown until it has happened.
