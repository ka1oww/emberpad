# EmberPad

The iPad app shows itself to users as **Ember Slate** (home-screen name and in-app text); the library header shows the Ember star mark alone; the project, targets, bundle IDs and paths keep the EmberPad name.

Base code for a personal offline iPad teaching app. The Ember House colour tokens, reusable type styles, original app and Companion artwork, and branded launch background, the phase-1 library screen, the initial worksheet chrome and the toolbar strip are in place; the teacher's on-device decisions are still pending. This is a development scaffold, not yet a classroom-ready release.

## Build and test without signing

```sh
swift test --package-path EmberSyncKit
xcodebuild -project EmberPad.xcodeproj -scheme EmberPad \
  -configuration Debug -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/emberpad-ios CODE_SIGNING_ALLOWED=NO build
UDID=$(xcrun simctl list devices available --json | python3 -c 'import json,sys; d=json.load(sys.stdin)["devices"]; c=[x for v in d.values() for x in v]; print(next((x for x in c if x["name"].startswith("iPad")), c[0])["udid"])')
xcodebuild -project EmberPad.xcodeproj -scheme EmberPad \
  -configuration Debug -destination "id=$UDID" \
  -derivedDataPath /tmp/emberpad-test CODE_SIGNING_ALLOWED=NO ONLY_ACTIVE_ARCH=YES test
xcodebuild -project EmberPad.xcodeproj -scheme 'EmberPad Companion' \
  -configuration Debug -destination 'generic/platform=macOS' \
  -derivedDataPath /tmp/emberpad-mac CODE_SIGNING_ALLOWED=NO build
zsh -n resign/renew.zsh
plutil -lint resign/dev.emberpad.renew.plist
```

These commands do not install on a device, provision an App ID or need an Apple account. The bundle IDs are final: changing the iPad ID later means deleting the app and its ink. The checked-in `EmberPad.xcodeproj` and shared schemes are the source of truth. `Apps/EmberPad`, `Apps/Companion`, `Apps/EmberPadTests` and `Apps/EmberPadUITests` are file-system synchronized folders, so adding or removing a `.swift` file there needs no `project.pbxproj` edit (`Info.plist` files stay referenced by path and are excluded from membership). Commit test changes with source changes.

The GitHub workflow runs package tests, both unsigned builds, the EmberPadTests simulator suite, the EmberPadUITests real-touch suite (in shard 3, with every test class not named in shards 1 and 2), and syntax/plist checks. Run only the UI tests locally with `-only-testing:EmberPadUITests` on the test command above. Ink feel, touch routing, Pencil double-tap, rendering at 1x/2x, capture traits, external-display behavior and signing cannot be established by those checks.

## Drawing stress test on an iPad

`scripts/device-stress-test.sh <device-udid> <output-dir>` writes on a simulator or a connected iPad as fast as a student does, with every tool: fast fountain-pen brackets, long writing, strokes started while the last one is still landing, every pen colour and width, hold-to-line, shapes, the highlighter, both erasers at every size, lasso and circle-to-lasso moves, scribble-to-erase, the laser, undo and redo bursts, rapid tool switches, a toolbar drag, and writing straight after a zoom, a scroll or a page change. While it draws it watches every frame and checks that no stroke is lost or doubled, landed ink never leaves the screen even for one frame, each undo takes one stroke and redo brings it back, erasers remove exactly what they should, and latency and frame stalls stay within the bounds in `StressBounds`. It writes `summary.json` and `summary.md` (with the measured numbers and evidence pictures) to the output directory and into the result bundle. The tests run in a separate app, Ember Stress (`io.github.ka1oww.emberpad.stresstest`), installed beside Ember Slate and never over it (the script removes only an earlier copy of Ember Stress, so PencilKit's record of past drawings never carries over), in temporary libraries, with synthesized Pencil input and no Mac pairing; Ember Slate and its notebooks are never touched. On a physical iPad set `DEVELOPMENT_TEAM` first; the script passes `-allowProvisioningUpdates`. `DeviceDrawingStressTests` skip themselves unless the script runs them, and CI leaves them out.

## Offline library

Import PDFs with **Import from Files**, choosing an existing or new class name. Files open through security-scoped coordinated reads and are copied into the app. Encrypted/locked or unreadable PDFs are rejected. A Finder/Files delivery can also place PDFs at `Documents/Inbox/<Class>/<file>.pdf`; a loose Inbox PDF goes to `Unfiled`. The reserved `Documents/Inbox/EmberLibrary` folder is the Mac's library delivery, described below, and is never read as loose PDFs. Nested paths within a class are preserved as source identity. Inbox is checked on foreground and by **File Inbox**. `Documents/Inbox` is reserved by iOS, which creates it itself and refuses to let the app create it, so a missing Inbox counts as empty and is never created. Retained Inbox files are idempotent receipts, and are never deleted while a sender could be writing them. Symlink deliveries are skipped. No absent-file deletion is inferred from an incremental Inbox.

If separate import locations would otherwise share a class/path, EmberPad gives the later assignment an available visible filename suffix, preserving any existing suffixes. It remembers each source's assignment, so re-imports keep their identity across picker batch order, Inbox/Files arrival order and app/store reopen. A changed file at that same source path follows the version rules below.

The export reads the stored PDF and drawings but never writes to them; it is built in a temporary folder that is removed when the share sheet closes. Teacher copies cannot be exported. Pages keep their original size; ink is rasterised at 3x over the vector page, so text stays sharp. Rotated pages (90 or 270 degrees) are exported at their displayed size, so ink lines up with what you saw on screen. **Export This Page** (worksheet More menu, beside Export flattened PDF) does the same for only the page in view: a one-page PDF named `<title> p<N> (annotated).pdf`, with the same renderer, ink flattening, read-only guarantees and Student-copy-only rule. Ink saved on other pages is not read. Each document version has its own `Application Support/Library/<UUID>/` folder:

```text
original.pdf            # untouched PDF bytes for this version
doc.json                # format 2: source class/path/hash and publication record, dates, status, ink pages, paired copy
pages.json              # every page in order: the PDF's own pages (ids pdf-0, pdf-1, ...) and pages added in Ember Slate,
                        # with each page's rotation and bookmark when set (EP62)
ink/pdf-0.drawing       # one page's ink by page id, native PKDrawing.dataRepresentation()
ink/<uuid>.drawing      # ink on an added page
```

Ink is stored by page id, so adding or deleting a page never moves another page's ink (EP61). A folder written before pages could be added has `page-<n>.drawing` files and no `pages.json`; the first time anything reads it, the store moves each `page-<n>.drawing` to `ink/pdf-<n>.drawing` and then writes `pages.json`. The moves are listed first in a `.pages-migration.json` journal, each is a rename within the folder, and `pages.json` is written last, so a crash at any point finishes the same moves on the next launch without losing or misplacing ink. `original.pdf` is never touched. A page added to a worksheet also counts as the teacher's work, like ink: a changed delivery adds an **Updated** copy beside it rather than replacing it.

EP62 adds two optional fields to a page in `pages.json`: `rotation` (90, 180 or 270, quarter turns clockwise on top of the PDF page's own rotation) and `bookmarked` (true). Each is written only when set, so a worksheet nobody turned or bookmarked keeps the exact `pages.json` it had, and a file written before EP62 reads as unturned and unbookmarked; the format stays `emberpad.pages/1`. Pages may also appear in any order, as long as each of the PDF's own pages appears exactly once. A turned page's ink is stored as if the page were not turned, so it always fits the page as `original.pdf` draws it; it is turned with the page on screen, in the student view and in exports, and turned back when it is saved. Turning a page therefore never rewrites its ink file. A moved or turned page counts as the teacher's work, like an added page; a bookmark alone does not, since it only helps find a page.

The app's `DocumentSession` owns every page drawing and updates from `canvasViewDrawingDidChange`, independently of overlays. It saves about one second after changes and flushes on editor exit and backgrounding. Save errors stay visible; corrupt saved ink never silently becomes an empty drawing. Storage uses Documents/Application Support, with no reliance on Caches. Deleting the app still deletes this data; the ink backup below keeps a copy of every inked Student worksheet on the paired Mac.

Same path and checksum is a replay. New bytes without ink replace the current copy while retaining the prior folder in hidden `.Previous` for 30 days. New bytes with ink create an **Updated** copy and mark the annotated one **Older version**; ink never moves to new bytes. An open, uninked worksheet is pinned: changed deliveries wait until the editor closes so an old canvas cannot write onto a replacement PDF. Recheck Inbox after closing it. Previous-version pruning is an explicit store operation; the base keeps versions conservatively until that maintenance path is wired.

The complete-manifest planner also returns archive and no-download relink actions for Mac deletion/rename. Ambiguous identical hashes are imported and archived conservatively rather than assigning somebody else's ink. Full manifests arrive by the Inbox copy or by sync, described below; the iPad has no cloud folder access (Debug builds also carry the synthetic peer-to-peer hello below).

### Library model v2

A version-2 manifest gives every entry a publication record: subject, optional class tag, a stable paper key, role (`student` or `teacher`), display title and an optional `archived` mark (written only when true). Each paper key has at most one copy per role. An archived copy is listed only under **Archived** on the iPad, beside copies archived because they left the Mac library, and it still pairs with its counterpart. Version-1 manifests and Inbox deliveries still load as Student copies whose subject is the class folder; the iPad never infers a Teacher role from a file or folder name. Format-1 `doc.json` files still load as Student copies and are upgraded to format 2 when next written. Format 2 keeps the publication record in `source` and stores `pairedDocumentID`: the single current copy of the opposite role with the same paper key, recomputed after document imports, replacements, relinks and archives.

A document's identity is its path plus role, and its role never changes, so one path may hold a Student and a Teacher copy and a role change files a new copy beside the archived old one. Student copies keep the rules above. Teacher copies cannot be inked in this version: the store refuses Teacher ink, a changed Teacher copy replaces in place, and a Teacher copy at a new path follows its paper key to its existing document. No rule replaces an inked document, moves ink onto other bytes or relinks across roles.

### Library source: Drive EMBER folder (macOS)

`EmberLibrarySource` builds a version-2 manifest from the Google Drive EMBER folder. `EmberLibrarySource.discoverDriveRoot()` finds it at `~/Library/CloudStorage/GoogleDrive-*/My Drive/EMBER`, taking the first Drive account folder by name that has one; a root passed in explicitly is used as given, and tests use synthetic trees. It only reads, and it never follows symlinks.

- **What is included:** eligible regular `*.pdf` files below the root, case-insensitively, including single-copy notes, commonly asked question booklets, answering techniques and TYS papers. Discovery is based on files; sign-off and publication records are not consulted. Hidden entries (names starting with `.`) and symlinks are skipped. Non-PDF files are skipped and counted. Build output is skipped and counted, never read: PDFs below folders named `redraws`, `crops`, `_build`, `artifacts`, `_assets`, `_qa` or starting with `_redraws`, PDFs below source folders (a name containing `Source (LaTeX)`, ending with `Word Source`, or equal to `Source`; `Text Sources` is kept), all case-insensitive, and the shared logo `ember-star.pdf`. A previous copy from a source folder is not carried forward.
- **Subject:** the top-level folder: `EMBER CHEMISTRY` is Chemistry, `EMBER MATH` is Math, `EMBER PHYSICS` is Physics and `EMBER BOOKLETS (MI + JC)` is Booklets. Any other top-level folder is a subject under its own name, except that leading underscores are removed from an underscore folder's subject name; a PDF directly in the root is General. The path below the subject folder is the manifest path and the title context: `NOTES & TUTORIALS/Topic/Notes.pdf` shows as **NOTES & TUTORIALS / Topic / Notes**.
- **Teacher pairing by name, in one directory:** a name ending in a Teacher marker pairs with the same-directory PDF whose name is identical once its marker is removed (case and repeated spaces ignored). Markers include `Teacher`, `Teacher Copy`, `Teacher Version`, `Solutions`, `Answers`, `Answer Key` and `Mark Scheme`, either in brackets (`(Teacher)`), after a hyphen, dash, underscore or em dash, as a trailing word, or as the whole name (`teacher.pdf`). A bracketed group at the end that contains the word Teacher also counts. A Student marker (`Student`, `Student Copy`, and corresponding version forms) is removed the same way. Both copies share the paper key `<subject>/<folders>/<name without marker>`. A PDF with no partner is a single-copy Student document, and an unpartnered Teacher-marked PDF is still delivered with role `teacher`, so it never becomes a Student copy. When a directory has exactly a Student-marked PDF and an unmarked PDF of the same name (and no Teacher-marked one), the unmarked PDF is the Teacher copy and the two pair, since Drive files the blank copy as `(Student)` beside the full-answers copy. Any other mix under one key, such as an unmarked, a Student-marked and a Teacher-marked PDF, or two Student-marked PDFs, is still held back as `duplicate-paper-key`.
- **Archive folders:** a delivered document below a non-build-output folder whose name starts with `_` (such as `_legacy-archive`) is delivered with the `archived` mark. A nested underscore folder stays in its source path but not its title; for a top-level underscore folder, leading underscores are removed from the subject name. Build-output folders remain excluded even when their names start with `_`.
- **Identity and misses:** content identity is the SHA-256 of the bytes. A file or folder that cannot be read (Drive offline, not downloaded yet, or metadata unavailable) is a miss with reason `unreadable`, never a deletion. Other miss reasons: `duplicate-paper-key` (two copies of one role under one key, or one path; all are held back rather than guessed between), `privacy-withheld`, `identical-copies` and `student-matches-a-teacher-copy` (a Student copy whose bytes equal any Teacher copy is held back, and the Teacher copy is still delivered), and `invalid-name`.
- **Carry-forward:** pass the previously delivered manifest as `previous`. Each previous copy (paper key and role) that is not delivered this run is carried forward unchanged, as `source-vanished`, `source-unreadable` or `held-back`, so a vanished source means "no update" and the planner never archives it. A carried copy still passes the privacy and cross-role checks.

Class is the folder- or file-name prefix (`MI PU1-3`, `YIJC JC1-2`, `NYJC-EJC JC1-2`, `SEC 1-4`), the first folder below the subject that has one winning over the file name. A prefix can also come from the alias table loaded from `~/Library/Application Support/EmberPad/class-aliases.json` and passed to `EmberLibrarySource` (synthetic example: `EmberSyncKit/Examples/class-aliases.example.json`). With no prefix, the copy belongs to **All classes**. Alias values must be known class codes or short uppercase tags matching `^[A-Z0-9][A-Z0-9-]{0,11}( [A-Z0-9][A-Z0-9-]{0,11}){0,2}$`; other values are skipped and counted. In every folder and file name, each `Sec 1-4` or `S1-4` token is checked against the complete word segment before it (after the preceding section token, if any): it must be empty, a class code or an alias key. Otherwise that segment's words are withheld and removed, and no class comes from it. Non-class name words in alias keys and configured `withhold` terms are also withheld. The real table is personal data and never goes in the repository. A final check rejects any copy whose emitted class tag is invalid, or whose source path, title, subject or paper key still contains a personal-name shape or withheld term. The local path of each copy and the miss list stay on the Mac and never go in the manifest.

The macOS Companion defaults to the discovered Drive EMBER folder and remembers a folder chosen with **Choose EMBER folder…**. The Companion prepares the iPad library by itself: once at launch, after **Choose EMBER folder…**, and whenever anything below the EMBER folder changes (a PDF or folder added, changed, renamed, moved or deleted, at any depth). `LibraryAutoPrepare` watches the folder with FSEvents, so there is no polling, and runs the same Prepare as the button (`LibraryOutbox.prepare(from:aliases:)`) once the folder has been quiet for 30 s after the last change. It waits longer while a changed PDF's modification date is less than 30 s old, which means it is still being written, but no more than 10 minutes in all. It never runs two Prepares at once: a change during one schedules exactly one more after it. Events that cannot change the library are ignored: hidden and non-PDF files (which only lengthen a wait already running), extended attributes, and the clone flag that each Prepare's own APFS copy into the Outbox reports on its source. A pending Prepare whose only changes are such clones of files whose size and date still match what the last Prepare read is dropped. On a Google Drive CloudStorage folder, files that Drive for desktop syncs in arrive as created events, and an online-only placeholder that is downloaded or made online-only again arrives as a modified event. Reading a placeholder downloads it, so the first Prepare after that is followed by one more. **Prepare iPad library** still prepares now and replaces any pending automatic Prepare. Below the buttons the window shows whether it is watching, a change waiting to settle, when the library was last prepared automatically, and why the last automatic Prepare failed, with no popups. A Prepare reads and hashes every PDF each time: for the 386 documents in the real EMBER folder (212 MB) that took about 1 s with the files cached and 6 to 7 s cold. The window shows document counts per subject, the pair, single-copy and archived totals, and the PDFs or folders not read this time with their reasons. Preparation never writes inside the EMBER folder; it writes the iPad Outbox described below. See the [light](docs/screenshots/companion-light.png) and [dark](docs/screenshots/companion-dark.png) screenshots.

### Library delivery: Outbox to Inbox

**Prepare iPad library** writes the Outbox at `~/Library/Application Support/EmberPad/Outbox`: `EmberLibrary/manifest.json` (the version-2 manifest) and `EmberLibrary/files/<sha256>.pdf`, one PDF per content hash, so no local file name leaves the Mac. The Outbox's own manifest is the `previous` manifest for the next read, so a copy missing from Drive is carried forward with its bytes from the old Outbox. Every PDF read this run is copied in and checked against its manifest hash; if one changed meanwhile, the write fails and the old Outbox stays. A new Outbox is built in a hidden staging folder beside it and swapped in with one atomic rename (`RENAME_SWAP`), so a reader sees either the whole old Outbox or the whole new one.

The optional delivery in `resign/renew.zsh` copies the Outbox into the iPad's `Documents/Inbox` (see [resign/README.md](resign/README.md)). On foreground and **File Inbox**, the iPad reads `Inbox/EmberLibrary/manifest.json`; a manifest that is cut short or not version 2 changes nothing. It plans the whole manifest through `DiffPlanner`, then runs each action that needs bytes only when that PDF is present with the manifest's size and SHA-256 and opens as a PDF. Archive actions run only when every such action succeeded, so a half-delivered or interrupted copy files what arrived and archives nothing; the next check finishes it. Ink rules are the store's usual ones: an inked copy gets an **Updated** version beside it, and an open worksheet waits. Only documents that came from a library delivery are ever archived; worksheets imported from Files or loose Inbox PDFs are not. A completely applied delivery is recorded by its manifest hash and not applied again, and only then are Inbox copies the manifest no longer lists removed. Loose Inbox scanning skips the reserved `EmberLibrary` folder.

### Sync wire protocol

`Wire*.swift` in EmberSyncKit is the private protocol a later transport carries between the Mac (server) and the iPad (client). It opens no connection itself: `WireClientSession` and `WireServerSession` are pure state machines that take received bytes and the current time and return frames to send and events, so a driver moves bytes and calls `tick` on a timer. The server emits at most one frame per `receive` call; send that frame, then call `receive(Data(), now:)` while `hasPendingInput` is true before reading more transport bytes. This bounds response generation for coalesced requests while preserving the transport's backpressure. `InMemoryWireTransport` is an in-process pair with bounded buffers for tests; it opens no socket.

A frame is a 1-byte type, a 4-byte big-endian payload length and the payload. The client sends HELLO (magic `EMBR`, version range, role, largest chunk and manifest it accepts) and the server answers HELLO with the highest common version. The client then sends GET-MANIFEST (answered by MANIFEST, the `ManifestCodec` JSON) and GET by SHA-256 with initial credit (answered by DATA chunks at explicit offsets and a final END with the total length). Each request has a strictly increasing client-chosen id and gets exactly one terminal frame: MANIFEST, END, PUT_DONE, DIGEST or a request ERROR (not found, cancelled, stalled, busy, manifest too large, unavailable, rejected, storage failed, integrity failed).

Version 2 adds one upload, PUT, used only by the ink backup and only from the iPad to the Mac. PUT announces a size, a SHA-256 and up to 4 KiB of JSON metadata; the Mac answers PUT_DONE "already held", or grants PUT_WINDOW credit, and the iPad sends PUT_DATA at explicit offsets within that credit and then PUT_END. The Mac hashes as bytes arrive and answers PUT_DONE only once the size and SHA-256 match and the copy is stored. A PUT is at most 256 MiB. Both peers still offer version 1: a version-1 peer never receives a PUT frame, because the iPad sends PUT only when version 2 was negotiated, and a session at version 1 treats one as a protocol violation. PUT never travels Mac to iPad, and PUT_WINDOW and PUT_DONE never travel iPad to Mac.

Version 3 adds one small question, GET_DIGEST (EP91). The iPad sends a request id (a 9-byte frame) and the Mac answers DIGEST with the SHA-256 of the manifest's `ManifestCodec` JSON, exactly the bytes a MANIFEST would carry (a 41-byte frame), or a request ERROR `unavailable` before **Prepare** has run. The Mac reads the manifest afresh for each GET_DIGEST, as for GET_MANIFEST. A sync writes those same bytes as its downloaded manifest, so the digest equals the library's applied-delivery receipt once that manifest is filed. Every peer still offers versions 1 and 2: the iPad sends GET_DIGEST only when version 3 was negotiated, and a session at version 1 or 2 treats one as a protocol violation.

Version 4 adds Present on Mac (EP93): PRESENT (type 17, iPad to Mac, up to 16 MiB) carries one encoded `PresentUpdate`, and PRESENT_REPLY (type 18, Mac to iPad, up to 64 KiB) carries one `PresentReply`. They are opaque to the wire session; `PresentMessages.swift` defines their contents (below). Every peer still offers versions 1 to 3. The iPad sends PRESENT only when version 4 was negotiated, a session at version 1 to 3 treats one as a protocol violation, and a Companion from before EP93 never receives one: the iPad's HELLO tells it the Mac is older and it says so. Sync, GET_DIGEST and the ink backup are unchanged.

Flow control is per transfer credit: the server sends only bytes the client has granted, chunked to the smaller of both peers' limits and round-robin across transfers. The client grants WINDOW increments only as the app reports bytes written, so a slow writer holds at most one window. The client checks every chunk's offset and credit, hashes the bytes as they arrive and reports a completed file only when the size and SHA-256 both match. CANCEL fails a request at once and discards its late bytes until the server acknowledges. A transfer with credit outstanding and no progress stalls on the client; one the client leaves without credit is dropped by the server. Unknown, out-of-direction and oversized frames are rejected from their headers before their payloads are buffered; malformed payloads are rejected when decoded. These violations close the session with a protocol-violation ERROR. Every length is bounded: chunks to 1 MiB, manifests to 32 MiB and credit to 16 MiB per transfer; concurrent requests are limited by `WireLimits`.

### Pairing

`PairingCredential`, `PairingKeychain` and `PairingTLS` in EmberSyncKit pair one Mac with one iPad. In the Companion's iPad section, **Pair iPad…** creates a pairing if there is none: a 256-bit secret and a 128-bit service id from `SecRandomCopyBytes`. The Mac saves it in its Keychain and shows it as a QR code (`EMBERPAD-PAIR:1:<service id>:<base64url secret>`, not a URL). The code opens in its own window with `sharingType = .none`, which keeps it out of screenshots and screen sharing where macOS honours that setting. The window closes after five minutes or on **Done**. On the iPad, tap **Pair with Mac…** in the library sidebar footer (or, when already paired, touch and hold **File Inbox** and choose **Pair with a different Mac…**), then scan the code with the camera. That needs only `NSCameraUsageDescription`, no entitlement. The camera preview is replaced while the screen is captured or a student display is connected. The scanner refuses any code not in the exact current format, and a refused code changes nothing.

Each side keeps the pairing only as one generic-password Keychain item (this-device-only on iPad, never synchronised). It is never stored in UserDefaults or files. Descriptions and reflection print `<redacted>` in place of the secret, and the app UI shows only the service id's first six characters and the date. **Forget iPad** on the Mac and **Forget Mac…** on the iPad each delete their own item. Once the Mac forgets, the old secret is useless: any new pairing has a fresh secret and service id. Pairing again overwrites the item, and **Pair iPad…** on the Mac treats an unreadable (corrupt) item as absent and replaces it with a fresh pairing.

`PairingTLS.parameters(for:)` is the only source of connection parameters for sync, and the Mac listener and iPad client use the same parameters. They set up TCP inside TLS 1.2 with a single PSK cipher suite (`TLS_PSK_WITH_AES_128_GCM_SHA256`) and peer-to-peer Wi-Fi on. The key is HKDF-SHA256 of the secret, bound to the service id; the PSK identity names the pairing, never the secret. The Bonjour type is `_embersync._tcp` and the instance name is the service id. Loopback tests over real sockets show the paired peer connects and negotiates that suite. A wrong key, a peer from another pairing, plain TCP, certificate TLS and a server with the wrong key all fail the handshake, and nothing they send reaches the server's reader. The Keychain store is tested against the real macOS Keychain under throwaway service names. The iPad app tests use an in-memory store, because the unsigned Simulator host has no Keychain entitlement. The Companion now listens (the sync server below); the iPad client (below) connects to it, so the Mac cannot tell whether the code was scanned until that iPad first syncs.

### Sync server

`SyncServer` in EmberSyncKit (macOS only) is the Companion's side of sync. While a pairing exists the Companion runs one: an `NWListener` on `PairingTLS.parameters(for:)`, so every connection uses the pairing's TLS pre-shared key and peer-to-peer Wi-Fi is on. That lets the iPad reach the Mac at home and at a venue with no shared Wi-Fi. It advertises the pairing's service id as `_embersync._tcp` over Bonjour, which needs the Companion's `NSLocalNetworkUsageDescription` and `NSBonjourServices` keys. A peer without this pairing's key fails the TLS handshake and never reaches the sync protocol. A connection that does not finish the handshake within 10 seconds is dropped, and at most four connections are open at once. **Forget iPad** stops the server at once; pairing again starts it with the new key. A failed listener retries by itself after five seconds.

Each connection runs one `WireServerSession` over `OutboxContentProvider`, which serves the Outbox's `manifest.json` and `files/<sha256>.pdf` by content hash. The manifest is read afresh for every request, so a new **Prepare iPad library** is served without a restart. Before **Prepare** has run, a manifest request gets `unavailable`. A file is opened with `O_NOFOLLOW` and must be a plain file, and it is read through that one descriptor for the whole transfer. The driver stops reading from the peer while 512 KiB of replies are still queued, and pulls file data only below that mark, so a slow iPad cannot make the Mac buffer the library.

While a transfer is in progress the server holds an IOKit `PreventUserIdleSystemSleep` assertion named "EmberPad Companion is sending the library to the iPad". It lets go two seconds after the last transfer ends, and on stop. The display may still sleep. The Companion header shows the server's status line: for example "Serving 16 documents · iPad synced 07:58", "Sending 2 files to the iPad", or "Sync unavailable · retrying". The iPad row adds the last sync time.

**Open at login** in the iPad section uses `SMAppService.mainApp`. It is off until you turn it on, and the Companion never registers itself. If macOS cannot find this copy of the app the switch is disabled, and if registering fails (for example in an unsigned build run from a build folder) the reason shows under it.

`SyncServerTests` run the real server on loopback with a real TLS-PSK `NWConnection`. The Outbox comes from the real Prepare path over a synthetic Drive EMBER tree, and the client is a small one built on EP-21's `WireClientSession`. The tests cover:

- the paired client fetches the manifest and every file, byte for byte, on window grants;
- the iPad's real `LibrarySyncDownloader` syncs the Outbox over the TLS-PSK connection and files it into a real library;
- a new Prepare is served without a restart, and an unknown hash is not found;
- wrong keys, another pairing, plain TCP and certificate TLS get no sync frame;
- a silent peer, connections over the limit and stop are all handled;
- the power guard is held only while sending, and the real assertion shows in `IOPMCopyAssertionsByProcess`.

`InkBackupTests` also run EP-24's real `LibrarySyncDownloader` end to end against this server (see Ink backup to the Mac below).

### Sync client (iPad)

Once paired, EmberPad syncs on launch, on every return to the foreground and on **Sync now** (in the library sidebar footer, which also shows the sync status, last synced time and plain error copy, and in the **File Inbox** menu). `LibrarySyncConnector` browses Bonjour for `_embersync._tcp` with peer-to-peer Wi-Fi on, takes only the instance named by the pairing's service id, and connects with `PairingTLS.parameters(for:)`, so a Mac without the pairing's key never gets a byte. The app declares `NSLocalNetworkUsageDescription` and `NSBonjourServices`; no entitlement is needed. A Mac not seen within 8 seconds is reported as not found, with nothing changed. Networking is foreground-only: leaving the app cancels the sync, and nothing runs while the iPad is not paired.

While EmberPad stays the active app, it also checks quietly about once a minute whether the Mac's library changed (EP91), so a worksheet the Companion prepares while the app is open appears without **Sync now**. `LibraryChangeMonitor` starts when the app becomes active (its first check is a minute after the foreground sync) and stops when it resigns active. Each check is one TLS-PSK connection found by the same Bonjour browse, carrying only HELLO and GET_DIGEST (`LibraryChangeProbe`): no manifest and no PDF. Measured against the real `SyncServer` over TLS-PSK on loopback, one unchanged check put 653 bytes of TCP payload on the wire (351 up, 302 down: the TLS handshake and four frames) and took about 6 ms, Bonjour aside; the real library's manifest, which a sync fetches, is roughly 150 to 200 KB. Only when the digest differs from the manifest the library last filed does the check run the usual sync, which downloads only the changed PDFs and backs up ink as every sync does. The check shares the sync's one slot, so a check and a sync never overlap; **Sync now** during a check cancels the check and syncs straight after it, and a check never runs while a sync does. It shows nothing itself: no status line, no error. A sync it starts shows its progress in the sidebar footer like any sync, and the library updates as it does today.

A check is skipped while Low Power Mode is on and while a worksheet is open, and runs as soon as the last open worksheet closes, so an open worksheet is never interrupted or reloaded. If a sync could not file a changed worksheet because it was open (the existing open-worksheet rule: it waits), the check after it closes syncs again and files it; it does not sync again for the same Mac library while the worksheet stays open. When the Mac cannot be reached (Companion closed, Mac asleep or out of range), or a sync the check started did not finish, the next check waits twice as long, up to five minutes, and returns to a minute after the next answer. A Companion from before EP91 only speaks versions 1 and 2: the iPad asks it nothing and stops checking until the next return to the foreground, and launch, foreground and **Sync now** still sync. A Mac with no library prepared counts as unchanged. Nothing about pairing, the TLS-PSK channel or the Companion's Prepare changes; the Companion serves GET_DIGEST from the same Outbox manifest, and a check is not counted as a sync in its header or held awake for.

Battery: an unchanged check wakes the Wi-Fi radio for well under a second to browse Bonjour (usually answered from the mDNS cache), make one TLS-PSK handshake and exchange those few hundred bytes, about 60 small radio bursts an hour while the app is open. Each burst costs a few tenths of a joule at most, so an hour of checks is of the order of 10 to 30 J: about 0.01 to 0.03% of an iPad battery of roughly 30 Wh (about 110 kJ), while the screen alone uses several thousand joules in that hour. This is an estimate from typical Wi-Fi power figures, not an on-device measurement. An unreachable Mac costs more per check (the Bonjour browse waits up to 8 seconds), which is why those checks back off to every five minutes.

`LibrarySyncDownloader` sends HELLO, asks for the manifest, plans it against the library with `DiffPlanner` and requests by SHA-256 only the PDFs an import, replace or new-version action needs. Each PDF is written to a hidden partial file and gets its `<sha256>.pdf` name only after the session has matched its size and SHA-256; bytes that do not match are dropped. The sidebar footer shows progress by bytes and files. The manifest is written last, atomically, in the same `EmberLibrary/manifest.json` and `files/` layout as the Inbox delivery, in `Application Support/Sync` (outside the Files-visible Documents folder). PDFs already verified stay for the next sync, which fetches only the rest.

The download is then filed by `LibraryDeliveryApplier.applyNewest`, the one manifest path for both routes: of the Inbox copy and the sync download it applies the one with the newer `generatedAt` (sync on a tie) and never the older one in the same check. The applied-delivery receipt now records the manifest's `generatedAt`, so an older manifest arriving later by either route is skipped as superseded instead of archiving papers the newer one added. All the Inbox rules above hold: ink is saved first, an inked copy gets an **Updated** version beside it, an open worksheet waits, and a cut-short sync files what arrived and archives nothing. After a complete apply the downloaded PDFs are removed, since the library holds them. **Last synced** is recorded only when the whole download arrived and the library holds a manifest at least that new.

The EmberSyncKit tests run EP-16's ink-safety tests over both routes, and run the client against a minimal in-test server built on `WireServerSession`, in memory and over real TLS-PSK loopback sockets. Bonjour browsing against an advertised in-test server runs only with `EMBERPAD_BONJOUR_TESTS=1`, because it uses the local network. The iPad tests drive `SyncClient` through `LibraryController` with synthetic PDFs.

### Ink backup to the Mac

On each sync, once the library download is filed and **Last synced** recorded, the iPad backs up its ink to the paired Mac over the same TLS-PSK connection (EP-33). It sends every Student worksheet whose ink changed since the Mac last confirmed a copy, as two files: an `.emberink` package (every inked page's PencilKit drawing, restorable as editable ink) and a flattened PDF (the same rendering as **Export flattened PDF**). Open worksheets are saved first; the backup only ever reads the library. The iPad remembers what the Mac confirmed in `Application Support/Backup/ledger.json`, per pairing, so pairing a new Mac sends everything again, and anything that did not reach the Mac is sent on the next sync. The sidebar's Mac sync line shows "Backing up ink to your Mac…" while it runs, then when the ink was last backed up and, on its own line, why a backup did not finish. A backup failure never fails, slows or undoes the library sync: a refused or failed copy, a dropped connection or leaving the app stops only the backup. A Companion from before EP-33 still syncs the library; the iPad asks for it to be updated. Nothing is ever sent back: the Mac never sends a backup to the iPad or changes its ink. Restoring inside the app is not part of this package.

On the Mac, the Companion's iPad section shows the **Ink backup** folder, when the last backup arrived, **Choose backup folder…** and **Show in Finder**. The folder defaults to `~/Library/Application Support/EmberPad/Ink Backup`. A folder inside Google Drive or any `~/Library/CloudStorage` folder, inside `~/Documents/Ember Projects` or inside the Outbox is refused (symlinks are resolved first), and a saved folder that later fails that check falls back to the default with a note. Changing the folder keeps earlier copies where they are. Copies are kept by subject and paper:

```text
Ink Backup/<Subject>/<Paper>/2026-11-06 19.42.10 ink 1A2B3C4D.emberink
Ink Backup/<Subject>/<Paper>/2026-11-06 19.42.10 annotated 1A2B3C4D.pdf
Ink Backup/<Subject>/<Paper>/.backup-index.json
```

`<Paper>` is the paper key without its subject (`Unit 1 - Paper 2`), or the title for a loose import; the time is when the copy arrived; the last part is the start of the iPad document id. Every copy is kept: nothing is overwritten or deleted, and a copy identical to the newest one of the same document and kind is answered "already held" instead of being kept twice. Each copy is written to a private file under `.incoming`, checked against its announced size and SHA-256, flushed to disk and only then linked into place under a name that cannot replace an existing file, so the folder never shows a partial copy. `.backup-index.json` lists every copy with its document id, title, SHA-256, size and arrival time. Names from the iPad are cleaned into single folder names and can never point outside the folder.

`InkBackupTests` cover the frames and version gating, PUT sessions (credit, already held, a hash mismatch, a storage failure, cancel and a stall), the folder (versions kept, nothing overwritten, cleaned names, no partial copy, refused locations), the ink package and the ledger, and loopback syncs: in memory, and over the real `SyncServer` with TLS-PSK sockets, with the real `LibrarySyncDownloader`. They show the upload, a new version on each ink change, a connection lost partway through a copy leaving the library sync whole and the rest sent next time, a copy the Mac fails or refuses, an older Mac, and an older iPad. The iPad tests drive `SyncClient` with real PencilKit drawings.

#### Restore drill

Run this drill once on a spare synthetic worksheet before relying on the backup, and again after any EmberPad update.

1. **Read the ink at once.** On the Mac, open the newest `annotated` PDF for the worksheet in Preview (Companion › **Show in Finder**, then the subject and paper folder). It needs nothing from EmberPad. To have it on the iPad as a read-only page, AirDrop it and **Import from Files**; its ink is part of the page and cannot be edited.
2. **Get the worksheet back.** Reinstall EmberPad, pair again and sync, so the library downloads the PDF again. It gets a new document id.
3. **Unpack the editable ink.** In the same folder, decode the newest `.emberink` file into page drawings:

   ```sh
   python3 - "<the .emberink file>" "$HOME/Desktop/restored-ink" <<'PY'
   import base64, json, pathlib, sys
   package = json.loads(pathlib.Path(sys.argv[1]).read_text())
   assert package["format"] == "emberpad.ink/1"
   out = pathlib.Path(sys.argv[2]); (out / "ink").mkdir(parents=True, exist_ok=True)
   layout = package.get("layout")  # present only when pages were added, moved or turned in Ember Slate
   ids = [p["id"] for p in layout] if layout else [f"pdf-{i}" for i in range(package["pageCount"])]
   for page in package["pages"]:
       (out / "ink" / f"{ids[page['page']]}.drawing").write_bytes(base64.b64decode(page["drawing"]))
   if layout:
       (out / "pages.json").write_text(json.dumps({"format": "emberpad.pages/1", "pages": layout}, indent=2))
   print(package["title"], "- drawn on the PDF with SHA-256", package["pdfSHA256"])
   PY
   ```

4. **Check it is the same PDF.** The printed SHA-256 must equal `shasum -a 256` of the worksheet's PDF in the Outbox (`~/Library/Application Support/EmberPad/Outbox/files/<sha256>.pdf`). If the paper was revised since, the ink belongs to the older version: use the flattened PDF instead.
5. **Put the ink back.** With EmberPad closed, use Xcode › Window › Devices and Simulators › EmberPad › Download Container, copy the restored `ink` folder (and `pages.json`, when the script wrote one) into `AppData/Library/Application Support/Library/<new document id>/` (the folder whose `doc.json` names that worksheet), replacing what is there, then Replace Container. Open the worksheet: the ink is editable again, and the next stroke saves it as usual.

**Moving the tool palette** (EP100, made floating in EP101, carried with no hold in EP102, carried freely in EP104). GoodNotes 6's Writing Tools menu floats over the page: its support article says to drag the floating menu to a screen edge, where it snaps to the top, bottom, left or right and turns upright on the sides. Ember Slate's tool palette works the same way. It is a rounded capsule as long as its tools, floating 10 pt in from an edge of the worksheet below the header, and the page no longer makes room for it: the page runs under it, as in GoodNotes. As in GoodNotes 6 there is no hold (EP102): touch the palette with a finger (on a tool or between them) and drag, and the palette itself moves with the finger once it has travelled 6 pt (less is a tap's drift), raised a little, with the tool the finger landed on staying under the finger the whole way; that tool is not chosen. A finger held still on it for 0.3 s picks it up too. While it is carried it keeps its shape and goes wherever the finger takes it, and nothing shows where it will land (EP104): no band or outline along an edge and no tick as it nears one; the finger picks it up and lets it go, and only then is its place chosen. Let go and it snaps with a short spring (a 0.2 s ease with Reduce Motion) to the edge nearest the finger, or to where a flick was heading (a finger that held it still before letting go never flicks it on, EP104), and along that edge it lands where it was carried to (straight in to the edge when it stays flat or upright, centred on the finger when it turns), kept whole on the screen. Across the top (the default, centred) or the bottom it lies flat; down the left or right it is a 56 pt column with the same tools in the same order, then the active tool's widths and colours stacked, the eraser's Partial and Whole as two buttons, and no lasso or laser hint (they need a row's width). When its tools are longer than the edge it scrolls. The Teacher copy panel slides over the palette like Slide Over, and on the pull tab's side the palette keeps clear of the tab, so the tab and the edge swipe (EP97) still work. The page pill moves up above a palette at the bottom. The edge and the place along it are kept with the other tool settings (`toolbarDock` and `toolbarAlong`, 0 to 1, in `toolState.v1`; settings stored before EP100 read as the top and before EP101 as centred), so every worksheet and the next launch open with the palette where it was left. Only a finger moves it: Apple Pencil never does, so a Pencil tap on the palette still picks a tool and Pencil writing on the page carries on while a finger moves it. A touch that lifts before it moves is a tap. When the palette is too long for its edge and scrolls, a drag along it scrolls it, and a drag across it (or after a hold) carries it. Every tool, its controls and its settings popover work on every edge, and a popover opens over the page beside the palette. Read-only hides the palette on every edge. VoiceOver offers Move tools to the top, bottom, left and right on the palette. Why EP100's row never moved on the iPad (EP101): a hold on a tool landed on a SwiftUI button, whose own touch recogniser began at once and, because a long press can be prevented by default, UIKit failed the hold within a millisecond, long before 0.3 s. The palette's recogniser now cannot be prevented, and when it begins it cancels the button's touch so the held tool is not tapped. The unit test could not catch this because it fed the drag's phases to the editor directly; `EmberPadUITests/ToolbarFingerDragUITests.swift` now drives real touches through UIKit (XCUITest press and drag, launched with the debug-only `-EmberPadUITestWorksheet` argument, which seeds a synthetic worksheet): it holds a tool and drags the palette to every edge, checks taps still pick tools, and reopens the worksheet to find the palette where it was left. It fails on the EP100 build and passes now. Why EP101's drag felt laggy and stepped (EP102): it was a 0.3 s long press, so nothing moved until the hold ended; it then hid the palette and drew a smaller raised copy centred on the finger, so the tool the finger held jumped away from under it; the copy flipped between a row and a column as the target edge changed, inside a spring animation; and every move rewrote state on the whole editor screen. Now the palette itself is moved by a render-only offset that only the palette reads, from a recogniser that begins after a few points of travel. `EmberPadUITests/ToolbarDragTrackingUITests.swift` measures it with real touches through the debug-only `ToolbarDragProbe`, which on every display frame compares where the held point of the palette is drawn with the finger. In the Simulator, a held drag on the EP101 build drew the held tool up to 129 pt from the finger (median 115 pt) and dropped frames (50 ms gaps), and a drag with no hold never moved it; now a drag with no hold picks it up within two frames, it is drawn a median 7 pt from the finger at 400 pt/s, which is exactly the one frame any drawing takes to show the finger's latest move, and never more than that one frame behind, with no dropped frames. `EmberPadUITests/ToolbarFreeDragUITests.swift` (EP104) carries it with real touches to the bottom and to the right side, and lets it go mid-page, near the left, and across from the left side to the right (where, held still before the lift, it lands as far down the side as it was carried, not flicked on by its last move), with the probe also comparing the window during the carry against the window at touch-down everywhere but round the palette: on the EP102 build the target edge's band changed about 4,500 square points of it and the tests fail; now nothing does. Let go mid-page, it flies to the nearest edge over about 20 frames, the largest step about 50 pt of a 370 pt flight, at rest in about half a second, where it was carried to along that edge. **Straight lines (always straight, draw and hold).** The highlighter's "Always straight" switch is on by default, like GoodNotes' "Draw in Straight Line": a highlighter stroke drawn with the Pencil that already looks like a line (its ends at least 80% of its length apart, the pen's test) becomes a straight line from its first to its last point when the Pencil lifts, with no guide while it is drawn (EP71); a stroke that doubles back or scribbles over a word stays as drawn, and strokes brought back by undo or redo are left alone. The fountain pen's "Draw and hold: straight line" switch (on by default, like GoodNotes' pen Draw and Hold) snaps a held pen stroke the same way, but only when the stroke was already close to a line when the hold latched (its ends at least 80% of its length apart), so a held letter, curve or closed loop stays as written and a held closed loop is still circle to lasso. As in GoodNotes (EP96), the moment a pen hold latches the stroke is drawn as that straight line, in the pen's own ink, colour, width and pen feel, with no guide; while the Pencil stays down the line's end follows it (led by the Pencil's predicted touches), its start stays put, and the lift commits exactly the line last drawn, with its end tip, as one undo step named "Straight Line". The line's end keeps up with the Pencil however long the line is (EP103). PencilKit redraws the whole line for every move and used to queue the moves it could not keep up with, so a long held line fell up to 2 s behind the Pencil and went on moving after it stopped; now the line's layer has one drawing in flight and only the newest waits. In the Simulator, with a 60 Hz synthetic Pencil and a screen recording, the end of a 520 pt held line lags the Pencil by a median of 0 ms and a p90 of 17 ms, against 367 ms and 900 ms before on a blank page (82 ms and 300 ms before on a 3000-stroke page). The line is drawn from its two ends, so moving it about costs the same however long the Pencil was held, and a held line is never taken for a scribble to erase, however its end was moved over writing (before EP96, moving a held line round and back over a 3000-stroke page erased 679 strokes on lift). Measured in the Simulator on a 3000-stroke page, EmberPad's own work per Pencil move after the hold went from a median of about 2.1 ms, with stalls of 89 to 236 ms, to about 1.2 ms with none over 17 ms (`HoldToLineTests`). See [the result](docs/screenshots/straight-lines-light.png). With the highlighter's "Draw and hold: straight line" switch on (the default; it is greyed while "Always straight" is on), holding the Pencil still (within 1 pt) for 0.5 s during a highlighter stroke marks it to snap; a dashed accent guide then shows the line, and further movement only moves its end. On lift, the marker stroke is replaced by a straight one from its first to its last point with the same ink and median width. A highlighter line within ±3° of horizontal is laid flat halfway between the heights of its ends (EP71, as GoodNotes); a held pen line within ±8° is laid flat at the height it began. The stroke and its snap are one undo step: one undo removes the straight line and redo restores it. Each page canvas carries a passive `HoldRecognizer` beside PencilKit's drawing recogniser that never recognises, cancels or delays touches, and the swap happens only after PencilKit commits the stroke and holds no other, at the first safe display frame (EP94), so ink is never held back or lost. The geometry is pure (`StrokeSnap`) and unit-tested; `HoldRecognizer` only reports holds; circle to lasso reuses it. First-stroke latency and undo on the actual iPad still need the device check.

**Highlighter and eraser as in GoodNotes** (EP71). The page ink multiplies into the PDF page instead of covering it, on the iPad, in the flattened export, in page thumbnails and on the student display, so black print stays black under a highlight instead of turning olive. On white paper multiplying changes nothing, so pen ink there looks as before; pen ink drawn after a highlight still sits on top of it. The highlighter's three widths are 7.5, 8 and 19.6 page points (the middle, GoodNotes' 2.8 mm, is the default; the thick is its 6.9 mm). PencilKit draws a marker no thinner than 7.5 points, so the thin one is 7.5 and no width changes when the Pencil lifts (EP75). Its presets are GoodNotes' five (#FFFF82, #00FF00, #FFDEEB, #00FFFF, #FF00FF) at an alpha that shows yellow as GoodNotes' #FFFFC1 on white; saved settings map the old yellow, green and pink to the new yellow, green and pink, keep custom colours and the selected colour, and gain cyan and magenta. Saved width and eraser-size choices keep thin, middle or thick and small, medium or large. "Erase highlighter only" now removes highlighter ink in both eraser modes and leaves every pen stroke (before EP71 it erased nothing). The eraser defaults to Whole stroke for a new install; a saved choice is kept. The stored ink format is unchanged.

**Shapes** (EP64, after the highlighter, GoodNotes' slot) turns a Pencil stroke into a clean shape when the Pencil lifts: a line, an arrow (a shaft with a barb on each side, drawn in one stroke), a rectangle or square, a triangle, a polygon of up to eight corners, or an ellipse or circle. Lines, rectangles and ellipses within 8° of level or upright are set level or upright, and a rectangle or ellipse within 10% of equal sides becomes a square or circle. A stroke that is none of these (a scribble, a word, a curve) stays as drawn. Shapes take the pen's three widths and its colour presets, shown in the strip as for the pen, and are drawn as wide as the fountain pen's line. Tapping Shapes again opens its settings, as GoodNotes': **Snap to other shapes** (on by default) moves a new shape's corners and line ends onto another shape's corner or line end within 12 pt (a rectangle or square moves whole so it stays square), and **Fill colour** (off by default) tints closed shapes with their stroke colour at 20%. Both are kept in `toolState.v1`; settings saved by an earlier build read them as their defaults. Recognition is pure (`ShapeRecognizer.swift`) and runs in the same swap as draw and hold: the freehand stroke and its clean shape are one undo step named after the shape. Shapes are ordinary PencilKit strokes (`ShapeInk.swift`), so lasso, eraser, undo and redo, export, thumbnails, the student view and the ink backup treat them as other ink and the stored drawing format is unchanged: an outline is one stroke in PencilKit's plain pen ink, which no other tool writes, and a fill is one more stroke under it, a translucent disc of the same ink clipped to the shape by a stroke mask (the kind PencilKit's own eraser leaves), so a worksheet written on an earlier build opens as before and a build without the Shape tool shows shapes and fills as they look here. A lasso around a shape takes its fill with it, and recolouring keeps the fill translucent. Read-only mode blocks the Shape tool with the other tools. See each [freehand stroke beside its clean shape](docs/screenshots/ep64/freehand-beside-clean.png), the [shapes on a worksheet](docs/screenshots/ep64/clean-shapes.png), [fill on with a snapped line](docs/screenshots/ep64/fill-and-snap.png), the [settings](docs/screenshots/ep64/settings-popover.png) and the [student view](docs/screenshots/ep64/student-view.png), from a synthetic worksheet with strokes sent through the real page controller (Simulator cannot synthesise Pencil touches). Recognition on a real hand needs the device check.

**Eraser circle** (EP68, as GoodNotes shows it). While the eraser touches a page, a light grey see-through circle with a thin outline is centred on the Pencil tip and follows it, and it goes on lift. It is the area the eraser erases at the zoom on screen. The partial eraser's circle is the PencilKit tool's own width in screen points, because PencilKit erases the same on-screen width at every zoom: zooming in leaves the circle the same size and it covers less of the page. PencilKit's partial eraser takes only 16.4 to 80.4 points (iOS 26.5) and raises anything smaller to 16.4, so the old 8 and 16 pt sizes erased the same width. EP68 made the three sizes 16.4, 32 and 64 pt; EP71 makes them GoodNotes' 25 (small), 50 (medium, the default) and 80.4 pt (large: GoodNotes erases about 100, but 80.4 is PencilKit's maximum), so each size erases, and shows, its own width. Saved settings keep their small, medium or large choice. The whole-stroke eraser's circle is its chosen size too (EP99, below). On an iPad with Apple Pencil hover the same circle shows while the Pencil hovers over a page with the eraser chosen; elsewhere the hover recogniser never fires. The circle is a layer above the pages on this iPad only (`EraserPreview.swift`): it is never ink, and is not on the student view, in exports or thumbnails, or in the undo history. It also never claims a touch, because a second observing recogniser like live ink's moves it. Read-only mode and other tools show no circle. Erase highlighter only and back to last tool work as before. On iOS 26.5 PencilKit itself draws a faint grey ring for the partial eraser, which the circle covers exactly. Tests hand stand-in Pencil touches to the drawing recognisers and check that the gap the partial eraser cuts, and the strokes the whole-stroke eraser removes, match the circle at each size and at zooms from 0.6x to 4x. See the [before and after at each size and zoomed](docs/screenshots/ep68/before-after.png), the [editor mid-erase](docs/screenshots/ep68/editor-partial-large.png) and [after lift](docs/screenshots/ep68/editor-after-lift.png), taken halfway through a real PencilKit erase in the Simulator. **Whole-stroke eraser sizes** (EP99, as GoodNotes). The whole-stroke eraser comes in the partial eraser's three sizes, 25, 50 and 80.4 points across on screen, chosen with the same size dots in the toolbar, and every stroke its circle touches goes, whole, as the Pencil passes over it. GoodNotes' eraser has one size whichever mode is chosen, so both modes share one size choice: a size picked in one mode is the other's too, and it is saved with the other tool settings (`eraserSizeIndex`, unchanged), so a saved small, medium or large keeps its meaning. Like the partial eraser it erases the same on-screen width at every zoom, so zooming in erases more finely. PencilKit's own whole-stroke (vector) eraser has no width (its `validWidthRange` is 0...0 on iOS 26.5 and every width asked for erases the same 3.5 page points either side of the tip), so the whole-stroke eraser is EmberPad's own (`WholeStrokeErase.swift`): while it is chosen PencilKit's drawing recogniser is off and a recogniser like the laser's takes the Pencil, so the Pencil neither inks nor scrolls the pages, and fingers still scroll and zoom. A stroke goes when its ink (its line plus half its width) comes within the circle anywhere along the Pencil's path; a stroke the partial eraser cut counts only where it still shows. Each eraser stroke is one undo step named "Erase". It changes a page only while PencilKit holds no uncommitted stroke (EP94): a pen stroke written just before the eraser was chosen is committed first and the sweep waits for it, so it is never thrown away. Erase highlighter only removes only highlighter strokes and leaves pen ink, and Back to last tool on lift switches back once the erase is done. The partial eraser, scribble to erase and the ink-edit gate are unchanged. See the Simulator captures mid-erase with the [small](docs/screenshots/ep99/whole-stroke-small.png) and [large](docs/screenshots/ep99/whole-stroke-large.png) whole-stroke eraser (synthetic worksheet).

**Fountain pen feel and tip sharpness.** The fountain pen aims at GoodNotes' Fountain Pen at Tip Sharpness maximum and Pressure Sensitivity minimum: a fine, even, pure-black line about 1.22 pt wide at the middle width (2.5), as GoodNotes draws 0.3 mm, the same width in every direction at Min (within 4%; a little thinner on up-right diagonals as pressure sensitivity rises), barely swelling with pressure, with ends that thin to sharp points over about 9 pt. The ink does not change when the Pencil lifts (EP56): only the end tip is added. PencilKit has no public hook into its own live stroke, so PencilKit still takes the Pencil (palm rejection, the commit, undo) in a clear monoline nobody sees, while `LivePen.swift` draws the stroke from the same coalesced and predicted Pencil samples (position, time, force, tilt) with the shape below, in a passive PencilKit layer of its own above the page's ink, drawn at the page's ink zoom. The start tip grows in while the stroke is written; predicted samples are drawn and dropped on lift. Once PencilKit has committed the stroke it is swapped for exactly the stroke drawn live plus its end tip, keeping its creation date. No swap, and no other change to the page's ink (draw and hold, a shape, scribble to erase, circle to lasso), lands while PencilKit holds a stroke it has not committed or the Pencil is down: setting the drawing then makes PencilKit throw that stroke away, and that was the bracket that vanished in class (EP94). The pen's swaps wait for half a second's pause in the writing (or until 32 are waiting) and land together on a display frame after the latest commit, each as its own undo step. Meanwhile the live layer keeps drawing each waiting stroke, and the page saves it visible, so the file and the student view never show a gap. If PencilKit throws a stroke away all the same, the live layer's copy goes on the page as its own undo step, never twice. On a slow run loop (a slow device, or a loaded CI runner) PencilKit can also group a burst's undo steps out of order, make a stroke's step only after the stroke has landed with its own (a late step that then takes back nothing, or only that stroke), leave a step that changes nothing for a stroke it threw away, or take a stroke it has committed back off the page, outside undo, as it commits the next one. The stroke taken back goes back on the page, every stroke still lands with the pen feel as its own undo step, and PencilKit's steps that change nothing or only repeat a landed stroke's own are dropped, so no stroke is lost and every tap of undo takes back one stroke (EP98). Before, a stroke taken back was lost and the strokes after it stayed in PencilKit's monoline: on the CI runner, 1 of 24 fast brackets. If a swap cannot apply (the page changed some other way), the clear stroke is given back the pen colour at full opacity, outside the undo stack. A clear stroke in a file saved by an earlier build is made visible when its page opens, so a written stroke is never left invisible. The student view's provisional line takes the pen colour and the shaped stroke's middle width. Each point's width is rebuilt from the pen width the stroke was drawn with, its force (smoothed; at Min pressure only reduces the change, within about 0.65 to 1.45 times), the stroke direction and the tip taper, and its nib is turned across the stroke, because PencilKit's committed fountain ink draws 2 × (size − 2) points across the nib and a quarter of that along it (measured in the Simulator). Position, timing, force, altitude, opacity, colour, transform and random seed stay as written. The ink is a new fountain-pen ink, never the committed one: PencilKit commits live fountain-pen strokes with an older ink (content version 2) whose seeded grain, at about 1 pt, breaks into a beaded grey fringe with about half the ink; the new ink draws the same points as one clean line at every zoom. The pen settings popover keeps its Tip sharpness slider: 0 to 100% in five ticks, default 100%, with the footer "Applied when the Pencil lifts." At 100% each end tapers over 9 pt at the middle width (3.6 pt per point of pen width), never more than half the stroke, to a quarter of the width; lower settings taper less, and 0% keeps blunt ends while still drawing the fine line. Strokes shorter than 3 pt at the middle width (dots, decimal points, charges, short arrowhead barbs) keep blunt ends. A pen stroke snapped straight by draw and hold takes the same pen feel in the same swap. Strokes already cut by the eraser, loops taken by circle to lasso and highlighter strokes are left alone. The stroke and its new shape are one undo step named "Ink": one undo removes the stroke and redo brings back the reshaped one. The pressure sensitivity setting (default Min) is read by the reshape but has no slider yet. Settings saved by an earlier build keep a tip sharpness the user chose; the old default (50%), saved before the choice was recorded, becomes 100%, so a 50% the user had picked by hand also moves to 100% once. While it is written the stroke already has its width, its thick-thin variation and its start tip; unit tests check that lift changes no ink away from the end tip. Strokes written on an earlier build keep the older ink. See a [worksheet at 0, 50 and 100%](docs/screenshots/pen-feel-tip-sharpness.png) (synthetic strokes committed through the real page controller in the Simulator). On the iPad Air 4 the ink no longer changes at lift and long strokes do not stutter. Each stroke stays in its own live layer from pen-down until the page has drawn it (EP103), so the lift no longer hides it for a moment while another layer catches up (before, it vanished for 70 to 80 ms on a fresh page), and what lands is pixel for pixel what that layer showed. When a stroke lands, PencilKit redraws the page in 256 pt tiles, from the middle of the screen outwards, over up to a quarter of a second, and only then reports it; the stroke's layer is masked off each tile under it as soon as that tile has been redrawn, and hidden once all have been, so the stroke is no longer drawn twice, bolder, until the report (on a 3000-stroke page, 5 to 7 doubled frames before, 0 or 1 after). If an earlier redraw is still under way when the stroke lands, as for a held line landing at once on a busy page, the layer waits for the report as before (about 60 to 100 ms doubled). Measured in the Simulator with a 60 Hz synthetic Pencil and a screen recording, the ink tip stays about a frame behind the Pencil (median 16 to 17 ms, worst 19 to 39 ms, against up to 1.8 s before), and the longest main-thread gap while writing fell from 125 ms to 78 ms (`InkFollowsThePencilTests`). In the Simulator, a long slow stroke shows one or two screen freezes of 100 to 245 ms that the old monoline did not, with the main thread free and each live update about 5 ms (compositing between PencilKit's hidden live stroke and the live layer); watch for it on other iPads. The real Pencil force range needs the device check.

**Scribble to erase** (EP82, made more eager in EP90; GoodNotes' pen gesture; on by default, tap the pen twice, Pen gestures). Scribbling with the fountain pen over ink erases the strokes it goes through, and the scribble leaves no ink. GoodNotes asks for "a tight zigzag over the strokes" or "horizontal lines back and forth over the strokes"; both work, as do a loose zigzag of two or three peaks, a row of loops along the word and a quick scrub of three passes over one word. A stroke has a scribble's shape when it turns back on itself along one axis at least twice (three passes), the passes going back over the same ground. A stroke on the page then goes, whole, pen, highlighter and shape ink alike, when the scribble crosses it (not only near one of its ends) and at least half of it is near the scribble's line and within its reach (a third, when four or more passes cross it, as for a tall h or l under a thin scrub). So does a stroke at least half inside the scribbled area (between one pass and the next), and a short stroke crossing one that goes (a t's bar, the second stroke of an x). A scribble only acts on ink: it must go through ink with at least three of its passes, or with two passes through two strokes. One over empty paper, beside ink, round it (a lasso loop), as shading inside a box, or written with the switch off stays as drawn. One letter can have a scribble's shape (m, n, u, w), but handwriting only touches other ink (a joined letter, a t's bar, a descender from the line above), which is too little, or too near the other stroke's end, to erase it. The synthetic fixtures (`ScribbleFixtures.swift`) hold the proof: 582 scribbles drawn at Pencil rate over words in print and joined up, at three sizes and speeds (EP82's rule erased 298 of them), each erase exactly their word and nothing on the lines above and below or beside it, and 179 cases of handwriting near ink and 3 scribbles over empty paper erase nothing, at any point while they are written. **The preview** (EP90): while the scribble is drawn, as soon as it would erase anything, the ink it will erase is outlined with the toolbar lasso's own line (the same dashed accent line and faint fill, from the same code), round all of it. The outline follows the scribble as it grows, goes when the stroke stops being a scribble or is cancelled, and never shows for handwriting or over empty paper. When the Pencil lifts, exactly the outlined strokes are erased. It is judged against the page's ink near the scribble only, so it keeps up at Pencil rate on a page of 1,500 strokes. See the EP90 frame strip from the iPad Simulator (synthetic worksheet): [scribble preview](docs/screenshots/ep90/scribble-preview.png). The erased strokes and the scribble go as one undo step, "Scribble to Erase": undo brings the ink back without the scribble, and redo erases it again. It runs once PencilKit has committed the stroke and holds no other, at the first safe display frame (EP94), and the scribble's ink is never on the page: PencilKit's copy is clear, and the live pen draws it until the page has drawn the erase, so the scribble and what it erases vanish together. A scribble that erases comes before draw and hold and circle to lasso, so the outline is kept even if the Pencil rests at its end; every other stroke snaps and lassos as before. The highlighter, the Shape tool and Apple's Scribble (handwriting to text) do not scribble to erase. The geometry is pure (`ScribbleErase.swift`; the page side is `ScribblePreview.swift`) and unit-tested; a test also drives a zigzag through PencilKit's own recogniser with stand-in Pencil touches. Recognition on a real hand needs the device check.

**Circle to lasso and the selection.** With the pen's "Circle to lasso" switch on (the default; tap the pen twice, Pen gestures), a pen stroke that ends closer to its start than 30% of its larger side (and at least 16 pt across), held still for 0.5 s at the end, selects the ink inside it. GoodNotes' form works too: lift the loop, then within 4 s long-press its line with the Pencil (0.5 s still, within 20 pt of the line); the press leaves no dot. A stroke is inside when at least half of the points sampled along it are, by the nonzero winding rule, so a loop drawn twice round or a figure of eight still holds its middle. The loop is not kept as ink and never returns on undo or redo; a held loop round nothing stays as drawn. A "Circle to lasso · selected" toast shows, and the tool stays on the pen. The toolbar lasso selects the same way, by drawing round ink with the Pencil (the loop need not close). PencilKit has no public API to set a lasso selection or to give its own lasso resize and rotate handles, so both use EmberPad's own selection layer (`SelectionOverlay.swift`, geometry in `SelectionGeometry.swift`); PencilKit's drawing recogniser is off while the lasso tool is chosen. The selection works like GoodNotes': on lift only the dashed lasso shows, with no box, handles or menu. A tap inside the selection opens a one-line menu beside it, above or, when there is no room above, below: Cut (Copy then Delete), Copy (PencilKit drawing data plus a PNG on the pasteboard), Delete, Duplicate (a copy 20 pt down and right, then selected), Resize and Color (the current pen colour presets; a highlighter stroke keeps its ink type and transparency). GoodNotes' overflow items (Take Screenshot, Add Element, Convert) are not offered yet. Drag inside to move. Resize draws the box round the ink with a red × at the top left, which goes back to the lasso, and one round handle at the bottom right: one drag on it scales the ink (keeping proportions) and turns it about the top-left corner, snapping to quarter turns within 4°. Dragging inside still moves. Each move, Resize drag, Cut, Delete, Duplicate and Color is one undo step; a move or Resize is one `PKStroke.transform` change on the selected strokes. With EmberPad ink copied, a finger long-press on a page offers Paste: the ink is centred on the touch, kept on the page where it fits, selected, and is one undo step. The selection is dropped by new ink, undo or redo on its page, a tool change, its page scrolling away, or a Pencil touch or finger tap elsewhere; scrolling and zooming keep it. It sits above the pages in the teacher's view only and never reaches the student view, which sees each change when it is committed. See the [Resize box](docs/screenshots/circle-lasso-selection-light.png), and Simulator captures of the [lasso on lift](docs/screenshots/ep42/01-lift-shows-only-the-lasso.png), the [menu on a tap inside](docs/screenshots/ep42/02-tap-inside-opens-menu.png), [Resize](docs/screenshots/ep42/03-resize-mode-handle-and-x.png), a [Resize drag that scales and turns](docs/screenshots/ep42/04-resize-drag-scaled-and-turned.png), the [× back to the lasso](docs/screenshots/ep42/05-x-back-to-lasso.png), [Color](docs/screenshots/ep42/06-color-red.png), the [menu below a selection near the top](docs/screenshots/ep42/07-menu-below-near-top.png), a [lifted loop](docs/screenshots/ep36/04-loop-lifted.png) and the [Paste menu](docs/screenshots/ep36/06-long-press-paste-menu.png) (a test drives the gestures, since Simulator cannot synthesise Pencil touches). Drag and Resize feel, the hold on real loops and the edit menu position need the device check.

The external scene uses `UIWindowSceneSessionRoleExternalDisplayNonInteractive`. Its model accepts only worksheet pages, committed drawings, provisional live strokes and the laser dot and trail. It shows a neutral **Paused** view while the main scene is inactive. With no worksheet open, as in the library, it shows the Ember star alone on black and no text, so no worksheet, folder or subject title reaches the class (EP92). Apple's Screen Mirroring from Control Center (AirPlay, for example to a Mac driving a projector) gets this scene too, as an HDMI display does, so the class sees the page, ink, page turns and zoom while the toolbar and the Teacher copy panel stay on the iPad, as in GoodNotes' Presentation Mode. `PresentedView` (`Apps/EmberPad/PresentedView.swift`) describes what the scene shows as plain `Codable` values (idle, paused, Teacher copy placeholder, or the page with its framing, visible rect, placed pages and their ink revisions, live strokes, laser dot and trail), read from the same student model the scene draws, for a later sender to serialize; it holds no title, answer URL or chrome state. The student view menu in the header (and the More menu) picks the framing. **Mirror Presenter Page (follow my view)**, the default, shows the worksheet viewport aspect-fit: the visible rect in page space, including zoom and up to two straddled pages, republished from scroll and zoom at 30 Hz at most. **Mirror Full Page** shows the focused canvas's whole page with a 1% margin. Editor chrome follows the viewport-centered page. Pages and ink are composited from cached bitmaps that are re-rendered only for a new zoom bucket or new ink, never per frame. Both framings draw from the same Student-only snapshot. See the [presenter](docs/screenshots/student-view-presenter-page-landscape.png), [straddled](docs/screenshots/student-view-presenter-page.png), [full-page](docs/screenshots/student-view-full-page.png) and [Teacher copy](docs/screenshots/student-view-teacher-copy-presenter.png) Simulator external-display captures. Live ink shows a stroke on the student view as it is written, not on lift: an observing recogniser beside PencilKit's reads the Pencil's coalesced and predicted touches and draws a provisional stroke, a uniform-width line in the tool's colour, over the cached bitmaps without re-rasterising the page. It never claims, delays or cancels a touch, so ink on the iPad is unchanged. Fingers, the erasers and the lasso draw no live ink. On lift the provisional stroke stays until PencilKit commits the drawing that contains it, then leaves in the same update that brings the committed bitmap, so the student view never shows both or neither; a stroke PencilKit discards leaves after a second. **Laser pointer (Dot and Trail).** The laser pointer, which sits after Image on the toolbar strip, shows a red dot under the Pencil on the iPad and at the same page point on the student view, in both framings. It is never ink: while it is chosen PencilKit's drawing recogniser is off on every page and a Pencil-only `LaserPointerRecognizer` on the PDF view takes the Pencil, so nothing is written and the pages do not scroll under it; fingers still scroll and zoom. Lift and the dot goes. On the iPad the dot keeps the same size at every zoom; on the student view it is sized from the shown area so it stays visible on a projector. Off the pages the iPad dot still follows the Pencil and the student view shows none. The student view's dot is held in `StudentLaserPointer`, built only through `StudentSafeDocument` like live ink, so a Teacher copy's dot stays on the iPad. Tap the laser again for its settings: Dot (the default) or Trail, kept in `toolState.v1` with the other tool settings. See the [iPad worksheet](docs/screenshots/laser-ipad-worksheet.png), the student view in [presenter](docs/screenshots/laser-student-presenter-page.png) and [full-page](docs/screenshots/laser-student-full-page.png) framing, [after lift](docs/screenshots/laser-student-after-lift.png), a [Teacher copy](docs/screenshots/laser-student-teacher-copy.png), the [strip](docs/screenshots/toolbar-strip-laser-light.png) and the [settings](docs/screenshots/tool-settings-laser-light.png). The student captures host the real `StudentDisplayView` at 1920 × 1080 in the test app, and the dot enters through the controller's laser events because Simulator cannot synthesise Pencil touches. In **Trail** mode the dot also leaves a red glowing line, a red core over a wider faint glow, on the iPad and at the same page points on the student view. Each point fades out over 1 s after it is drawn, so the line shortens behind the Pencil, and a second after lift nothing is left; putting the laser away or leaving the worksheet clears it at once. The trail is pure (`LaserTrail`), drawn by `LaserTrailLayer` in ten opacity steps of two shape layers each, so moving or fading it only replaces paths and never re-rasterises the page. A lift or leaving the page breaks the line, and the student view's trail never joins two pages. The student trail is held in `StudentLaserTrail`, gated through `StudentSafeDocument` like the dot, so a Teacher copy's trail stays on the iPad. Trail mode only changes what is drawn: it never inks and never adds an undo step. Debug builds expose **Device checks** in the library's Debug section, with pass/fail results for the scene, log, PDF and Pencil checks. The probe appends scene and capture snapshots to `Documents/device-checks.log`, provides a runtime-generated synthetic writing-trial PDF, and can replace the external student scene with a solid-colour, role-labelled test pattern. Its scribble recorder accepts Pencil or touch input, labels each saved drawing `erase` or `keep`, and exports the collected stroke samples as versioned JSON through Files. Samples are held in recorder state and are not persisted unless exported; they are not added to the device-check log or uploaded. Its **Pen feel probe** takes Pencil input only: write one line with the fountain pen at each of the three widths, saving each, then export `pen-feel-probe.json` (`ember.pen-feel-probe/v1`) through Files. Scribble exports now carry each point's size too; older exports without it still load. These controls are compiled out of Release builds.

The student view's page snapshot can only be built through `StudentSafeDocument`, whose failable initializer accepts only a Student-role record, from a session that supplies that record's own pages and drawings, in both framings. Live strokes are held in `StudentLiveInk`, which is built the same way and is drawn only over the same session's published page, so a Teacher copy never shows live ink. A Teacher copy opened as the main page therefore shows **Teacher copy · private** on the student view, never its pages. Private content is hidden while another screen is attached to the iPad without the student view on it (AirPlay or HDMI mirroring, or an extended display; `UIScreen.screens`, re-read when the capture trait or a scene changes), and whenever inactive. Private content is also hidden from the moment the screen is captured until the screen list settles (about 1 s), since a mirrored screen may not be listed yet. Once settled, the iPad's own Screen Recording attaches no screen, so the answers show again for the teacher's recording, and the app shows no capture message, since iPadOS shows its own recording indicator (EP54). A Mac recording over QuickTime or a ReplayKit broadcast is also treated as recording. When hidden, a Teacher copy's pages and the private-answer pane then leave the view hierarchy and draw no pixels, rather than being blurred or covered. The editor assigns the paired Teacher copy's URL as the private answer only for the teacher's main scene, and clears it when the editor disappears. AirPlay/HDMI, QuickTime, recording and capture-trait behavior must be checked with the teacher. Leaving the app can restore system mirroring; stay in EmberPad while sharing. ### Present on Mac (EP93)

Present on Mac shows the student view on the Mac over the pairing's direct wireless link, for a Mac driving a projector over HDMI, with no Wi-Fi network and no cable. It sends what the student view shows, not video: the page's paper once, then ink, page turns, scroll and zoom, the stroke being written and the laser, and the Mac draws them. It reuses the pairing, the TLS-PSK channel and the sync server; there is no new pairing step.

**On the iPad.** In a worksheet, the Sharing menu (the AirPlay icon in the header, and the More menu) has a **Present on Mac** switch, with a status row under it and a footer "Shows the student view on your Mac over a direct wireless link. No Wi-Fi network needed." A small light on the AirPlay icon shows the state: green when presenting, amber while connecting or reconnecting, none when off. Nothing connects and nothing is sent until the switch is on, and turning it off stops at once and stops retrying. Without a pairing the row says "Pair this iPad with your Mac first" and nothing connects. An older Companion gets "Update EmberPad Companion on your Mac to present", Present turns itself off, and sync is unaffected.

**What is sent.** Everything comes from the same Student-only model the external student scene draws (`StudentDisplayModel`, built only through `StudentSafeDocument`), as `PresentedView` values plus that page's paper and ink. A Teacher copy opened as the main page sends only **Teacher copy · private**: no page, paper, ink, live stroke or laser. The library sends only the idle screen (the Ember star alone), and an inactive iPad sends **Paused**. No title, answer URL, toolbar, popover or library name is ever encoded. `PresentControllerTests` encode a Teacher copy with ink, a live stroke and the laser and check that its ink and any PDF are absent from the bytes, which are under 300.

**Messages.** `PresentEncoder` compares what the iPad shows with what the Mac holds and sends only the difference. A paper goes once per page, as a one-page PDF of that page (a JPEG at most 2,400 px on its long side if the page's PDF is over 6 MB), named by its SHA-256 so the Mac never needs it twice. A page's ink goes whole once, then as only its new strokes on top of the revision the Mac holds; an erase or anything else that is not an append resends the page's drawing. The stroke being written goes as its new points only, with its predicted tail replaced each frame. Every update carries a sequence number. On every (re)connect the iPad sends a snapshot (everything the Mac does not hold, which after a reconnect is usually not the paper), then deltas; an update the Mac cannot apply in order, or an append on top of a revision it does not hold, gets a resnapshot request instead. An idle link sends a 65-byte heartbeat each second and the Mac acknowledges each one. The iPad builds updates on a `CADisplayLink` at 30 to 60 Hz and encodes and sends them on its own queue, never on the main thread; while 256 KiB are still waiting to leave it skips frames, and the next update carries everything that changed, so a weak link coalesces rather than loses.

**Reconnect.** The iPad reconnects by itself while the switch is on: a link silent for 3 seconds is dropped (the Mac's replies and each 64 KiB chunk the transport accepts count as life, so a large first snapshot over a weak signal is not cut off), and it tries again after 0.25, 0.5, 1, 2 and then every 3 seconds. Even attempts dial the paired Mac's Bonjour service directly and odd ones browse for it, both with peer-to-peer Wi-Fi on (`includePeerToPeer`). The Mac shows an amber light and keeps the last picture up while it waits; the new link's snapshot brings anything written meanwhile, so no ink is lost. Measured in process, the picture was back about 0.3 s after a dropped link. The Mac closes a present connection it has not heard from for 6 seconds, and a newer present connection replaces an older one.

**Lock and background.** When the iPad locks or EmberPad goes to the background, the student view turns to **Paused** (as for HDMI), the iPad sends that, and closes the link about 0.8 s later. Network.framework connections do not survive suspension, so Present does not try to keep one. The Mac shows **Paused** with an amber light until the iPad comes back. On return the iPad reconnects straight away (the light goes amber, then green) and the new snapshot brings the page and any ink written meanwhile. Present stays switched on across a lock.

**On the Mac.** The Companion's menu window has a **Present on Mac** section with the status, a **Show on** picker (Automatic picks the projector, the first display that is not the built-in one, else the main display) and **Hide presentation** / **Show presentation**. When the iPad starts presenting, the Companion opens its presentation window on that display by itself: borderless and covering an external display, or a full-screen-capable "EmberPad Presentation" window on the built-in one. Esc hides it. It shows the page aspect-fit on black with no chrome, the paper from its PDF, the ink from the sent PencilKit drawings, the live stroke and the laser dot and trail, and a small light in the corner: green when presenting, amber while reconnecting. While shown, it keeps the display awake. When the iPad stops presenting the window closes.

**Data.** Measured over TLS-PSK on loopback against the real `SyncServer` (`presentOverTheRealServerMeasuresBytesPerSecond`), payload bytes: idle, about 99 B/s up and 110 B/s down; writing without a break (120 Pencil samples a second sent at 60 Hz, a stroke committed every 1.5 s), about 8.2 to 8.3 kB/s up and 220 B/s down. The one-time paper for a synthetic worksheet page was about 11.5 kB. Apple's mirroring streams video of the whole screen, typically megabits per second.

**Tests and captures.** `PresentTests` in EmberSyncKit cover the round-trip of every message, Teacher copy and library content, delta sequencing and the gap resnapshot, appends that do not fit, live points, an older Companion reporting unsupported while sync still works, and a dropped link catching up with no lost strokes over an in-process loopback. `PresentEndToEndTests` (skipped unless `EP93_E2E_DIR` is set) drive the real editor in the Simulator over real TLS-PSK on loopback to a Mac-side host running the real `SyncServer`, `PresentHost` and the Companion's presentation canvas. See the [worksheet on the iPad](docs/screenshots/ep93/worksheet-ipad.png) and [on the Mac](docs/screenshots/ep93/worksheet-mac.png) (the live stroke and laser are fed in at the student model, because Simulator cannot synthesise Pencil touches), the Mac with the [Teacher copy open](docs/screenshots/ep93/teacher-copy-mac.png), [while the iPad is locked](docs/screenshots/ep93/paused-reconnecting-mac.png) and [after it came back, caught up with a stroke written meanwhile](docs/screenshots/ep93/caught-up-mac.png), and the [Present control](docs/screenshots/ep93/present-control-ipad.png). Range, a walking iPad and the projector need the device check.

### Peer-to-peer hello (Debug only)

The Device checks screen's **Peer-to-peer hello** section and the Companion window's **Peer-to-peer hello (debug)** section are used to check that the Mac and iPad can talk with neither joined to a network. The proof is a successful on-device run while neither device is joined to a network. The Companion's **Start** button opens an `NWListener` advertising `_emberws._tcp` as `EmberPad Companion (debug)`. The iPad browses for it, then **Echo and time 50 MB** connects, checks a 64-byte echo and sends 50,000,000 synthetic bytes. The Companion acknowledges the byte count and SHA-256, and the screen reports decimal MB/s plus the path interface Network.framework reports for each connection; this does not prove peer-to-peer Wi-Fi was used. Results go to the pass/fail list and `Documents/device-checks.log`. The listener, browser and every connection set `includePeerToPeer`. Keep Wi-Fi on on both devices; neither needs to join a network. Both Info.plists declare `NSLocalNetworkUsageDescription` and `NSBonjourServices`, so each app asks for Local Network access the first time; if it is denied, the screens say so. There is no pairing, key or TLS (that is EP-22): any device in range can connect to a running Debug listener, so start it only for the check. The framing, server, browser and client live in `EmberSyncKit/Sources/EmberSyncKit/PeerHello*.swift` under `#if DEBUG`. A Release build contains none of them and does not link `Network.framework`.

`swift test --package-path EmberSyncKit` runs the framing tests and an in-process 50 MB loopback transfer. To time the real Companion on one Mac, launch the Debug build with `-EmberPeerHelloAutostart YES`. It logs `EmberPad peer hello listening on port N`. Then run the skipped live test:

```sh
EMBERPAD_PEER_HELLO_PORT=N swift test --package-path EmberSyncKit --filter liveCompanion   # 127.0.0.1
EMBERPAD_PEER_HELLO_BROWSE=1 swift test --package-path EmberSyncKit --filter liveCompanion # via Bonjour
```

The library reads `embedded.mobileprovision` best-effort: amber at 48 hours or less, red below 24 hours, unknown when absent/malformed (normal for unsigned Simulator builds). This parses only a reminder, not a signature or security decision. The library shows the Inbox delivery time and, once paired, the last completed sync time; neither is shown until it has happened.
